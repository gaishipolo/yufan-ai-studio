# 个人例外（deny）

> 「只对这个人关掉某一项」—— 不动角色、不动小组，也不连累同角色的人。

## 要解决的问题

在例外出现之前，减法只能做到**共享单元**：

| 做法 | 后果 |
|---|---|
| 只撤个人授予 | **没用**。角色/小组还在给 |
| 撤角色里的这一项 | 同角色其他人一起失去，要逐个补回（漏一个就是静默降权） |
| 把他移出这个角色 | 他丢掉该角色的**全部**权限 |
| 造一个更窄的角色 | 不连累别人，但每出现一个例外就多一个角色要维护 |

## 一条规则，不是一棵树

> **只有个人层能否决**；团队、小组、角色只能给，不能否。

```
granted   = 团队 ∪ 小组 ∪ 角色 ∪ 个人授予
if 全量(*)        → 全集（不进下面任何一步）
expanded  = 摊开 资源:*
allowed   = expanded − 个人例外
effective = 页面门控(allowed)
```

实现只有一处：`core.authz.evaluate()`。`resolve_identity()` 与
`effective-permissions` 都调它 —— 任何一处再自己拼一遍集合，就会出现
「接口 403 但总览说他有权」。

### 为什么只有个人层能 deny（这是可扩展性，不是省事）

| 每层都能 deny | 只有个人层能 deny |
|---|---|
| 加一层（部门 / 外协）就要重新回答「谁压谁」 | 加层只是往 `granted` 里加，语义不变 |
| 优先级表随层数增长，且要人人记住 | 规则一句话，永不增长 |
| 排障要走完整条链 | 排障只有两个来源：给多了 / 你自己关了 |

推论（使用约定）：**组里要更少权限 → 别给那个组；个人要更少 → 个人例外。**
权限只在「应该一致的人」之间共享。

### 三条位置约束

- **摊开在减法之前**：否则角色里的 `task:*` 会把刚被否决的 `task:delete`
  又摊回来，症状是「关了但没关」，而库里那条否决记录看起来毫无问题。
- **减法在门控之前**：否决的对象可以是**页面**，「进不去那一页」是靠门控
  把它管的接口一并关掉实现的。顺序反了，页面被否决、接口还开着。
- **减法也作用于 `_actor_codes()`**：那处 `apply_page_gate=False` **只跳门控、
  不跳例外**。跳了就是提权 —— 被否决 `identity:role:write` 的人仍能把它授给别人。

## 数据

`permission_grants` 加一列 `effect`（`allow` | `deny`），唯一约束从
`(scope, scope_id, permission)` 扩成四列 —— 否则「先否决、后来又重新授权」
会撞约束。

**为什么不分表**：判定每请求要一次读出「给的和不给的」，两张表就是两次往返；
而「整组替换」「码是否合法」「删组清绑定」的规则对两者完全一样。

**为什么不在 DB 写 CHECK**：测试库是 sqlite，全库零 `CheckConstraint` 先例。
只在一半环境生效的约束等于没测。规则写在 `_validate_exceptions()` 一处，
另有一条**扫库守卫**断言不存在 `effect='deny' AND scope!='user'`。

## 接口

| 端点 | 作用 |
|---|---|
| `PUT /identity/users/{id}/permission-exceptions` | 整组替换例外，**不动授予** |
| `GET /identity/users/{id}/permission-exceptions` | 读例外清单 |
| `GET /identity/users/{id}/effective-permissions` | 增加 `sources` / `roleDetails` / `denied` / `deniedOff` |

`denied`、`deniedOff`、`gatedOff` 三者分工：

- `denied`：全部例外，**含当前无人授予的那些**（角色撤了那条例外还在，
  它必须仍然可见、可撤销，否则就是一个谁也看不见的隐藏状态）；
- `deniedOff`：授予了但因本人例外而不生效；
- `gatedOff`：授予了但所属页面没开。

后两者**互斥**。一个码不生效只有这两种原因，混在一起管理员就只能猜。

## 例外只接受「具体的、可管理的」码

| 拒绝 | 错误码 | 理由 |
|---|---|---|
| 通配（`task:*` / `*`） | `40024` | 「关掉 `task:*`」没有唯一解释：是现在这几个动作，还是连以后新加的？ |
| `identity:*` | `40025` | 不可逆：管理员把自己 `identity:user:permission:manage` 关掉就再也打不开这一页 |
| 目录里没有的码 | `40022` | 拼错，或模块已下线 |
| 全量账号（超管或持有 `*`） | `40928` | 求值在 `*` 处短路，例外不会生效 —— 不能让「点了没反应」的开关存在 |

## 写入口的一个细节

写例外时，**同码的允许项一起清掉**。库里同时留着「允许」和「否决」是两种表示，
迟早有一处只认其中一种（本仓踩过三次）。清掉之后语义也干净：
**恢复 = 删掉否决**，不需要记住原来给过什么。

反过来说，**来源只有个人时不需要写否决**：那一条本来就是「只给他一个人的」，
直接删允许项即可（界面上那个动作叫「移除」）。

## 界面

「用户与权限 → 某人 → 权限」这一页按**页面分组、一行一个权限码**，
每行右边是来源与一个动作。动作由来源决定，不靠人判断：

| 行的来源 | 动作 |
|---|---|
| 只有个人 | 移除 |
| 含团队 / 小组 / 角色 | 仅对此人关闭 |
| 已否决 | 恢复 |

这样「他为什么能删任务」在那一行上就答完了（来源 chip），
「只想撤他一个」也在同一行上（不碰共享单元）。

选择器（角色 / 小组 / 个人权限弹窗）**不显示否决**：例外不属于「授予」，
混进勾选框就是两处表达同一件事。但个人权限弹窗顶部会说明「已关闭 N 项」并
指向总览 —— 否则那就是一个隐藏状态。

## 守卫

| 用例 | 判别力要求 |
|---|---|
| 角色给 + 本人否决 → 403，同角色其他人 200 | 去掉减法必红 |
| 被否决 `identity:role:write` 的人不能授出它 | 去掉 `_actor_codes` 的减法必红 |
| 改允许项后例外仍在 | 去掉 `set_grants` 的 `effect` 条件必红 |
| 否决 `page:x` → 落 `deniedOff` 而非 `gatedOff` | 换归类必红 |
| 通配 / `identity:*` / 全量账号 → 400 / 400 / 409 | 去掉校验必红 |
| 扫库：不存在 deny 落在非个人层 | — |
| `effective ∩ denied = ∅`、`effective ⊆ expanded` | — |

## 明确不做

- 不做小组嵌套 / 部门层级（组织规模到不了，且它不产生减法）
- 不做多层 deny / 优先级表（复杂度随层数平方增长）
- 不做角色继承角色
- 前端永不本地重算权限（`can()` 只读后端下发的 `effective`）
