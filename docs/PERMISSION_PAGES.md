# 页面权限与接口权限（两层模型）

> 起因：在此之前「能不能看见某一页」和「能不能调某个接口」是**同一个权限码**。
> 于是两件本该独立的事被绑死——想让某人「能查任务、但先别进任务中心」做不到；
> 想下线一个页面，只能删前端路由，而后端接口照旧全开。
>
> 现在分成两层：**页面权限**（`page:*`）管可见性，**接口权限**（`资源:动作`）
> 管能力，页面声明它依赖哪些接口；关掉页面，这些接口自动失效。

## 1. 两层各管什么

| 层 | 码 | 判据在哪 | 失败表现 |
|---|---|---|---|
| 页面 | `page:task-center` | 前端路由守卫 / 侧栏过滤（`RequirePermission` / `nav`） | 菜单不出现，直接输 URL 显示「没有访问权限」 |
| 接口 | `task:read`、`task:delete` | 后端 `require(...)`（每个路由） | 403，`message` 里写着缺哪个码 |

两层都是**普通权限点**，走同一套授权（角色 / 小组 / 个人 / 团队），在同一个
「角色与权限」界面里勾选。页面权限点在目录里归到 `页面` 分组，描述里写着它
关联的接口码 —— 管理员不必翻代码就能知道「关掉这一页会连带关掉什么」。

## 2. 门控规则（只有一条）

> **某个接口权限，只有在「至少一个声明它的页面被授予」时才有效。**
> 不被任何页面声明的接口，不参与门控。

由此推出的三个行为，都是刻意的：

| 场景 | 结果 | 为什么 |
|---|---|---|
| 只授 `task:read`，不给 `page:task-center` | `GET /tasks` → 403 | 页面关了，接口跟着关 —— 这就是这个功能本身 |
| `catalog:read` 被「生成工作台」和「生图」同时声明，只开了其中一页 | `GET /models` 仍然 200 | 共享接口不能被某一页连坐，否则报错会出现在一个看起来无关的接口上 |
| `export:read` 没有任何页面声明 | 照常可用 | 门控是「页面 → 接口」的从属关系，不是全站总开关 |
| 持有 `task:*`，不给 `page:task-center` | `GET /tasks` → 403（`缺少权限: task:read`） | 通配不是门控的逃逸口：它先摊成具体码再判 |
| 持有 `task:read`，但本人例外关掉了它 | `GET /tasks` → 403，且 `deniedOff` 里能看到 | 例外是并集之上的第二道减法，只对个人生效（见 EXCEPTIONS.md） |

另外两条边界：

- **超管旁路**：`*` 在门控之前就短路，所有页面与接口都放行。新页面还没配给
  任何角色时，超管必须进得去把它配好。
- **通配**：`page:*` 等价于所有页面都开；`task:*` 等价于持有该资源所有动作。
- **通配要先摊开，再过门控**（2026-11-20 修）。门控是按**具体码**反查页面的
  （`pages_for("task:read")`），而 `task:*` 自己反查不到任何页面 —— 原来它因此
  被当成「没有页面声明的基础设施码」原样放行，于是「关掉任务中心」对持有
  `task:*` 的账号完全无效（内置「内容编辑」就写着 `task:*` / `image:*`，
  所以这不是理论问题）。现在 `resolve_identity()` 先 `expand_grants()` 再
  `gate()`：生效集合里是具体码，`gatedOff` 也精确到具体码。
  `page:*` 与 `*` 不摊开 —— 前者本来就由 `permission_holds` 判，后者门控前已短路。

  连带的界面口径：**「后端认不认」和「目录里渲染不渲染」是两件事**。
  `task:*` 不在目录里（目录只有具体码）但后端接受，所以权限弹窗初始化时
  不能按「目录里有」过滤已选码 —— 那会在下一次保存时把它静默撤掉。
  判据用 `isResolvablePermission`（`*` / `资源:*` / 目录内的码）。

## 3. 为什么门控在服务端

前端路由守卫只能挡住「在界面上点进来」，挡不住「拿着令牌直接打接口」。
所以门控落在 `core.authz.evaluate()`（`IdentityService.resolve_identity()` 调它）：
权限并集与个人例外算完之后过一遍
`page_catalog.gate()`，**令牌、`/identity/me`、`effective-permissions`、
每个 `require()` 看到的都是同一份结果**。前端拿到的 `permissions` 里已经
包含页面码，菜单与路由据此工作，不需要再算一遍。

## 4. 页面在哪声明

后端模块的 `ModuleSpec.pages`（`core/pages.py::PageSpec`）—— 不是只写在前端
路由表里：门控要由服务端判定，而且页面权限得进权限目录才有人能勾。
`PageSpec` 只回答两件事：我是谁、我在哪条路由。

```python
# modules/task/__init__.py
pages=(
    PageSpec(code="page:task-center", name="任务中心", route="/tasks"),
),
```

### 「这一页管哪些接口」写在**接口**上

归属关系写在 `PermissionSpec.pages`，不写在页面上：

```python
# modules/task/permissions.py
PermissionSpec(PERM_READ, "查看任务", group="内容生产", pages=("page:task-center",)),

# 共享接口：两个页面码，任一页被授予它就有效
PermissionSpec("catalog:read", "查看模型目录", group="内容生产",
               pages=("page:image", "page:studio")),
```

方向为什么是「接口写页面」：新增接口的人正在写那个 `PermissionSpec`，顺手就把
归属写了；反过来（页面列 `requires`）要求他记得回到另一个文件、另一段元组里补
一条，漏了只能靠守卫事后抓。共享接口也因此只写一处 —— 它是接口的属性，不是
某一份页面清单里的一条。跨模块引用页面码是正常的（`task:create` 归「生成工作台」，
那个页面声明在 catalog 模块）。

前端契约没变：`GET /identity/permissions` 里页面项的 `requires` 由
`PageCatalog.requires_of()` 反推（顺序按码排序），界面照旧按它画「页面 → 接口」。

### 新增一页要改两处

1. 后端 `ModuleSpec.pages` 加 `PageSpec`（只写 code/name/route）；
2. 前端 `modules/<id>/module.ts` 的 `permissions: ['page:<slug>']`；
3. 跑 `cd api && app export-openapi`（新页面码写进前端生成物）与
   `cd studio && npm run gen:routes`（路由清单）。

漏第 1 步：前端路由守卫会因为「目录里没有这个码」而**永远拦住**（`router.test`
有守卫）。漏第 2 步：页面能进，但接口被门控关掉。

### 新增一个接口要改**一处**

在它的 `PermissionSpec` 上写 `pages=(...)`。写错页面 slug 会在**启动期**报错
（`PageCatalog.bind()` 校验页面码存在）—— 不然那条接口要么永远不生效、要么
永远生效，两种都要等用户点了才发现。

漏写的两种情况都有守卫盯着：

- 后端 `tests/test_permission_coverage.py`：「有判定点、却既没 `pages`、
  也没列入后台能力豁免表」的码 → 报错。豁免表 `BACKGROUND_ONLY_PERMISSIONS`
  是**显式声明**的：确实没有前端页面的接口（如 `export:*`、CLI 用的统一生成
  接口）写进去并说明理由。
- 前端 `src/app/router.test.ts`：「每个页面码都要有关联接口」——没有任何接口的
  `pages` 指向它的页面码，等于一个装饰开关。

**给已有页面补一个新接口码时**（比如某模块这版才把 `model_driver:read` 关联到
「任务中心」页），除了写法改到接口那一侧，还要知道：老库里持有那个码的授权会
突然失效。增量迁移会补上（见 §7），但**补的是「一个可用页面都没有」的码**——
已有可用页面的授权不动，因为那个页面是管理员自己配的，不该被覆盖。

## 6. 团队层为什么不能放页面码

团队层的语义是「所有启用账号」，而且这一层**没有 deny**（例外只存在于个人层，
见 [EXCEPTIONS.md](./EXCEPTIONS.md)）。把 `page:*` 放进团队层，
等于「这一页对任何人在任何情况下都关不掉」——直接废掉页面权限本身。
所以 `TEAM_FORBIDDEN_PREFIXES = ("identity:", "page:")`，写接口直接 400。

页面只能挂在可以按人调整的层上：角色 / 小组 / 个人。

## 7. 迁移与兼容

- **内置角色**（editor / viewer / asset_specialist）的模板里已经带了页面码。
  老库在启动时由 `sync_new_permissions()` 把「这一版新增的权限点」补进这些角色，
  所以升级后不需要手工配置。
- **自定义角色 / 小组授权 / 个人授权**：升级时由 `migrate_roles_to_pages()`
  补齐——按「这些接口码属于哪些页面」把页面码加上去，等价于保持升级前的可用性。
  迁移之后仍然可以按需调整：把页面码从角色里去掉，那一页就随之关闭。
- **迁移是增量的，不是「一次性」**：判据不是「这个库迁移过没有」，而是
  「**哪些接口码是这一版才开始受门控的**」——拿当前的「接口码 → 声明它的页面」
  映射与上一版存档的映射（`app_meta` 的 `permissions.pages_migrated`，存的是映射本身）
  求差，只对新增的那些码补齐。
  为什么要这样：一次性迁移有个漏洞，**这一版新声明的页面关系不会被补到**。
  比如某模块这一版才把 `model_driver:read` 关联到「任务中心」页，
  老库里持有这个码的角色就会突然失效——升级前能用、升级后 403，
  而配置界面看上去完全正常。增量迁移堵上了这个洞。
  代价是管理员之后特意关掉的页面**不会**被重新打开：那些码不是新增的，不在差集里。
- **补齐只补「一个可用页面都没有」的码**：一个码常被多个页面声明
  （`library:read` ← 资产库 + 模板封装）。若无条件把声明它的页面全补上，
  一个只配了「资产库」的角色会顺带拿到「模板封装」——那是凭空多给一页的可见性，
  不是「保持升级前的可用性」。所以只在该码**一个声明它的页面都没有**时才补。
- **「后台能力」是显式声明的**：有些接口没有前端页面（CLI / 运维脚本用，
  如 `export:*`、统一生成接口 `model_driver:create`），它们**本来就不该**受页面门控。
  这份清单写在 `tests/test_permission_coverage.py` 的 `BACKGROUND_ONLY_PERMISSIONS`，
  每条都写明理由；后端还有一条守卫盯着「有判定点却既没页面声明、也没列入豁免表」的码——
  那就是漏声明。
- **团队层**不需要动：它本来就不含页面码（页面由角色/小组/个人负责）。
- 「只挂团队层、没有任何角色」的账号：团队层给了 `task:read` 但没有任何页面，
  接口会被门控关掉。这是刻意的——「能看见哪一页」不由团队层决定。
- **迁移之后的排障入口**：`GET /identity/users/{id}/effective-permissions` 的
  `gatedOff` 字段列出「有接口码但被门控关掉」的那些码。

## 7.5 界面上怎么看这两层

「角色与权限」里的勾选清单分两段，**页面在上、接口在下**，两层的因果画在同一屏里：

- **页面段**：每个页面一张卡片，写着它的路由与**关联接口**（哪些接口会被这一页关掉）。
  勾页面**不会**自动勾接口 —— 页面是可见性，接口是能力，自动勾会把
  「只想让人看得见这一页、不让他动」这种诉求抹掉。
- **接口段**：每个接口标明它被哪些页面管着，以及这些页面**当前开没开**：
  - 「随 任务中心 生效」= 页面开着，这个接口现在算数；
  - 「页面未开启时不生效（任务中心）」= 勾了也白勾，**在勾之前就能看见**；
  - 「不受页面开关影响」= 没有页面声明它（基础设施接口），一直可用。
- **摘要条**分开报「页面 N 个 / 接口 N 个」，免得把两种东西当成一种。

「有效权限」详情里也多了两段：**页面**（能看见哪几页）与
**被页面门控关掉的接口**（有接口码但页面没开 → 现在不生效）。
后者专门用来回答那句「权限列表里明明有 `task:read`，接口却 403」。

## 8. 排障：403 但权限看起来是对的

`GET /identity/users/{id}/effective-permissions` 现在多两个字段：

```jsonc
{
  "pages": ["page:task-center"],          // 能进哪几页
  "gatedOff": ["catalog:read"],           // 有接口码、但所属页面一页都没给 → 失效
  "effective": ["task:read", "..."]       // require() 唯一判据
}
```

看到 `gatedOff` 里有某个码，就是「页面没开」而不是「权限没授」。

## 9. 不该做的事

- **不要在前端路由上写接口码**：那样等于回到两层合一，门控会把这个页面的接口
  全关掉，而菜单又显示不出来——一个页面直接消失。
- **不要把 `page:` 码写进 `require(...)`**：页面码回答的是「能不能看见」，
  不是「能不能调用」；用它守接口会让「关掉页面」和「停用接口」两件事再次纠缠。
- **`pages` 里只写真实存在的页面码**：写 `page:*` 或拼错 slug 会在启动期报错
  （`PageCatalog.bind()`）。想「让所有页面都管这条接口」本身就不用表达 ——
  门控是「任一页被授予就有效」，写两个具体页面码就够了。
- **不要用「目录里有没有」判断某个权限码能不能提交**：`task:*` 这类通配不在目录里，
  但后端接受。判据是 `isResolvablePermission`（见 §2 末尾那段）。
