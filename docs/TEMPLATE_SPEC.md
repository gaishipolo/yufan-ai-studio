# 模板规格（Template Spec）

> 状态：**设计定稿，待实施**（2026-11-14）。
> **封装（`kind=pack`）的现状（2026-11-19）**：资产库的封装能力**已重新上线**，
> 但它**不是槽位类型** —— `SLOT_TYPES` 仍然只有 `image / video / audio / text`。
> 封装在模板库里的身份是「一种特殊的素材」：和素材并列在同一个网格里，点它按标签
> 一次填满多个槽位（见 §10.5）。
> 本文中凡出现 `type=pack` / `pack_id` 的段落，都是 2026-11-16 之前的**历史设计**，
> 已在下面逐处标注作废。
> 目标读者：改模板封装 / 模板库 / 生成链的人。
> 与 `TEMPLATE_LIBRARY_V2.md` 无关（那份是任务中心 v2 的旧计划，用户明确「先不用管」）。

## 1. 这份文档解决什么

现有的「封装 → 模板」只服务一种形态：**一支原片 + 一组图片做替换**。它把三件事写死在了结构里：

| 约束 | 现在的落点 | 后果 |
|---|---|---|
| 必须有且只有一支原片 | `ManifestDraftIn.video` 必填单值；`video_templates.source_video_asset_id` | 「只有提示词」「多图无视频」表达不出来 |
| 参考槽位只有图片，用途来自固定词表 | `packs[].references` + `PACK_ROLES`（product/character/scene 三套） | 音频、第二支视频、文本参考进不了槽位 |
| 封装自己存了一份素材清单 | `template_pack_references`（发布时把 asset id 复制一份） | 第二事实来源；封装侧自己物化素材 |

同时框架里**已经有**通用能力，只是没被用上：

- `modules/model_driver/generic_inputs.py`：按 `kind` 收窄后缀、probe 时长、写 `references/bindings`，支持 `image / video / audio`；
- `modules/task/service.py`：文本参考走 `freeze_text_refs` 冻结；
- `CreateTaskIn`：`prompt + model + referenceLibraryIds + textLibraryIds + durationSec/aspectRatio`，已经是通用形态；
- `ModelSpec.param_schema`：参数区由模型声明驱动，前端不用为每个模型写表单；
- 资产库：`video / audio / image / text` 四类（`pack` 已随素材封装下线），`core/ports/library_lookup` 是唯一读取入口。

所以结论不是「给封装加字段」，而是**把模板降级为「表单元数据」，把执行让给 task**。

### 1.1 决策判据（先定判据，再选方案）

这份文档的取舍只依据下面五条框架原则，**不依据改动量或实现难度**：

| 原则 | 判据（违反即否决） |
|---|---|
| 数据归属唯一 | 每类数据只有一处权威源：素材与素材结构 → 资产库；模板声明 → spec；执行记录 → task。**不得为过渡复制第二份** |
| 能力只实现一次 | 取字节、查元数据、编译编号、校验 —— 各自只有一处实现，谁的第二处都不许长 |
| 派生结果不进数据 | 编号、展开顺序、可读性判定都是算出来的，不落库 |
| 模块不互相 import | 跨模块只经 `core/ports` 或纯 JSON 契约 |
| 发布即冻结 | 已发布内容不可改写；改模板 = 新版本 |

按这五条回看，先前两条结论**被否决**：

- ~~「槽位指向资产库封装本期不做，因为要扩资产库模型」~~ —— 拿成本否决了"数据归属唯一"；
  而且事实也错：资产库封装的成员表本来就有 `position` / `role` / `description`，成员允许
  `image / video / audio / text`（只禁嵌套 pack），`LibraryLookup.expand_packs()` 已经能按
  `position` 有序返回带 `role` 与 `readable` 的成员，其 docstring 明确写着"顺序即槽位，
  调用方不得重排"。**所以它进 P1，不是"预留"。**
- ~~「P2 期间由 spec 发布时投影回 `video_templates`，让替换链继续消费」~~ —— 让新写的
  spec 去喂旧表，等于把第二事实来源制度化。**改为：P1 起替换链的 runtime 端口直接读 spec，
  `video_templates` 只作为历史数据只读保留。**

## 2. 目标 / 非目标

**目标**

1. 同一套结构支持四种组合：纯提示词、提示词+多图、提示词+图片+视频、再加音频/文本参考。
2. 封装模块只管「定表」：槽位声明、提示词、模型与参数默认值。**不取字节、不查素材元数据、不物化**。
3. 模板库只管「填表」：把槽位填满并提交。不复制校验规则。
4. task 不知道「模板」存在。
5. 素材取用只剩两处：`core/ports/library_lookup`（元数据/可读性）与 task 的 `generic_inputs.materialize`（字节落地）。
6. **终态统一**（2026-11-14 用户拍板「统一」）：替换不再是平行链路，而是 task 的一个 capability；
   不留独立替换工作台，成片复核并入任务中心。**注意是删掉重复的编排，不是把封装并进 task** ——
   P3 之后项目里只有两个概念：模板（封装模块）与任务（task）。见 §11.1。
7. **素材结构不由模板复制**：一组"同一对象的多个视图"归资产库封装（`kind=pack`），
   模板只引用它的 id，成员与角色由库给（`LibraryLookup.expand_packs()`）。

**非目标（本期不做）**

- 模板市场 / 跨工作台共享 / 版本回滚 UI；
- 在 spec 里复制封装成员（见 §12 不变量 9）。

## 3. 三层职责

```
封装（编写侧，modules/template_pack）        模板库（消费侧，前端 + 只读接口）        task（执行）
┌─────────────────────────────┐  发布   ┌──────────────────────────┐   compile   ┌──────────────┐
│ TemplateSpec                │ ──────▶ │ 卡片 = 已发布版本快照      │ ─────────▶ │ /tasks       │
│  slots[]（槽位声明）         │  冻结   │ 渲染槽位表单（fixed 只读） │  填表结果    │ 只认 prompt + │
│  prompt（整段）             │         │ 提交前调 compile 拿请求体  │             │ references +  │
│  model + params             │         └──────────────────────────┘             │ params        │
└─────────────────────────────┘                                                  └──────────────┘
```

三条边界是硬的：

- 封装 **不 import** `modules/task`（`test_modules_do_not_import_each_other`）；
- 模板库 **不拼编译结果**：`{{slot:x}} → {{Mixed N}}` 的展开只在服务端一处（§6）；
- task **不读** spec 表，入参与模板无关。

## 4. 核心词汇

### 4.1 InputSlot（槽位）

| 字段 | 类型 | 说明 |
|---|---|---|
| `key` | `^[a-z][a-z0-9_]{0,39}$` | 槽位标识，提示词里用它引用；版本内唯一 |
| `type` | `image \| video \| audio \| text` | **就是资产库的 kind**：决定提哪种素材选择器、以及能进哪个字段（`pack` 已随素材封装下线） |
| `binding` | `fixed \| user` | `fixed`：封装时定死，模板库只读；`user`：模板库填 |
| `ref_mode` | `mixed \| attachment` | `mixed` 参与 `{{Mixed N}}` 编号；`attachment` 作为附加输入、不占号（音频通常用这个） |
| `min` / `max` | int | **一槽一张，已锁死**：`min` 只有 0（可选）/ 1（必填），`max` 恒为 1（迁移 `4e06879f9f75` 清掉历史多值数据，契约 `le=1`） |
| `label` | str(1..40) | 槽位名的展示文案（"产品主图"/"背景音乐"） |
| `usage` | — | **已删**（迁移 `d7f2a91c48b3`）。它从来没有进过提示词（编译器完全不看它），只在前端显示一行字 —— 作者填了会以为那句话管用，而模型根本看不到。说了等于没说，还让人以为说了 |
| `filled_text` | str(0..2000) | **选中时文案**：使用者在模板库填了素材时，提示词里 `{{slot:key}}` 这一处替换成什么。空 = 直接插编号（旧行为）。**只对可选槽位（`min=0`）有意义** —— 必填 = 素材一定在 = 直接插编号，带了会被 400 拒。可含对**自己**的引用（`{{slot:key}}` / `{{slot:key*}}` / `{{slot:key.N}}`）；也可引用**必定有素材**的槽位（必填 / 已固定）—— 可选槽位不得引用 |
| `empty_text` | str(0..2000) | **未选时文案**：`min=0` 的槽位没填素材时，提示词里这一处替换成什么。空 = 编译时报错。可引用**必定有素材**的槽位（必填 / 已固定），但**不得引用它自己**。同样**只对可选槽位有意义** |
| `asset_id` | str \| null | 非封装槽位且 `binding=fixed` 时必填；其余为空 |
| `tag_ids` | list[str] | **候选集范围**：一组标签 id（**任意级别**：分组 / 系列 / 具体词），空 = 不限。固定与填写都只在这几个标签（各自含下级）里挑；多个标签之间是并集；编译不看它 |
| `position` | int | 排序，**就是编号顺序**，见 §6 |

> 素材封装（`kind=pack`）下线后，槽位表里的 `pack_id` 与 `type=pack` 相关约束已从契约里删除（
> 后端 `SpecSlotIn` 里没有这些字段，迁移 `c3d8e1f04a7b` 也删了 `template_spec_slots.pack_id`。
> 本文其余段落里提到封装的地方是历史设计记录，不是现行契约。

约束：

- **槽位数量 0 ~ `MAX_SLOTS`**：下不封底。没有槽位 = 纯提示词模板（去 §6 看它怎么编译），
  封装页也允许把槽位删到 0 —— "至少一个槽位"是曾经写死在页面上的假约束，服务端从来没有；
- **提示词里的引用必须指向存在的槽位**：`{{slot:gone}}` 在结构校验（预检 / 保存 / 发布）就 400，
  不拖到 `compile`。槽位能删到 0，这条判据因此比过去更有用；封装页删槽位时会顺手把
  它的引用清掉并告知清了几处（不静默改用户的文字，但也不留一条必然失败的引用）；
- `type=text` 不许 `ref_mode=mixed`（文本不占视觉编号）；
- `type=audio` 只允许 `ref_mode=attachment`；
- 版本内 `position` 连续唯一；`key` 唯一；
> **以下两条已作废（2026-11-19）**：`type=pack` 不再是合法槽位类型，校验收在
> `PICK_MODES` 之外 —— 现在只有 `pick_mode`（`asset`/`pack`，默认 `asset`）这一层
> 历史字段，且模板库不使用它（封装走 §10.5 的网格）。保留原文只为说明当时的取舍。
>
> ~~- `type=pack` 时 `min/max` 不参与（数量 = 成员数，恒为 1/1），且 `ref_mode` 必须是 `mixed`~~
> ~~- 非封装槽位且 `binding=fixed` 只能表达**一个**资产；需要固定多张时，要么用 `type=pack` 指向一个资产库封装~~
>
> 现行规则：槽位仍然是**一槽一张**（`min 0/1`、`max 1`），固定槽位只能表达一个资产；
> 需要「一次选好几张不同视角」时，把这几格放进同一个封装容器（§10.5），
> 使用者选一次包、它们一起填好。

**「要什么」只有一根轴**（2026-11-14 合并，见 §11.4）：曾经 `type`（image/video/…）与
`source`（asset/pack）并列，两根轴表达同一件事时接口能收到 `type=image, source=pack` 这种
自相矛盾的组合。

> **2026-11-19 修订**：`source` 轴没有回来，`type=pack` 也没有回来。封装重新上线后走的是
> **填表侧的素材粒度**（§10.5）—— 槽位仍然只声明「要图片还是视频」和「圈哪些标签」，
> 「这一格从包里取」是使用者填表时的动作，不是模板的结构。这样编译层一行都不用改。

### 4.3 allowedModels（使用模板时允许选用的模型清单）

| 字段 | 类型 | 说明 |
|---|---|---|
| `allowed_models` | list[str] | 使用模板时**允许选用的模型清单**。空 = 只有 `model` 那一个（老模板的行为） |

**为什么需要它**：模板原本只有一个写死的 `model`。但作者比使用者更清楚这份模板
适用于哪几款模型 —— 同一段提示词在视频模型 A 与 B 上表现差别很大，而使用者恰恰
是知道自己在哪个渠道发布的人。写死一个模型等于替使用者做了决定。

**口径（前后端同一份）**：

- 清单里的模型 id 必须**存在于模型目录**（发布 / 预检时校验，与「发布时该模型必须
  在目录里存在」同一道闸，`spec_service._check_model`）。清单是给使用者看的选项，
  里面出现一个不存在的模型，使用者挑到它才 400 —— 那时素材都填完了；
- 清单里的**每一款**都要能承接作者写的参数与参考素材（挑到哪一款都不该被拒）：
  参数键必须落在该模型的 `param_schema` 内；参与编号的槽位按「固定槽位 1 张 +
  用户槽位的 `max_count`」算上限，**与 `model.max_references` 直接比**。
  只判 `max_references == 0` 是不够的：「最多接 4 张」的模型配了 5 个槽位照样
  发布成功，使用者填满才在提交时被 400 打回 —— 那时作者已经把模板发出去了；
- **可选项 = 固定模型 ∪ 清单**（去重、保序，固定模型在前）。固定模型永远可用 ——
  它是模板自己的模型，作者没把它写进清单也不该让使用者无路可走；
- 清单**随发布快照走**（`template_spec_versions.allowed_models`），使用者读的是版本，
  不是草稿：草稿改了清单没发版，使用者看到的仍是旧清单；
- 清单为空 = 只有固定模型。**老模板一条都不改**（存量行为不变）。

**使用侧**：模板库填表页在清单非空时给一个「只含这几款模型」的下拉；选中的那款
跟着 `compile` 的 `model` 参数走（不在清单里 → 当场 400，不静默换成固定模型）。

## 5. 提示词只有一段

`prompt` 是**一段字符串**（2026-11-14 合并，见 `c9a1f4e27b53`）。原来的
`locked`（封装写死）/ `editable`（模板库可改）两段，存在理由只有一个：
"模板库允许改那一半"。用户拍板取消这个入口之后，两段就没有区别了。

**要可变内容，用 `text` 槽位**：模板里声明 `type=text` 的槽位（填表时选一份文案），
编译时按槽位顺序拆成 `{{Text N}}`，执行层再按 `textLibraryIds` 把正文注入。
模板库因此**不改任何文字**，只选素材 —— 这也让"模板改一个字就换版本"的问题消失。

字数上限沿用 `MAX_PROMPT = 20000`（编写）、`EXECUTION_PROMPT_LIMIT = 7000`（执行，
按展开后的成品判）。

## 6. 编号与编译规则（唯一一处）

**作者写的引用就是 `{{Mixed N}}`**（2026-11-19 统一）：`N` = 第几个**图片/成片**
槽位（按槽位顺序数，文本/音频不占号）。以前作者写内部 key `{{slot:image_1}}`、
模型看到 `{{Mixed 1}}`，同一件事两套写法，作者还得去记 key。

**`N` 是槽位序号，不是最终编号**。编译时按「槽位顺序 + 实际填了几张」现算：
第 1 个槽位填了 2 张，它占 1、2 两个号，第 2 个槽位就是 3 号。所以作者写的
`{{Mixed 2}}` 可能展开成 `{{Mixed 3}}`。写死最终编号才会错位 —— 这正是
「按序号引用」和「按编号引用」的区别。

引用语法（三个形态，与槽位 `*` / `.N` 一致）：

| 写法 | 含义 |
|---|---|
| `{{Mixed 2}}` | 第 2 个图片/成片槽位那一段（可选槽位走「选中时 / 未选时文案」） |
| `{{Mixed 2*}}` | 该槽位**全部**编号，按填充顺序用「、」连接 |
| `{{Mixed 2.3}}` | 该槽位第 3 张（越界即 400） |

**文本槽位仍用 `{{slot:key}}`**：它有独立的 `{{Text N}}` 编号空间，不参与 Mixed 计数。
`{{Text N}}` 与 `{{Mixed N}}` 不同：前者仍是派生编号，手写会被 400 拒。

**固定文本在发布时内联**：`binding=fixed` 的文本槽位，发布时按 `{{slot:key}}`
读正文写进 `prompt` / `randomPrompt`，并从发布快照里摘掉这条槽位。文本是唯一能
这么做的素材（字符串可以直接抄），所以**不要求这条素材全员可读**；图 / 视频仍走
「随模板公开」那道闸。草稿阶段保留槽位与引用，老版本不受影响。正文后来被编辑时
草稿指纹没变，发布靠比对内联后的 prompt 决定是否出新版本。

**换算只在一处**：后端 `rules.normalize_refs` 在入口（`validate_spec` /
`compile_spec` / `_check_executable`）把 `{{Mixed N}}` 换成 `{{slot:key}}`，
后面的逻辑只认一种写法。前端同理：`specDraft.toSlotTokens` / `toMixedTokens`
是唯一的换算对，解析函数都先换再解析。

**结构一变就重编号**：增删槽位、拖动排序、把图片改成文本，都会让后面所有序号平移。
`specDraft.renumberRefs` 的做法是「先用旧槽位换回 key → 再用新槽位换回序号」，
不做任何「猜它原来指谁」的推断。

展开算法（`compile()`，纯函数、不写库）：

1. 解析填充：
   - 非封装槽位：`fixed` 取 spec 里的 `asset_id`；`user` 取入参 `slotValues[key]`（资产 id 列表），数量必须落在 `[min, max]`；
   - `type=pack`：取 spec 的 `pack_id`（fixed）或入参（user）里的封装 id，调
     `LibraryLookup.expand_packs()` 展开成员 —— **顺序由库给，编译不得重排**；成员必须同类型、
     全部 `readable`（有不可读成员就报"封装《X》的成员 Y 无权访问"，不静默少一张）；
   - 单资产的可读性与存在性一律经 `library_lookup`，不直查表。
2. 按 `position` 升序累加计数，得到 `slot_key → [token…]`：
   - `mixed` 槽位用 `{{Mixed N}}`（视觉编号）；
   - `text` 槽位用**自己的** `{{Text N}}`（N = 文本素材的序号，与 `text_library_ids` 的顺序逐一对应）；
   - `audio` 槽位没有编号空间，跳过。
3. 把 `{{slot:…}}` 替换成对应 token。`audio` 槽位被引用 → 400；`text` 槽位可以引用
   （它就是"提示词里可变的那一处"）。
   `type=pack` 的槽位，其成员的 `role` 作为该 token 的角色写进执行请求（`expand_packs` 已带出）。
4. 校验总量：`mixed` 展开后总数 ≤ `min(10, 模型 max_references)`；音频/文本数量按模型声明另判（§13 开放问题）。
5. 产出执行请求：

```jsonc
{
  "model": "libtv-wan3-replacement",
  "prompt": "<整段提示词，token 已展开>",
  "params": { "aspectRatio": "9:16", "durationSec": 6 },
  "referenceLibraryIds": ["0a2062…", "454955…", "5987f1…"],   // mixed 按编号序 + attachment 追加在后
  "textLibraryIds": ["…"],                                      // text 槽位
  "slotTokens": { "source": ["{{Mixed 1}}"], "hero": ["{{Mixed 2}}"], "detail": ["{{Mixed 3}}"],
                  "brief": ["{{Text 1}}"] }
}
```

`slotTokens` 只回给前端做展示（角标编号），不参与提交。

### 6.1 可选槽位：`min=0` 时提示词里那一段怎么说

`min=0` 的槽位（`binding=user`）**不填素材也能编译**。没填时，提示词里
`{{Mixed N}}`（文本槽位是 `{{slot:key}}`）那一处替换成什么，由槽位自己声明：

| 引用写法 | 填了素材 | 没填素材 |
|---|---|---|
| `{{Mixed N}}` | 插 `filled_text`；`filled_text` 为空则插编号（旧行为） | 插 `empty_text`；`empty_text` 为空则**报错** |

**只有这一种写法**（2026-11-27）：一槽一素材（契约里 `max_count` 恒为 1），
「整组」（`{{Mixed N*}}`）与「第 N 张」（`{{Mixed N.M}}`）都不存在了 ——
结构校验直接拒（`rules.py::_validate_ref_modifier`），判据落在**引用 token 的
修饰符**上，不是「正文里出现 `*` 或 `.N`」（正文里「价格 * 3」「2.5 倍」是正常文字，
不能误伤）。这两种写法曾经留着的坏处：整组引用会**绕过 `filled_text`**，
「第 N 张」在没填素材时必然报错。

**必填槽位（`min>=1`）只有「填了素材」这一种情况**：它的素材一定在（不填在编译期
就报错），所以单张引用**直接插编号** —— `filled_text` / `empty_text` 对它没有意义，
结构校验直接拒（`rules._validate_slot_texts`，400 并说清「改成可选」）。

> **必填 = 素材一定在 = 直接插编号。** 两段文案（「填了怎么说 / 没填怎么说」）是
> **可选槽位**才有的两种状态。给必填槽位加自定义措辞，等于多出一条
> 「哪些槽位能写文案」的记忆负担，还跟界面上说的规则对不上。

#### 槽位文案里能引用谁（2026-11-26 改）

两段文案（`filled_text` / `empty_text`）里可以写 `{{slot:key}}`。能引用哪些槽位，
作者侧、使用者改写、前端守卫**同一套判据**：

> **能引用 = 那个槽位必定有素材**：必填（`min_count >= 1`）或已固定（`binding == "fixed"`），
> 且参与编号（`ref_mode == "mixed"`）。可选槽位仍禁止。

判据只写一处：后端 `core/template_spec/rules.py::is_always_filled`，前端
`studio/src/features/template-specs/specDraft.ts::isAlwaysFilled`（两边注释互相指认）。

| 引用谁 | `filled_text` | `empty_text` |
|---|---|---|
| 自己 | 允许（推荐写法） | **禁止** |
| 必定有素材的槽位（必填 / 已固定） | 允许 | 允许 |
| 可选槽位 | 禁止 | 禁止 |

两条不对称的理由：

- **`filled_text` 允许引用自己**：那一支有素材、编号存在；「人物参考 {{slot:hero}}」
  里的编号就靠自引用派生成。
- **`empty_text` 禁止引用自己**：那一支恰恰没有素材 —— 它用的正是「使用者没给
  这一格挑素材」的时候。

引用**别的**槽位时，展开结果取决于那个槽位排在前面还是后面（编号按槽位顺序算）。
所以只放开**必定有素材**的那一类：那种槽位的编号永远存在，展开稳定。

> **为什么以前误伤**：老规则是「见引用就拒」，理由写成「没填素材就没有编号可指」。
> 那句话只对**这一格自己**成立 —— 文字里提的**别的**槽位若是必填 / 已固定，
> 它的编号一直存在。于是「这段话里提一下必填槽位的素材」这种合法写法被一起禁掉了，
> 这正是模板封装者反馈的场景。

槽位文案里的引用**展开成编号**（`compile.py::_expand_slot_text`），不展开成对方的
文案段 —— 展开成文案会递归（对方文案里再引用别人）。

界面同理：默认描述段里的引用**也画成胶囊**（胶囊的底色与边框 + 段的下划线，
两个特征同时在），不再画成裸的 `{{Mixed 1}}` —— 它确实是引用，画成裸文本
既难看，又让人以为那不是引用。

三条设计约束：

- **不另设 `required` 字段**。`min=0` 就是「可选」——两个事实源不同步时，界面显示「必填」
  而编译器放行（或反过来），这种错只在生成结果里显形。
- **`{{Mixed N}}` 是唯一插入点**。「有素材时这么说 / 没素材时那么说」是同一个槽位的两种
  说法，写进提示词正文就要让作者把同一段话维护两遍（正文一遍、槽位一遍），两处措辞
  一漂移编译时就对不上。替代方案（「正文里正则匹配整段再替换」）不可取：段落边界靠猜，
  猜错的后果是提示词缺一整块，且匹配失败时的行为没人说得清。
- **发布闸门**：可选槽位被**单张引用**时必须有 `empty_text`。整组引用不要求（没填时
  降级为空，既有语义），第 N 张引用不要求（没填时必然报错，与文案无关）。闸门放在**发布**
  而不是保存 —— 草稿能存（作者还没想清楚也能存），发布出去之前必须写好：发布意味着
  「别人会拿去用」，别人不该替作者填这个坑。

#### 可选槽位的插入点只能来自框选段（2026-11-27）

可选槽位在正文里的那个**单个引用**就是它的**插入点**：填了素材插编号，没填插
`empty_text`。而 `empty_text` 按设计是**作者在正文里框选出来的那一段**（提交时
那段正文让位成插入点，文字挪进 `empty_text`）。于是：

- 正文里**单个引用**某个可选槽位的地方**最多一处**（被引用了就只能有一处），且
  那一处就是框选段；
- 可选槽位的 `empty_text` 必须**来自框选段** —— 记在 `empty_text_from_anchor` 上。

**两段提示词各算各的**：随机档提示词是整段替换主提示词的另一段话，它的插入点与
主提示词里的互不相干（发布闸也是两段一起看，见 §6.1 的发布闸那条）。

多出来的那处引用（粘贴进来的「普通引用」）会让「打开草稿时该还原哪一段」变成猜：
库里两处长得一模一样，还原只能猜第一个 → **作者原话被顶掉**。

> **整组引用不在这条规则里**：它的语义是「列出这一组的编号」，不是插入点，也不碰
> 兜底文案（发布闸同样不要求整组引用写 `empty_text`）。

**老数据怎么办**：`empty_text_from_anchor` 是后加的列，老数据一律为假 → 预检红，
并把原来那句一起带进消息里（作者可以照抄回正文）→ **强制改成符合要求的**。
已发布的版本照常给使用者用（这条只在作者保存 / 预检 / 发布时判）。

判据两处同口径、注释互相指认：后端
@@core/template_spec/rules.py::validate_optional_slot_refs@@、前端
@@studio/src/features/template-specs/defaultText.ts::optionalSlotRefError@@。

**前端只提示、不拦写入**：老模板打开时，正文里那处引用（就是它的插入点）天然落在
框选段外 —— 而作者要做的恰恰是把它删掉。拦写入会让人连字都改不动；真正的闸在保存
时（后端：最多一处 + 标记来自框选段）。
**老数据怎么来的**（2026-11-27 补）：老模板的「未选时文案」是作者在老界面**手填**
的，正文里另有一处引用 —— 库里两种形态长得一模一样。把那句兜底文案「替换」到正文里
那处引用的位置、再框选它，得到的存储态与原来**逐字相同**（一处引用 + 同一句
`empty_text`），只多了「来自框选段」这一个标记。所以迁移只做一件事：
**把符合条件的行刷成 True**（脚本 `api/scripts/migrate_spec_optional_anchors.py`，
带 `--dry-run`，幂等）。

刷的行：可选槽位 + `empty_text` 非空 + 该规格提示词里指向它的**单个引用恰好一处**。
刷不到的（多于一处 / 零处 / 只有整组引用）留给预检拦，由作者自己处理。


### 6.2 封装页什么时候显示这两个框

两段文案的显示条件**只剩一条**：槽位**可选**（`min=0`）且 `binding=user`。

> **2026-11-18 改动**：之前还有一条「槽位在提示词里被**单张引用**」——
> 那是在拿**写作顺序**当门槛：作者得先跳到正文插一个 `{{slot:key}}` token，
> 再回来写「有素材 / 没素材」两段话。用户拍板去掉这条：
> **只要是可选就显示这两个输入框。**
>
> 理由：写作顺序不该由界面的门槛决定；先让人把话写下来更顺。
> 必填槽位仍然不给写（**必填 = 素材一定在 = 直接插编号**，没有「没填」这个状态）。

**没有插入点时这两段话编译期用不上**（后端只在单张引用时展开它们），
所以界面**照实说一句** —— 但这句话写在**输入框的占位提示**里，不是一行常驻小字：

- 没有插入点 → 占位提示「…提示词里写下 `{{slot:key}}` 引用这个槽位，这段话才会被用上」
- 有插入点 → 占位提示「使用者填了素材时，提示词里这一段怎么说（打 @ 插入编号）」/
  「使用者不填素材时用这段（留空则发布会被拦）」

> **2026-11-18 改动**：这条说明原来是常驻 `<p>` 小字。现在改成**框内占位符**
> —— 提示跟着框走、填了内容就自动消失、不占额外版面。两个框的占位文字**必须能
> 分开**（「使用者填了素材时…」/「使用者没填素材时…」），文字一样的话使用者
> 分不清哪个框是「有素材」、哪个是「没素材」。

**同一条事实源也要管模板库的确认框**：确认框里「XX（未填）：<兜底文案>」这一行
只在槽位**真的被单张引用**时才摆 —— 后端 `compile.py::_fallback_or_raise` 只在那种
情况下用 `empty_text`。没被引用的槽位，它的兜底文案是死数据，摆出来会让使用者
以为这段话会进提示词。

**「选中时文案」里要引用编号时打 `@` 选，不让用户手敲 `{{slot:key}}`。**
手敲有两个错且都不报错：key 拼错要到编译期才 400；槽位改名后手敲的引用**静默失效**。
候选是**算出来**的（`specDraft.selfRefChips`），且**只列这个槽位自己**的三种写法：

| 候选 | token | 展开成 | 何时出现 |
|---|---|---|---|
| 单张 | `{{slot:x}}` | 第一张的编号 | 总是 |
| 全部 | `{{slot:x*}}` | 这组的编号 | `maxCount > 1` |
| 第 N 张 | `{{slot:x.N}}` | 第 N 张的编号 | `maxCount > 1`，N 从 2 起 |

候选**除了自己**，还列**必定有素材**的槽位（必填 / 已固定）—— 那种槽位每次编译都有
编号，引用它成立（规则见 §6.1「槽位文案里能引用谁」）。可选槽位不列：它可能没人填，
那时没有编号可指。

> **2026-11-26 改动**：以前候选只列自己，后端也只认自己。后来发现「默认描述 / 未选时
> 文案里提一下别的必填槽位的素材」是合法且常见的写法，于是两边一起放开（见 §6.1）。

**正文里的 @ 候选不列可选槽位**（2026-11-26 用户拍板）：可选槽位一旦被正文引用，
就必须给它写「未选时文案」，而写它的唯一入口（框选正文）会把那段正文让位成插入点
—— 作者只想补一句兜底话，却改动了一整段正文。所以 @ 菜单不给可选槽位入口
（手敲/粘贴仍可，预检会点名要求补兜底文案）。必填 / 已固定 / 文本槽位照旧。

候选面板与提示词框共用同一个组件（`MentionTextarea`）：两处各写一遍的话，候选面板的
行为会漂移（一边能键盘选、一边不能；一边的面板会被视口切掉、另一边不会）。

**切成必填时清掉两段文案，并告知作者**（`specDraft.textsToClearForRequired` +
`SpecWorkspace.patchSlot`）。清掉而不是留着：留着的话后端会 400（必填槽位带文案直接拒），
而界面看不出是哪一条规则 —— 作者明明写了文案，点保存却被拒。切回「可选」时文案**不会**
自动回来 —— 那是作者的决定，不该由系统替他猜。


**这份出参是「模板层」结果，不是任何端点的请求体。** `POST /tasks` 把时长与画幅放在
**顶层**（`durationSec` / `aspectRatio`），不接受自由 `params`；生图端点又是另一套摆法。
摊平由提交方按目标端点做 —— 模板库页面对照生成的 `CreateTaskIn` 类型把 `params` 展开，
类型检查就是那份映射的守卫。`compile` 刻意不假设端点：否则换一个执行端点就要改编译规则，
而那属于 P3 的 capability 声明。

### 6.3 使用者改写「未选时文案」（2026-11-21）

作者的 `empty_text` 是**通用版本**（「主角是穿红裙的年轻女性」）；使用者往往知道得更具体
（「这次不要人物，只留原片」）。模板库的自定义档里，每个**可选**槽位多一排切换：

| 填法 | 界面 | 提交 |
|---|---|---|
| 选素材（默认） | 现有的素材网格 | `slotValues[key] = [assetId…]`，可以不挑 |
| 改提示词 | 一个输入框，**预填作者的 `empty_text`** | `slotTextOverrides[key] = "改后的那段话"`，这一格**不传素材** |

编译前把该槽位的 `empty_text` 换成使用者那段（`spec_service._apply_slot_text_overrides`），
编号展开仍由 `compile_spec` 一处算 —— 与「随机档整段换 `prompt`」同一个位置、同一个手法，
编译核心因此保持纯函数。

**入口只在两件事同时成立时出现**（`hasFallbackSlotRef` + 不是必填 + 没被「第 N 张」钉住）：

- 提示词里真有插入点：`{{slot:x}}` 或 `{{slot:x*}}`。`{{slot:x.2}}` 不用兜底文案；
- 这一格不是必填、也没被 `.N` 引用钉成「必须交素材」。

> 没有插入点还摆输入框，等于让人打了字也不生效 —— 与已删的 `usage` 字段同一类错。

五条 400（`_apply_slot_text_overrides`），都点明是哪一格：槽位不存在 / 必填或固定 /
同一格既挑素材又改文案 / 没有插入点 / 文案为空或含 `{{`。

**2026-11-26 放宽**：改写出来的文案里**可以引用必定有素材的槽位**（必填 / 已固定），
与作者侧同一套判据（§6.1）—— 使用者改写是作者那段的延续，规则不该两套。仍禁止引用
**可选**槽位与**自己**（自己那一支没有素材）。校验走 `rules.normalize_text_refs`
（把作者写法 `{{Mixed N}}` 换算成内部写法 `{{slot:key}}`）再判引用是否合法。

**与 2026-11-14 删掉的 `promptOverride` 不是一回事**：那个改的是**整段提示词**
（与「提示词只有一段」冲突）；这里改的是某一个插入点里的那一段话，骨架与编号仍由模板定。

**快照冻结不受影响**：`compile` 本来就是纯函数，改的只是入参；同一份 spec + 同一份
override 必得同一结果。

## 8. 契约

编写侧（模块 `template_pack`，权限码沿用 `template_pack:read / create / publish`，不新增码）：

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/template-specs/validate` | 只预检不落库（**必须挂 `rate_limit`**，`test_route_policy` 按方法扫） |
| `POST` | `/template-specs` | 保存草稿；`key + fingerprint` 幂等，`revision` 冲突 409 |
| `GET` | `/template-specs` / `/template-specs/{key}` | 列表 / 详情（含 draft 与最新版本） |
| `POST` | `/template-specs/{key}/publish` | 冻结发布：draft → version + slots，回执含 `version` 与 `tokensPreview` |
| `POST` | `/template-specs/{key}/disable` | 下架（历史版本保留） |
| — | `demoAssetId`（`POST`/`GET` 出参） | 展示案例：图或视频的资产 id。**只存在草稿、不进发布快照** —— 改案例不用发新版。挑选走 `/library/selection?purpose=case`（案例池，要 `library:case:read`）；从「我的素材」挑的那条会先转成案例（要 `library:case:write`），所以**没有该权限时整条「设置案例」入口不出现** |
| — | `allowedModels`（`POST`/`GET` 出参） | 使用模板时允许选用的模型清单。草稿里可改，**进发布快照**（见 §4.3） |
| `DELETE` | `/template-specs/{key}` | **软删**进回收站（`deleted_at`）。列表与模板库都看不到，可恢复 |
| `POST` | `/template-specs/{key}/restore` | 从回收站恢复 |
| `GET` | `/template-specs/trash` | 回收站列表（按删除时间倒序；不看 status / target） |

消费侧：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/template-specs/published` | 模板库卡片：已发布版本的快照（slots + 两段 prompt + model + params），不返回 draft。`?target=replacement\|generation\|all` 按**模型声明**筛（见 §11.0），不按槽位形状猜 |
| `POST` | `/template-specs/{key}/compile` | **纯函数式**：入参 `{version?, model?, slotValues}`，出参见 §6。不落库、不调 task。`model` = 使用者挑的那款，必须落在该版本的允许清单里（§4.3）；不传 = 固定模型 |

`compile` 之所以存在：展开与校验是**模板语义**，不能下放前端（否则编号规则有两份），也不该让封装去调 task（跨模块）。它只做映射，不产生副作用，天然可缓存、可单测。

模板库拿到 `compile` 出参后，由前端提交到**模型能力对应的接口**（2026-11-14 起）：

| 模型能力 | 接口 | 顶层字段 |
|---|---|---|
| `video` | `POST /tasks` | `durationSec` / `aspectRatio` / `stylePreset`，没有自由 `params` |
| `image` | `POST /generations/image` | `size` / `count`，其余声明的参数进 `params` |

**模板本身不声明「是图片还是视频」**：它只写模型，能力由 `GET /models` 决定。
判错方向的代价很具体 —— 图片模板走 `/tasks` 会被按 `Capability.VIDEO` 拒掉，
用户看到的是「这些参数无法提交给通用生成任务：count」，一句与模型无关的错。

两条映射都在前端一处（`features/template-library/taskPayload.ts`：
`toTaskPayload` / `toImagePayload` / `toSubmitPayload`）。共同口径是**参数不许静默丢**：
视频那边多出来的键没有落点 → 报错；图片那边除 `size`/`count` 外的键进 `params`，
由服务端按模型 `paramSchema` 校验（未声明即 400，也是看得见的失败）。

`compile` **不再有 `promptOverride`**（2026-11-14）：模板库不改文字，可变内容走 `text` 槽位。
旧字段会被 `extra="forbid"` 拒成 422，不是静默忽略。

## 9. 封装页 UI 规格（按参考截图）

单页编辑，三块区域：

```
┌─ 槽位区（左） ────────────┬─ 提示词区（中） ──────────────────────┐
│ [+ 上传] [从资产库选]      │  ┌ 已引用（= 槽位清单，可点回定位/删） │
│ ┌──┐┌──┐                  │  │  6036 / 米兰之夜6036-产品…          │
│ │1 ││2 │  ← 角标 = 编号    │  └────────────────────────────────────┘
│ └──┘└──┘                  │  [整段提示词：可写描述文字]              │
│ 槽位卡片：类型/固定或待选/  │  [引用用 chip 插入，手写大括号会被拦]    │
│ min-max/用途说明            │  总字数 961 / 20000（分段计）           │
├───────────────────────────┴────────────────────────────────────────┤
│ [模型 ⌄] [模式/参数：9:16·720P·8s·1个 ⌄]              [预检][发布]   │
└────────────────────────────────────────────────────────────────────┘
```

`@` 弹层两级（照截图）：

- 一级：`已引用`（当前槽位清单）+ `素材引用`：图片 / 视频 / 音频 / 文本 / 资产；
- 二级：
  - 图片 / 视频 / 音频 / 文本 → 插入 `type=<该 kind>, binding=user` 槽位（占位留空，模板库填）；
  - 资产 → 插入 `type=<该 kind>` 槽位。**封装包不是一个槽位类型**（`SLOT_TYPES` 里没有
    `pack`）：它是槽位**所在的容器**（`group`，见 §10.5），装的东西仍然是图片/视频。
    几个槽位放进同一个容器时，模板库只出一个选包入口、只列包；
  - **类型下拉的选项就是 `SLOT_TYPES`**（图片 / 成片 / 音频 / 文本）—— 封装不是一类媒体，
    它装的东西仍然是图片/视频，所以不进这个下拉；
  - **槽位的「候选标签」**把候选集收窄到几个标签（各自含其下级，任意级别）：封装时挑固定素材、
    模板库填写，两处看到的是同一批素材（`AssetPicker` 的 `tagIds` 从同一处传）；
  - 每个槽位卡片上有「封装时固定」开关：打开 = `binding=fixed`（模板库只读），关闭 = `user`。

细节：

- 插入位置决定 `position`；拖动缩略图改序 → 重排 `position` → 角标实时重算（因为编号是派生的，这里天然一致）。
- 音频/文本槽位在提示词里**不出现 chip**，只在槽位区列出，且 `ref_mode=attachment` 时提示「作为附加输入，不参与编号」。
- 底部模型切换后，`params` 区按新模型的 `param_schema` 重绘（已有能力）；旧值不在新 schema 里就丢弃并提示。

## 10. 模板库填表页

同一份 spec 的**只读镜像**：

- 提示词**整段只读**；要可变就用 `text` 槽位（填表时选文案）；
- `fixed` 槽位显示缩略图 + 「封装时固定」；`user` 槽位按 `type` 走不同的填法（见 §10.3）：
  图片/视频 → 一格一个选择器，上面一行标签用来在候选范围里再筛；**封装容器里的槽位
  由容器统一出一个选包入口、只列包**（见 §10.5）；文本/音频 → 各自的列表；
- 作者声明了「允许选用的模型」时（§4.3），这一栏给一个**只含这几款模型**的下拉：
  使用者挑的那款决定提交到哪个接口、参数默认值取哪款的 schema。清单为空时不出现
  这个下拉（老模板的样子，行为不变）；
- 提交按钮在 `min` 未满足时禁用，旁边说明缺哪个槽位（不写冗长引导语）；
- 提交 = `compile` → **按模型能力摊平** → `/tasks` 或 `/generations/image` → 提示 + 「去任务中心」。

### 10.1 已落地的形态（2026-11-14，`/templates/library`）

两栏常驻：左列卡片（名称 / 版本 / 槽位数 / 固定数），右栏就地填表。换模板只换右栏，
不跳页 —— 填到一半不会丢上下文。要点：

- **卡片不摆空封面**：spec 没有封图字段，就不放渐变块冒充缩略图（第一版放了
  `aspect-[16/10]` 的占位，截图一看就是大片空白）。卡片按「叫什么、第几版、要几样素材」
  排；选中的那一份才在右栏出图。
- 槽位卡片左上角是序号（= 编号顺序），`fixed` 显示缩略图 + 「封装固定」且**没有选择按钮**，
  `user` 显示「选择 / 更换」。
- 提示词整段只读（`不可编辑`），下面一列「`{{slot:key}}` → 第几位 / 第几份文案」。
- 提示词就在原位展开（见 §10.2）：选过的位置显示缩略图 / 正文，没选的位置是一个
  「选择」按钮；不再用「`{{slot:x}}` → 第几位」的对照表 —— 用户不需要先学占位符语法。
- 底部按钮在必填未满足时禁用并说明缺几项 —— 这是提交前置条件，不是业务规则；
  数量上下限、可读性、编号展开仍然只有服务端一份。
- 模型与参数**只读展示**：模板定的是模板定的。要改参数回规格页改模板。

**浏览器实测（2026-11-14）**：Chrome headless 注入令牌打开 `/templates/library` →
点槽位 2「选择」→ 弹层挑「3030粉」→ 按钮从「还缺 1 项素材」变「生成」→ 点生成 →
提交接口 **201**（视频 `/tasks`、图片 `/generations/image`）、右栏出现「已提交：… 去任务中心」；控制台无 error、无失败请求、
右栏 420px 无横向溢出（`scrollWidth > clientWidth` 的元素为空）。任务随即 DELETE，
验证不留下扣费记录。

### 10.2 占位符在界面上怎么显示（2026-11-14）

**封装页显示 `{{slot:key}}` 本身**：作者要看见引用才能把它插进提示词、才能判断
哪一处会变。其余页面一律渲染成真实数据 —— 但**模板库不显示提示词**（2026-11-14
起，见 §10.3 末尾）：填表的人只需要看见"要填什么"，整段提示词在那一栏里既不能改、
也不影响他做选择。

| 位置 | 数据来源 | 显示成 |
|---|---|---|
| 任务中心 | 任务的 `textLibraryIds` / `referenceLibraryIds` | `{{Text N}}` → 第 N 份文案正文；`{{Mixed N}}` → 第 N 张参考素材缩略图 |
| 资产库 | 快照的 `prompt` + `reference_library_ids` | 同上（快照存的是**注入正文之后**的提示词） |

实现只有一处：`entities/library/ui/PromptRefs.tsx`，两处传不同的 resolver。

**缩略块可点**：提示词里没有别的地方能看一眼原图，所以行内缩略块点开是弹层大图 /
可播放视频；封装里的单张点开看那一张，「N 张」点开看整组（封装没有「一张代表图」）。
单选槽位选完即关选择器 —— 留着弹层等于让用户再点一次右上角，而缩略图早该出来了。
解析不到就**原样保留占位符**（灰底小字）—— 历史任务缺快照时，看到 `{{Text 1}}`
比看到空白更接近真相。

配套的三处数据改动：

- `ImageFeedItem` 补 `referenceLibraryIds` / `textLibraryIds`：只给 prompt，前端无法
  还原正文与缩略图。它是**只读投影**，在 `test_architecture.py` 的
  `_REFERENCE_PROJECTIONS` 里显式豁免（真正写入方 `modules/image` 已声明来源）；
- 视频入库快照的 `prompt` 改成 `inject_text_refs(...)`：资产详情是给人看的，
  `{{Text 1}}` 在那里没有上下文可解析（快照不带文案 id）；
- 生图作业名也从「提示词前缀」改成**注入正文之后**的文案：模板生成的图取名
  `{{Text 1}}`，列表里谁也不知道那是什么。

**生成产物命名**：`用户名-年-月-日-时-分-秒`（`core/naming.py` / `format.generatedFileName`）。
标题是一句描述、同一句话能生成十次，落在磁盘上就是十个同名文件；名字里放作者与时间，
下载后能分清哪个是新的。时间按**本地时区**格式化，后缀只认真实产物。

### 10.3 素材填写按一级标签分组（2026-11-14）

用户要的形态：「显示这个模板所有需要输入的一级标签，一级标签下显示二级标签，点二级标签
选择素材。比如名称产品1的槽位、类型图片、一级标签产品，就显示 `产品.产品1`，下面是图片类型
一级标签为产品的二级标签，点二级标签显示具体素材」。

```
填入素材                                      还缺 1 项
┌──────────────────────────────────────────────────┐
│ 产品 · 产品1        ＊        图片 · 已选 1/2 · 共 9 │
│ [T35✓] [3030]                                     │
│ 点一个标签，下面是它的素材。                       │
└──────────────────────────────────────────────────┘
2. 文案            文本                    选择文本
```

- 标题 = **槽位名**；槽位没圈标签时额外提示去封装页补一个；
- 标签筛选是**三行**（一级分组 / 二级系列 / 三级具体词）**多选**：跨链多选是并集，
  同一条链上只按最具体的一层筛（父的范围含子，两个都留着范围会重复）；
- 能挑的标签只在**槽位的候选集**之内（作者圈定的范围 + 它的下级）——
  作者与使用者看到的必须是同一批素材；
- 没挑标签时按候选集筛（`/library/selection?kind=<type>&tagIds=<id…>`），
  挑了之后按挑的筛；
- 点素材即选中：单选槽位替换、多选槽位累加、已满则禁用其余（`slotPick.pickWithin`）；
- 胶囊**不带计数**：标签接口的数字是「列表口径」（被装进封装的成员不单列），
  而这里用「选择器口径」（成员也要能挑），两者对不上；真实条数放在右上角「共 N」。

**发布闸门**（同一条改动的另一半）：要让用户填的**图片/视频槽位必须圈至少一个标签**（`tag_ids`），
否则发布 400 并指名是哪几个槽位。理由很直接 —— 没有标签时这一段只能退化成"全部素材"，
素材一多就没法挑，而这正是要消灭的形态。只要求 `binding=user`：固定槽位作者已经选死，
模板使用者不挑；文本/音频/封装各走各的选择器，没有"按标签分组"的概念。

**右栏只显示"要你填的东西"**（2026-11-14 当天补的）：`binding=fixed` 的槽位与整段
提示词都不进这一栏。固定素材是作者选死的，列一串只读 chip 只会让人以为还能点；
提示词在填表页既不可编辑、也不参与选择。两者都在封装页看。
槽位全是固定的模板，这一栏只留一句「素材都由作者固定了，直接生成即可」。

### 10.4 随机性三档（2026-11-19 改为「整段换提示词」）

右栏顶上一根**分段控件**（`shared/ui/Segmented.tsx`），三档决定**可选槽位**那一段
提示词怎么说：

| 档 | 可选槽位 | 用哪段提示词 |
|---|---|---|
| **随机** | **不显示** | 作者另写的**随机档提示词**，整段替换主提示词 |
| **均衡**（默认） | **不显示** | 主提示词，可选槽位用「未选时文案」 |
| **自定义** | 显示 | 主提示词，使用者挑素材 |

三档的差别**只在可选槽位与提示词来源**。**必填槽位三档都显示、都要使用者自己填** ——
必填意味着「不给素材就生成不了」，任何一档把它藏起来都等于让人卡死在界面上。

> **2026-11-19 两次语义变更**：① 「随机」原先是「系统从素材库随机挑素材」，改为
> 「不传素材，抽一段随机文案」；② 同日再改为「不传素材，**整段换成作者写的随机档
> 提示词**」—— 按槽位拆碎写不出一个完整的新场景，作者得在十几个格子里各写几条，
> 写完还是拼不出。随之移除 `useRandomPools` / 洗牌 / 「换一批」/「系统」角标，
> 以及按槽位的 `random_texts` / `randomTextChoices`（迁移 `667e0540179b` 换列）。

控件**无条件出现**（2026-11-18 用户拍板：「全是必填也显示」）。三档是这一栏的
**前提** —— 先定「谁说了算」，再看下面要填哪几格；全是必填的模板也让使用者看见
这个选择，切换到别的模板时档位也就有上下文了。

三档的含义写进每个按钮的 `title`（悬停可见），**不在控件下面挂解释文字** ——
那行小字说的是同一件事，而布局本身已经能说明「这三档在选什么」。

**唯一例外**：模板没配随机档提示词时，那一档**显示但置灰**，并在控件下写一行
原因（「该模板未配置随机档提示词」）。死按钮必须给原因，否则用户会以为坏了；
干脆不渲染这一档则等于这个能力不存在，用户不会想到去问。

#### 「均衡」= 不显示 + 不传，两件事必须同时做

只做一件会得到两种不同的错误：

- 只不显示、不传 → 提示词里那个可选槽位的段落没了（作者写了「未选时文案」
  也不生效），使用者的意图被悄悄丢掉；
- 只显示、不传 → 界面上摆着一个填不了的槽位，用户不知道该干嘛。

所以均衡档下可选槽位**既不出现在右栏，也不进 `slotValues`** ——
两者是同一件事的两面。缺料判定与二次确认框都改看**真正提交的那份**。

#### 随机档：整段替换提示词

作者在封装页的提示词下面另写一段「随机档提示词」（同一个 `PromptBox`，同样能
`@` 引用槽位、同样有字数上限）。模板库选「随机」时：

1. 前端 compile 请求带 `useRandomPrompt: true`；
2. 后端在 `compile_for` 里把 `spec.prompt` **整段换成** `spec.random_prompt`，
   再交给纯函数 `compile_spec`；
3. 可选槽位仍不显示、不传素材（与均衡档一致），它们由「未选时文案」兜底。

**为什么是替换而不是追加**：要变的是「整个场景怎么写」，不是「某一句话换说法」。
追加会让两段之间的衔接变成作者要操心的隐式契约；替换则两份各自都读得通。

**为什么仍是纯函数**：随机的是「用哪一段」，而两段都是确定的文字。切换发生在
service 层（`compile_for`），`compile_spec` 看到的始终是一份确定的 spec ——
同一 `(spec, fills)` 必得同一结果，与项目不变量一致。

**没配就拒绝**：`random_prompt` 为空时传 `useRandomPrompt: true` 一律 400，
**不静默回退主提示词** —— 回退的样子是「随机档和均衡档产出一模一样」，用户会
以为随机坏了却查不出原因。前端也会把这一档置灰；档位用派生值
（`resolveRandomness`）而不是在 effect 里改 state，因为换模板后 state 可能还停在
`random`，派生保证「选中的档」与「提交的标记」永远一致。

**两段提示词的引用规则相同**：`random_prompt` 也能引用任意槽位、也能用
`{{slot:key.N}}` 钉住可选槽位；发布闸口**两段一起检查**兜底文案（随机档同样
不传可选素材）。「哪些槽位必须显示」与「缺几张」的判据都按**当前生效那段**
提示词算 —— 拿主提示词去判随机档，会把随机档钉住的槽位误当成可以省掉。

#### 均衡档的例外：提示词里「第 N 张」引用了它

有些可选槽位**不能不传**，否则编译期 400，而那句报错（「第 2 张不存在」）
与「我用的是均衡模式」毫无关系，使用者只会以为模板坏了。三种引用写法的语义：

| 写法 | 没填素材时 | 均衡档能省掉吗 |
|---|---|---|
| 根本没引用 | 无影响 | **能** |
| `{{slot:x*}}`（整组） | 降级为空 | **能** |
| `{{slot:x}}`（单张） | 用「未选时文案」兜底；**没写兜底就报错** | 写了兜底**能**，没写**不能** |
| `{{slot:x.N}}`（第 N 张） | **必然报错**（没有「第 2 张」这回事） | **不能** |

所以「能省掉」的条件是：没被引用、或只被整组引用、或被单张引用且作者写了
「未选时文案」。不能满足的槽位在均衡档下**照常显示**。

`slotIndexRefs.ts` 的引用正则与后端 `compile.py::_SLOT_REF` **同形状**
（两边允许空格）—— 形状漂移过一次的后果是「界面以为不冲突而后端 400」。

#### 槽位的实际下限不看 `minCount`

`minCount` 是作者写死的**意图**；提示词里的引用是**硬约束**。两者不一致时
取大的（`requiredSlotCount`）：

| 提示词写法 | 实际下限 |
|---|---|
| 没被引用 / 整组引用 | `minCount` |
| 单张引用且无兜底文案 | `max(minCount, 1)` |
| `{{slot:x.N}}` | `max(minCount, N)` |

拿 `minCount` 当唯一判据的后果：界面显示「不缺料」，用户一点生成，后端回一句
「第 3 张不存在」—— 使用者完全看不出是自己的模板有问题。这个下限**与档位无关**，
三档下都一样（它来自提示词本身）。

> 发布闸门已经在**发布**时拦掉「单张引用且无兜底文案」的可选槽位
> （`rules.py::_validate_slot_texts` 之后的 `_check_executable`），
> 所以这条分支实际只对**闸门加上之前发布的旧模板**生效。

#### 实测（2026-11-18，真实后端）

起当前版本后端（`uvicorn main:app --port 8099`），建了一个临时模板
（必填 `image_1` + 可选 `opt_1`）走完三档：

| 场景 | 结果 |
|---|---|
| 均衡档：只传必填 `image_1` | 200，提示词 `测试 {{Mixed 1}}`，可选槽位不出现在结果里 |
| 传了 `opt_1` | 200，提示词 `测试 {{Mixed 1}} 再看 {{Mixed 2}}` |
| 提示词写 `{{slot:opt_1.1}}` 但均衡档不传 | **400**「提示词引用的「可选参考」第 1 张不存在（这次填了 0 张）」 |
| 提示词写 `{{slot:opt_1}}` + 有 `emptyText`，均衡档不传 | 200，兜底文案生效（`测试 {{Mixed 1}} 再看 （无参考）`） |

第三条正是上面那条例外的由来。验证用的临时模板已下架并软删，模板库恢复原状。

### 10.5 封装：一个容器，一次选包填多格（2026-11-20）

**素材从哪来只有两种情况，由「这一格在不在封装容器里」决定：**

| 位置 | 模板库那一格列什么 | 挑的单位 |
|---|---|---|
| 独立槽位（`group` 为空） | 只列候选**素材** | 一张一张挑 |
| 在封装容器里（`group` 非空） | 只列**封装包**，点一次填好几格 | 一整套一起换 |

**没有「来源」这个字段。** 2026-11-20 删掉了 `pickMode`：它和 `group` 表达同一件事，
两处并存时接口能收到「在容器里、却声明从素材取」这种没法解释的组合；而界面上已经不
显示它了 —— 那就是一个作者看不见、却还在影响模板库列什么的隐藏状态。来源是位置的结果。

> 演进：11-19 是「包和素材并排在一个网格里，靠标签自动归位」（判据落在标签的巧合上）；
> 11-20 上午加 `pickMode` 让作者显式声明；同一天下午收敛成「容器 = 包」——
> 因为「来源」和「在不在容器里」是同一件事，一个字段够，两个就一定会漂移。

#### 10.5.1 容器长什么样

作者：槽位板块的「加槽位」→ **封装（一次选包填多格）** → 得到一个框，里面默认
两个图片子槽位；框里还能继续加图片/视频。

```
┌ 封装槽位 · 2 个槽位 · 使用者选一次包，一起填好 ────────┐
│  左图   用户填  必填                                   │
│  右图   用户填  必填                                   │
│                                        [+ 加槽位]      │
└────────────────────────────────────────────────────────┘
 补充图（可选）
```

模板库那边：

```
封装槽位 2/2                         选一个包，这几格一起填好
[拼接测试（小图）· 2 张] [6036黑白 · 3 张]
左图  6036.jpg ×
右图  6036米兰之夜内衣产品图-1.png ×
```

数据上容器不是一条独立记录：它就是槽位上的一列 `group`（空 = 独立槽位）。
`group` 相同的槽位：

- **共用一个选包入口**：模板库只列一次包，点一次按标签把成员分到各格；
- 只能是**图片/视频**、只能**用户填**（容器里没有「用户填 / 已固定」开关）；
- 顺序上必须**相邻** —— 容器在界面上会不会断开，而 `{{Mixed N}}` 仍按 `position`
  排，两者一错位就是「看着是两段、编号却连着」。后端 `_validate_groups` 会拦。

点包只填**本容器**的格子：同一个包会在两个容器里各出现一次，点哪个填哪个。

#### 拖动能穿过封装的边界，也能整块搬

拖动一个槽位时，**落到谁旁边就归谁的组**：

| 落到哪 | 结果 |
|---|---|
| 某行的上半 / 下半 | 插到它前面 / 后面；那一行在容器里就进容器，在外面就留在顶层 |
| 封装框的空白处（标题栏、底部按钮那一圈） | 追加到这个容器的末尾 |
| 列表末尾的「拖到这里移出封装」 | 移出到顶层。这条只在拖的是容器成员时出现 —— 容器正好是最后一段时，后面没有行可以当落点 |

抓封装框头的那个手柄拖动，是**整块搬**（里面的槽位一起走，顺序与归属都不变）：
落点是「段与段之间」，容器里的行不接这个落点（否则把容器拖到自己成员上，高亮会画在
成员之间，看起来像要插进去）。拖到自己的成员之间 = 不动。

插入位置在拖动时**画成一条线**（将要插进去的那条缝），不是把整行高亮 ——
整列都在发光等于没信息。线用绝对定位，不占版面，拖动时列不会抖。

进容器会改写归属：`group` 换成容器的、`binding` 换成 `user`。**固定槽位进不来**
（它钉着一张具体素材，改过来等于把那句话删掉而没人知道），文本/音频也进不来
（不参与编号分发），两种情况都会说明原因。出容器只清 `group` —— 回到「从候选素材里挑」
就是它的全部含义，没有第二个字段要跟着改。

成员相邻这条不变量由落点规则自己保证（插到谁旁边就归谁的组），所以不需要禁止跨组拖动。
容器被拖空时它自然消失（容器是按 `group` 聚合渲染的，不是一条独立记录）。

#### 容器的筛选行

**容器的筛选行 = 子槽位候选标签的并集**（自动继承），作用与普通槽位那一行相同：
自动圈定范围、手动再收窄。例如「左图 = 产品 + 正面图，右图 = 产品 + 三视图」，
容器就是 产品 + 正面图 + 三视图 —— 一级维度（产品）要由使用者选一个二级
（6036 / T35…），选完就变成「6036 + 正面图 + 三视图」。

发给 `/library/packs` 的是**具体的二级标签** + `mode=all`：成员标签的并集要覆盖
全部条件，也就是「这个包能不能把这几格都填上」。容器里有几格，包就得几张对得上，
否则点一次只填一半。**一级维度不进这个条件** —— 素材身上挂的是它的叶子，把
「产品」也带上等于要求每个成员都挂一级标签，一个包都匹配不上（前端按
`childCount` 判断，只把叶子发过去）。

#### 判据两道

1. **这一格在同一个容器里**（`group` 相同）。独立槽位不参与 —— 它只从候选素材里挑，
   点包不该动它。
2. **成员的标签 ∩ 槽位的候选标签**。所以出现在「正面图」里的包，一定至少含一张
   正面图；包里没有能对上某格的成员时，那一格留空（必填会亮缺料星号）。

- **列表**：`GET /library/packs?tagIds=<子槽位候选标签并集>&mode=all`，后端只返回
  「成员标签并集覆盖全部条件」的包。容器没圈候选标签时**不发这个请求**：没有判据
  就填不上，列出来只是个死按钮。
- **分发**：点包后拉 `GET /library/packs/{id}`，对**这个容器里**的每一格取
  `members.filter(m => m.tags ∩ slot.tagIds ≠ ∅)`：

| 匹配数 | 处理 |
|---|---|
| 1 | 填进那一格 |
| 0 | 不动（必填槽位自己会亮出缺料星号） |
| 多 | **也不填**，toast 说清是哪几格有几张 —— 猜一张进去，生成的图错了没人知道 |

已进回收站的成员（`deleted`）不参与分发，**也不参与上面那条列表判据**：
包身上那串标签是并集快照，而过滤要看的是「现在还能填吗」。只看快照的话，
包里唯一那张「细节图」删掉之后，这个包仍然会出现在「细节图」那一格里 ——
点下去一格都填不上。所以 `list_packs` 只对 `state=active` 的成员取并集；
卡片上的「N 张」仍按成员总数算（详情里会把已删的那张照列并标出来）。

**一格已经填满，包也照样能点**：包是「动作」不是「选中项」，它改的是这一批格子
（有素材的格覆盖、对不上的一格不动），点第二次是幂等的。按「本格满了」置灰，
会让「正面图先手挑了一张」之后这一行里的包再也点不动 —— 而它本来正好能把
三视图那格一起填上。

**候选素材只取一屏（24 张），下面跟着一行「还有 N 张 · 显示全部」**。首屏不拉满
是为了不一口气发几十个缩略图请求，但不能只有首屏：标题写着「共 47」而第 25 张以后
在界面上不存在，用户只会以为那张图不在库里。上限 200（与服务端 `pageSize` 的 `le`
同值），再多就提示按标签收窄。

#### 发布闸门

容器里只能是**用户填的图片/视频**：固定槽位钉的是一张具体素材（要钉就钉那张），
文本/音频不参与编号分发。这些在 `rules._validate_slot` 里当场 400；
候选标签仍然必须有（发布闸原有那条），否则没有分发判据。

#### 悬停预览：摊开成员，而不是放大封面

包的封面只是第一个成员的封面。放大它等于把这个包当成一张普通图，用户看不出
它还有三视图和细节图。所以包的悬停浮层（`PackHoverPreview`）列的是**成员缩略图**
（最多 6 张 + 「还有 N 张」），已删成员照列并标「已删除」——包静默少一张比露出来更糟。

#### 编译层零改动

分发填进去的仍然是**成员素材的 id**，所以 `compile_spec`、`{{Mixed N}}` 编号、
`empty_text` / `filled_text` / `minCount` 全部照旧。「选一次」只发生在选择这一层。

#### 不做的

- **「来自哪个包」只记在页面状态里（`packFill`），不落库**：`values` 里始终只有素材 id，
  所以提交出去的配置与包无关 —— 包删了，成片照旧能生成（成员还在）。
  但在当前这一页会**持续订阅**那个包的详情，包被删时清回它填过的那几格并提示；
  **只认 404**：网络抖动或服务重启也会让请求失败，那时清空等于在用户没操作的情况下
  丢掉已配好的素材。
  **这条记账只对当前模板有效**：换模板要清掉（`packFill` / `pendingPack` 一起），
  槽位 key 是自动生成的（`image_1`…），两个模板重名是常态 —— 留着的话，
  上一个模板的包在别处被删，会把这个模板里手挑的那几格一起清掉；
  点了包、详情还在路上时换模板，回来那一笔也会把旧包分发进新模板。
  使用者手改了某一格，那一格也要从记账里摘掉（它已经不是「包填的」了）。
- **不支持一个模板多组产品**：那需要给槽位加「属于哪一组」，而当前所有产品槽位
  共享一次选择已经够了。

#### 接读为什么不在 P1（2026-11-14 实现时确认）

原稿把「runtime 改读 spec」放在 P1，理由是"不许投影回旧表"。真做时撞上一个事实：
替换链按「原片 + 素材包」找模板（`find_template_for_run(source_asset_id, pack_id, template_id)`），
而一条 spec 可能根本没有视频槽位、也没有包槽位 —— 要让它读 spec，先得有一条判据说
"哪条 spec 是可替换模板"（模型属于替换通道？有 fixed video 槽？有 fixed pack 槽？）。

这条判据本质属于 P3「替换变成 task 的一个 capability」，P1 硬定就是猜。所以：

- **P1 只定表**，不写 `video_templates`（不产生第二份数据），替换链继续读自己的旧表；
- **P3 一次性接读**，并把判据写进 capability 声明（模型侧声明"我是替换能力"，
  spec 侧只按槽位组合校验），避免用启发式推断。

#### 数据迁移为什么也不在 P1（同日，同一根因）

上表那套映射是**目标形状**，但它的验收标准依赖一个 P1 还不存在的东西："
哪条 spec 与旧模板等价"。而 `compile` 产出的是 `POST /tasks` 的请求体，不是替换任务 ——
把一条 `video_templates` 迁成 spec，运行行为就换了（没有审核范围校验、没有成片复核、
不再走替换链）。在 P3 定清 capability 之前做这件事，会得到一个"看起来等价、
跑起来不同"的模板集，比不迁更糟。

所以 P1 只交**可机检的那一半**：`tests/test_template_spec_equivalence.py` 用旧
`media_order` 与 spec `compile` 对同一组素材断言「编号 → 素材 → 角色」逐项相等。
P3 补上 capability 判据后，迁移只需要让这份守卫继续绿，就算没换语义。

迁移形态也一并定下（P3 照此实现，别重新推导）：

- **位置**：`api/scripts/`（一次性运维脚本，不是模块）。它要同时写资产库（建 `kind=pack`）
  和规格表，而业务模块之间不许互相 import —— 脚本在 `modules/` 之外，正是为此存在的
  （同类先例：`scripts/tp_live_check.py`）。
- **只产草稿**：迁出来的 spec `status=draft`，不自动发布。原模板的模型/参数组合要人来确认
  （旧数据里"用哪个模型跑替换"是运行时按渠道定的，不是模板里的一列）。
- **幂等**：以 `spec.attributes.migratedFrom = "template_pack:<id>"` 为标记，重跑跳过；
  资产库封装按 `(owner, 成员 asset 序列)` 去重，避免第二次跑就多出一批同内容的封装。

### 11.0 P3 第一刀已落地：替换能力由模型声明（2026-11-14）

替换链要按「原片 + 素材包」找回对应模板。判据**不能**从槽位组合推断
（"有 fixed video 槽 + 有 pack 槽就是替换模板"）—— 普通多图模板会被误判，
然后在替换链路里以「没有绑定档案」失败，那是个和用户操作毫无关系的错。

所以判据落在模型侧：

- `ModelSpec.replacement: bool = False`（`infra/ai/base.py`）—— 驱动声明「我能跑替换」；
  三个 `*-replacement` 模型置 `True`，其余默认 `False`；
- 经 `ModelSummary`（core 端口）→ `GET /models` 与 `/model-driver/models` 出参；
- `GET /template-specs/published?target=replacement|generation|all` 按它筛，
  只跟**当前发布版本** join（草稿里的模型不算数）。

实测（dev 库 6 个模板）：`/models` 三个替换模型 `replacement=true`；`?target=replacement`
拿到 5 个（全是 libtv），`?target=generation` 拿到 1 个（纯提示词，agnes 模型）。

**这一刀不动表、不动替换链**：下一步才是"runtime 端口读 spec"。先有稳定判据，
接读时才不用回头改筛选口径。

### 11.4 槽位「要什么」合成一根轴 + 一级标签（2026-11-14，迁移 `a7d3f0c85e21`）

封装页的槽位卡片原来有两列要填：**类型**（图片/视频/音频/文本）与**来源**（单个资产/资产库封装）。
用户看完直说：「类型这里应该是获取资产库的种类」「来源改成一**级标签**，获取资产库的所有一级标签，
封装时固定选择素材只能选类型筛选、一级标签筛选后的素材；用户选择也一样」。

**改法**

| 原来 | 现在 |
|---|---|
| `type` ∈ image/video/audio/text | `type` ∈ **资产库的 kind**（多一个 `pack`） |
| `source` ∈ asset/pack | **删掉**：`type=pack` 就是"要一个封装"（`InputSlot.is_pack` 唯一一处定义） |
| （无） | `tag_ids`：一组标签（任意级别），**候选集范围**，空 = 不限 |

为什么 `source` 要真的删、而不是留着不用：两根轴表达同一件事时，接口能收到
`type=image, source=pack` 这种自相矛盾的组合，而代码里每一个 `if slot.source == "pack"`
都得再回答一次"那 type 算什么"。合并之后判据只剩 `type`，`compile` / 校验 / 选择器 / 前端
全部同一口径。`ref_mode` 显然也是派生的（audio/text → attachment，其余 → mixed），但它
属于另一根轴、这轮不动 —— 记在这里免得下次误以为"漏了一个"。

**候选集与内容分开**：`tag_ids` 只决定"能选什么"，`compile` 完全不看它 —— 标签被改名、
被删掉，已发布版本照旧能编译。它是作者写的声明，所以跟着槽位一起进发布快照（存在
`template_spec_slots` 行里），而不是"编译时再查一次库"。

**两处选择器同一批素材**：封装时挑固定素材（`SpecWorkspace`）与模板库填写（`SpecLibrary`）
都把 `slot.tagIds` 传给 `AssetPicker.tagIds` → `/library/selection` 的 `tagIds`（标签按
`expand_tag_ids` 展开成"自身 + 全部下级"，多个标签之间是并集）。两处各筛各的，
就会出现"作者选的图用户根本挑不到"。

**老模板继续能用**（2026-11-17）：契约从 `tagId`（一个）换成 `tagIds`（一组）后，
老草稿里的 `tagId` 由 `SpecSlotIn` 的 before 校验器翻译成 `tagIds` 的第一项；
已发布槽位行只有旧的 `tag_id` 时，读的时候退回它（`spec_service._slot_tag_ids`）。
迁移 `d9e4f1a83c07` 只加列、不回填 —— 回退读一次就够，不必动数据。

**迁移**：`template_spec_slots.source='pack'` 的行 → `type='pack'`；草稿 JSON 里的
`"source"` 并进 `type` 后删键（漏了这一步，草稿一打开就 422 —— `extra="forbid"`）。
降级能把 `source` 算回来，但**原来的 `type` 找不回来**（已被 `pack` 覆盖，按 `image` 写回）。

### 11.1 P3 终局：统一到 task（2026-11-14 拍板）

**不留独立替换工作台。** 替换不再是一条平行链路，而是"某个模型 + 某组槽位"的普通生成：

| 现在的替换专属物 | P3 之后 |
|---|---|
| `video_templates` 表 + `/templates/video-templates` 路由 | **P1 起只读**（runtime 改读 spec），P3 删除。模板只在 `template_specs` |
| `template_packs` / `_references` / `_versions` | 删。多图语义由 `type=pack` 槽位指向资产库封装表达（见 §4.1）；旧包在 P1 迁成资产库封装 |
| `replacement_runs` / `_run_inputs` / `_reviews` | 删除或**只读归档**；新任务一律落 task 自己的记录 |
| `supportedScopes` / `wardrobeMode` / `scopeOptions` | `spec.attributes: dict[str, str]`（`scope` / `wardrobe` 两个键），由 `compile` 读、进提示词变量 |
| 成片复核（review / reconfirm） | 任务中心的评价能力；不再在模板模块里长第二套 |
| `modules/template` 的 `_materialize_inputs` / `stage_library_refs` / `pipeline.py` | 删。字节只由 `generic_inputs.materialize` 落地 |

**保留但换位置的**

- 发布即冻结（`template_spec_versions`）不变量不变；
- 「审核范围不能临时扩大」这条规则保留 —— 只是载体从素材包表变成 `spec.attributes.scope`，由 `compile` 校验；
- 历史档案（`replacement_runs`）不迁移成 task 记录（形状不同、字段不对应），保留只读视图供查历史，写入口关闭。

**三条到达判据**（比看文件树可靠，缺一条就是"又长出一套平行的东西"）

1. 删掉 `video_templates` 与 `template_pack_references` 后，替换业务仍完整；
2. `modules/template` 里不再有物化素材的代码，字节只由 `generic_inputs` 落地；
3. `/tasks` 入参与今天完全一致 —— 模板没有污染执行层。

**为什么不合并模块**：封装仍只管"定表"、task 仍只管"执行"，`modules/template` 的下线是**删掉重复的编排**，不是把封装并进 task。P3 之后项目里只有两个概念：模板（在封装模块）与任务（在 task）。

## 12. 不变量与守卫（每条都要有测试）

4. 编号只由 `position` + 填充数量决定：给定同一份 spec 与同一组填充，`compile` 是纯函数（同一入参两次调用结果相同）。
5. `audio` 槽位永不拿到 `{{Mixed N}}`；引用音频槽 → 400。
5b. **作者写的 `{{Mixed N}}` 指向第 N 个图片/成片槽位**（文本/音频不占号）：
    `rules.visual_slot_keys`、`compile` 的 `counter`、前端 `specDraft.visualSlots`
    三处同一判据；越界的 N → 400（不能原样漏进供应商提示词）。
5c. **结构一变就重编号**：增删 / 排序 / 改类型之后，正文与两段文案里的序号必须
    整体平移（`specDraft.renumberRefs`）。守卫：在第一个槽位前插一个，
    `{{Mixed 1}}` 应变 `{{Mixed 2}}`；把图片槽位改成文本，后面的编号前移。
6. 提示词里引用了不存在的槽位 → 400；`{{slot:x.2}}` 越界 → 400。
7. 发布后 `template_spec_versions` 与 `_slots` **只插入不更新**（改模板 = 新版本）。
8. `fixed` 槽位绑定的素材（`asset_id` / `pack_id`）在发布时校验存在且可读；素材被删只影响"新建任务"，不影响历史。
9. **spec 不得复制封装成员**：`{{slot:…}}` 展开一律现场调 `LibraryLookup.expand_packs()`，
   不落库、不缓存成员列表 —— 库改了成员，模板立刻跟着变，这才是"结构归库"的含义。
10. `compile` 不得重排 `expand_packs()` 给出的成员顺序（库的 `position` 即槽位顺序）。
11. **可选 = `min_count == 0`**：不另设 `required` 字段。判据在三处（封装页开关、
    发布闸门、编译规则）必须同口径 —— 不同步时界面显示「必填」而编译器放行，
    这种错只在生成结果里显形。
12. **槽位文案里只能引用「必定有素材」的槽位**（必填 `min_count >= 1` 或已固定
    `binding == "fixed"`，且 `ref_mode == "mixed"`）；可选槽位一律不许。
    `filled_text` 还可以引用**自己**（`{{slot:key}}` / `{{slot:key*}}` / `{{slot:key.N}}`），
    `empty_text` **不可以**引用自己 —— 后者用的正是「这一格没素材」的时候。
    判据只有一处：后端 `rules.py::is_always_filled`，前端 `specDraft.ts::isAlwaysFilled`。
    （2026-11-26 改：老口径「见引用就拒」误伤了「默认描述里提一下必填槽位的素材」。）
13. **可选槽位被单张引用时，`empty_text` 必须有值**（发布闸门）。整组引用不要求
    （没填时降级为空），第 N 张引用不要求（没填时必然报错，与文案无关）。
14. **必填 = 素材一定在 = 直接插编号**：必填槽位（`min_count >= 1`）**不许带**
    `filled_text` / `empty_text`（结构校验 400，并说清「改成可选」）。
    这些文案是**可选槽位**才有的状态 —— 必填槽位没有「没填」这个状态。
15. **两段文案的引用 token 由程序生成**：作者在「选中时文案」里打 `@` 选候选
    （候选列该槽位自己的三种写法 + **必定有素材**的其它槽位），**不手敲 `{{slot:key}}`**
    —— 手敲拼错了要到编译期才 400，而槽位改名后手敲的引用会静默失效。
    正文**默认描述段内**的 `@` 候选只列必定有素材的槽位（段内文案的引用范围更窄）。
16. **切成必填时清掉两段文案**（并告知作者）。留着的话后端会 400（见 14），
    而界面看不出是哪一条规则 —— 作者明明写了文案，点保存却被拒。
17. **随机性三档只改可选槽位**（§10.4）：必填槽位三档都显示、都要使用者自己填。
    藏起来等于让人卡死在界面上。
18. **「均衡」= 不显示 + 不传，两件事必须同时做**：可选槽位既不出现在右栏，
    也不进 `slotValues`。只做一件会得到「意图被悄悄丢掉」或「摆着一个填不了的
    槽位」两种不同的错误。
19. **随机档 = 整段换提示词，不是换某一段文案**：随机档不传可选素材（同均衡档），
    差别只有 `useRandomPrompt` —— 后端把 `prompt` 整段换成 `random_prompt`。
    档位用**派生值**（`resolveRandomness`）而不是 effect 同步：换模板后 state 可能
    还停在 `random`，派生保证「选中的档」与「提交的标记」一致。
    **「第 N 张钉住」与「缺几张」都按当前生效那段提示词算** —— 拿主提示词去判
    随机档，会把随机档钉住的槽位误当成可以省掉。
20. **槽位的实际下限不看 `minCount`**：提示词里「第 N 张」是硬约束，
    实际下限取 `max(minCount, N)`；单张引用且无兜底文案时至少 1 张。
    这个下限**与档位无关**。
21. **说明性小字能并进控件就别单独摆一行**（2026-11-18 用户拍板）：解释优先
    塞进**占位符**（填了内容就消失）、**选项名**（如「文本（占 {{Text N}}）」）、
    **`title`**（悬浮才看），而不是常驻 `<p>`/`hint=`。常驻小字既难看又占版面，
    而且**同一件事说两遍**（控件里已有又说一遍）是这类界面最常见的冗余。
    但**状态/数据/警告**类小字要留（版本号、类型、最多数量、缺标签警告）——
    删掉的是「解释」，不是「信息」。
22. **约束与解释要分开判**（2026-11-18）：删说明性小字时最容易连带删掉**约束**。
    「保存后整组替换」「改密后所有设备会被登出」「口令要 ≥4 个不同字符」——
    这些用户不看输入框猜不到，删掉就是让人做出错误预期。
    判据：**看得见 → 删**（重复说明）；**看不见又猜不到 → 留**（约束）。
    两条都要钉进守卫，否则「顺手删干净」会误伤约束。
    「保存后整组替换」原来被手抄三份，收到 `PermissionSummaryBar` 一处。
23. **死按钮必须给原因**（2026-11-19）：模板没配随机档提示词时，那一档
    **显示但置灰**，并在控件下写一行「该模板未配置随机档提示词」。不渲染这一档
    等于这个能力不存在（用户不会想到去问）；显示了而不给原因，用户会以为坏了。

24. **必填槽位必须在「正文」里被引用**（2026-11-27 收紧）：必填槽位
    (`min_count >= 1` 且 `binding != "fixed"` 且 `ref_mode == "mixed"`）的引用
    必须落在**正文**（框选的默认描述段之外）—— 写在某个槽位的「未选时文案 /
    选中时文案」里**不算数**。
    - 为什么：框选段在提交时会变成那个槽位的「未选时文案」；使用者挑了素材它被
      「选中时文案」顶掉，使用者（自定义档）或模型（随机档）改写它它被换掉，
      而同一格只能二选一 → 那处引用随时会消失，素材就白传给供应商。
    - 「两段文案里都写了」也不行：只要其中一段能被丢掉，就等于没写
      （之前放过 `empty ∩ filled` 一条兜底，正是漏网的那种形态）。
    - 判据只有两处：后端 `rules.py::validate_required_slot_refs`、
      前端 `template-specs/requiredRefs.ts::requiredSlotRefError`（互相指认）。
    - 前端**只提示、不拦写入**：作者可能正在把引用挪到正文，半路上的草稿本来就不合法。

25. **「未选时文案」不许引用自己**（三处同口径）：作者侧的文案由
    `rules._validate_slot_texts` 拦，使用者/模型改写的那份由
    `spec_service._apply_slot_text_overrides` 就地拦（不靠更深的
    `validate_spec` 兜底 —— 那样报错说的是「未选时文案」，定位不到是这次改写造成的）。
    理由：未选时文案用的正是「这一格没素材」的时候，那一格自己那时没有编号可指。
    （「选中时文案」相反：允许引用自己，那是「人物参考 {{slot:hero}}」的推荐写法。）

26. **可选槽位只能被框选**（2026-11-27）：正文里**单个引用**某个可选槽位
    （`{{Mixed N}}` / `{{slot:key}}`，无修饰符）的地方**最多一处**，且那一处必须
    是作者框选出来的那一段（`empty_text_from_anchor` 为真）。
    **两段提示词各算各的**（主提示词 / 随机档提示词）—— 随机档是另一段话，它的
    插入点与主提示词里的互不相干。
    - 为什么：那一处是它的**插入点**（填了素材插编号，没填插 `empty_text`），
      而 `empty_text` 按设计就是正文里框选出来的那段。多出来的一处（粘贴进来的）
      让「打开草稿时还原哪一段」变成猜 → 作者原话被顶掉。
    - **整组引用 / 第 N 张引用不在这条规则里**：它们不是插入点，不碰兜底文案。
    - 判据只有两处：后端 `rules.py::validate_optional_slot_refs`、
      前端 `template-specs/defaultText.ts::optionalSlotRefError`。
    - 老数据没有标记 → 预检红（消息里带上原来那句），强制作者重新框选一次。

27. **引用不带修饰符**（2026-11-27）：槽位引用只有**单个引用**一种写法
    （`{{Mixed N}}` / `{{slot:key}}`）。「整组」（`*`）与「第 N 张」（`.N`）在
    一槽一素材下不存在，结构校验直接拒 —— 判据落在**引用 token 的修饰符**上，
    正文里普通的乘号与小数点不受影响。
    判据两处同口径：后端 `rules.py::_validate_ref_modifier`、
    前端 `specDraft.ts::promptRefError`（作者粘贴时当场拒）。

## 13. 开放问题（实施时再定，不阻塞 P1）

1. **模型能力声明不足**：`ModelSpec` 现在只有 `max_references`，分不出「接受几张图 / 几段音频 / 几支视频」。`attachment` 槽位（音频）到底能不能交，目前只能靠驱动自己 400。P2 前建议给 `ModelSpec` 加 `accepts: frozenset[str]`（`image/video/audio/text`）与分类型上限，`compile` 用它做受理前校验。
2. **槽位指向资产库封装**（`source: "pack"`）：**进 P1**（原先以"要扩资产库模型"为由推迟，被 §1.1 判据否决）。
   事实核查：`library_pack_items` 已有 `position` / `role` / `description`；成员允许
   `image / video / audio / text`（只禁嵌套 `pack`）；`LibraryLookup.expand_packs()` 已能按
   `position` 有序返回带 `role` 与 `readable` 的成员，且契约写明"顺序即槽位，调用方不得重排"。
   `compile` 只需调用它，不需要给资产库加任何字段。
3. **`attributes` 归一**：旧 `supportedScopes`、`wardrobeMode` 统一放进 `spec.attributes`（`dict[str, str]`），避免每收编一个概念就加一列。键名先定 `scope` / `wardrobe`，其余按需加。
4. **`compile` 的缓存**：入参 `(version, slotValues)` 是纯输入，可加一层进程内 LRU；但先不上，等有性能证据。
5. **提示词上限两处不一致** —— **已定（2026-11-14）**：两个数不是一个东西，别合并。
   - `MAX_PROMPT = 20000` 是**编写**上限（草稿能写多长），沿用旧 manifest 口径；
   - `EXECUTION_PROMPT_LIMIT = 7000` 是**执行**上限，即 `CreateTaskIn.prompt` 的
     `max_length`，放在 `core/template_spec`。（2026-11-16 从 2000 放宽到 7000：
     多段描述 + 槽位引用的真实模板轻松过 2000，而百炼驱动本身允许 20000。）
   判据分三处：保存草稿**不判**（`validate_draft(executable=False)`，否则旧模板里
   2 万字级别的提示词连草稿都存不进来，P3 迁移会被一刀切）；预检与发布按两段原文之和
   **粗判**（运营正看着屏幕，这里说清最省事）；`compile` 按**展开后的成品**精判
   （`{{slot:key*}}` 一次可能多出几十字）。漂移由
   `test_execution_prompt_limit_matches_task_schema` 钉住 —— 它直接读 `CreateTaskIn`
   的 `MaxLen`，改哪边都会先红。
   等第二个执行端点进来，这个数应随**该能力**声明（届时按模型取），而不是继续全局一个。
6. **历史替换档案的归宿** —— **已定（2026-11-14，用户拍板「直接删」）**：`replacement_runs`
   / `_run_inputs` / `_reviews` 随替换链一起删表，不导出、不留只读视图。理由：那批行记的是
   旧链路的中间态（`prompt_sha256`、归档工作区指针、渠道快照），形状与 `tasks` 不对应，
   迁不成新记录；留一份只读视图反而让人以为旧链路还活着。开发库 49 行历史记录随之消失，
   升级前的 `pg_dump` 备份是唯一回溯途径。见 §11.3。
