## 一句话

能同时**打开页面用**的人很多（局域网 50–100 在线不是问题）；能同时**提交任务**的人
也不少（交接是秒级的，2 个槽位每分钟能处理好几条）。**真正的等待发生在上游出片**，
那里不占本机任何资源 —— 所以「能挂多少条任务」看的是 LibTV 账号与额度，不是槽位数。

## 1. 三个硬上限

| 层 | 上限 | 依据 |
|---|---|---|
| 页面 / 接口 | 单进程 uvicorn + 数据库连接 30 | `api/src/core/config.py:119-120`（`DB_POOL_SIZE=10` + 溢出 20，池等待 5s） |
| 后台任务 | **2 个槽位**，所有 job 共用 | `config.py:256`（`WORKER_CONCURRENCY=2`）；`api/src/workers.py` 的 `Worker._loop` 起 N 个协程 |
| LibTV 交接 | 每个账号同一时刻只允许 **1 条在上传/提交**；不限制上游并行排队 | `api/src/modules/model_driver/libtv/process.py:59`（`ACCOUNT_STAGES={upload,submit}`）+ `account_lock_name()` 按 `host-port` 分锁 |

2 个槽位是**所有** job 的总量：`generation.submit` / `generation.poll` /
`libtv.download` / `export.build` / `library.download.build` 全排这两条队。
百炼（`bailian-wan3-*`）没有账号锁，只受槽位限制；`libtv-wan3-replacement` 两层都受。

> 这三项都是**本机**的硬上限，不是「同时能跑几条生成」。一条任务在等出片时
> 既不占槽位、也不占账号锁（见 §1.1），所以「能同时挂多少条」由上游决定。

### 1.1 槽位**只在「握手段」被占用**

一条任务从头到尾并不一直占着槽位。占的只是交接的那几下：

| 阶段 | 占槽位多久 | 依据 |
|---|---|---|
| 上传素材 | 秒级（≤30s，超时上限 1500s） | `STAGES["upload"]` |
| 提交下单 | 秒级（≤30s，超时上限 100s） | `STAGES["submit"]` |
| **等模型出片（几分钟）** | **不占** | 只有一个短 poll job，查一次就放回队列 |
| 下载成片 | 秒级（≤30s，超时上限 240s） | `STAGES["download"]` |

也就是**一条任务大约占 1 分钟槽位时间**，其余几分钟是在等上游。
`generation.poll` 是独立 job，按 `GENERATION_POLL_INTERVAL_SEC=2`（LibTV 声明
5 秒、上游排队中退避到 15 秒）投一跳，每跳只占「问一次供应商」那几十毫秒。

> 2026-11-22 修正：本文档初版把 `STAGES` 里的**超时上限**当成了实际耗时，
> 于是写成「一条任务占 5–8 分钟槽位、2–3 个人就排满」。实际交接是秒级，
> 那段结论已按此重写。超时上限只在异常路径上生效（见 §3）。

## 2. 具体能扛多少

### 2.1 只用页面（挑模板、填素材、逛资产库）

- 局域网 **50–100 人同时在线**不会有明显问题（估）。每人每秒不到 1 个请求，
  单进程异步 + 30 个连接够用。
- 唯一体感瓶颈：静态资源由 uvicorn 发且**没有 gzip**（`WEB_DIST_DIR` 那套），
  一个页面首次加载约 500KB。100 人同时打开会明显变慢，但不会挂。
- 大文件上传/预览走 API + 预签名，会占连接与线程池，不占 worker 槽位。

### 2.2 同时点「生成」

**没有人会因为「槽位被占」而排队**：2 个槽位每分钟能交接 2–4 条任务，而交接只有
几十秒。真正让人等的是**上游**（见 §2.3），并且那段等待对双方都是「排队中」。

| 同时提交 | 实际发生什么 |
|---|---|
| 1–2 人 | 提交立刻被接走，秒级交接完 |
| 3–5 人 | 交接彼此错开几秒到几十秒，之后都在等上游出片 |
| 更多人 | 只有**同一 LibTV 账号**的上传/提交会串行（一次一条），其余仍并行等待 |

账号被占**不会直接失败**：`EXECUTOR_BUSY` 在 `api/src/modules/model_driver/drivers/libtv.py`
里被翻译成 `RateLimited`，框架按 `GENERATION_THROTTLE_DELAYS=10,20,30,60,90,120,180,240`
（`config.py:442`）重新排队，任务保持 queued。**8 次退避累计约 12.5 分钟**，
超过才报失败 —— 这是「交接排队最多等多久」的上限，不是出片时间。

### 2.3 吞吐：卡在上游，不在本机

本机这侧几乎不是瓶颈：交接是秒级，2 个槽位每分钟能处理好几条。真正决定「一小时出
多少片」的是**上游出片速度 × 能同时挂多少条**：

```
每小时条数 ≈ 可同时处理的条数 × 3600 / 单条出片秒数
```

- LibTV：一个账号能挂多少条、排多久，看 `app libtv-account` 的排队位次与额度；
  我们只串行它的**上传/提交**（`ACCOUNT_STAGES`），防撞风控，不限制上游并行度。
- 百炼：按它的配额，本机只受 2 个槽位的交接能力限制。
- 所以「2 个账号」并不等于「同时只能出 2 条」——**别拿槽位数当并发上限**。

**本机唯一会随规模变化的是 poll 负载**：在途 N 条、间隔 T 秒 → 每秒 N/T 条短 job。
单跳是轻量 HTTP 查询（几十毫秒级），在途二三十条时占不到一个槽位的零头；
在途上百条才会开始挤占交接。`TASK_MAX_IN_FLIGHT_PER_USER=5` 正是压这个值，
同时也是为了让共享账号的排队位次不被一个人占满。

生图侧另有一条同类上限（`IMAGE_MAX_IN_FLIGHT_PER_USER=5`，2026-11-23 加），
但**它压的不是 poll**：生图默认走 Agnes 且是**同步**提交（`submit` 直接返回
终态、框架不轮询），不产生 poll 短 job、也不占本机槽位。它防的是一个人
占满**上游供应商账号**的排队位次。两条上限**分开计数**是有意的：默认组合
（视频 LibTV / 生图 Agnes）本来就不共用同一个上游资源，合并计数只会误伤
「同时做视频和生图」的正常用户。

## 3. 风险清单

| 风险 | 现状 | 处置 |
|---|---|---|
| 一个人连点几十条占满上游位次 | **已处理**（2026-11-22）：`TASK_MAX_IN_FLIGHT_PER_USER=5`，判据 queued + running | `service._assert_in_flight_room()`，create 与 retry 两处都拦，超限 429 并说清上限与在途数。压的是**共享账号的排队位次**与 poll 频率，不是槽位 |
| 生图同样能刷队列 | **已处理**（2026-11-23，T37）：`IMAGE_MAX_IN_FLIGHT_PER_USER=5`，判据 queued + running | `image/service.py::_assert_in_flight_room()`，`generate` 与 `retry` 两处都拦，超限 429 并说清上限与在途数。压的是**共享供应商账号的上游排队位次**——生图默认走 Agnes 且是**同步**提交（submit 直接返回终态、框架不轮询），所以它不产生 poll 负载、也不占本机槽位，限它防的是「一个人占满上游位次」 |
| 全局限流关闭 | `RATE_LIMIT_GLOBAL_PER_MIN=0`（按 IP，`middleware.py`） | 内网默认不开；对外暴露前必须开，否则脚本刷接口没有兜底 |
| 一个卡住的上传吃掉一半交接能力 | **异常路径**：上传超时 1500s（25 分钟），期间占着 1 个槽位 + 该账号的锁 | 出现时按 `run/records/executor-*.json` 定位；降 `STAGES["upload"]` 要权衡大素材 |
| 单实例 | `QUEUE_DRIVER=db` + `LEADER_ELECTOR=backend` | 多副本见 README §8；注意**每个副本都会各起 2 个 worker**，副本翻倍不等于槽位翻倍 |

## 4. 怎么量（别靠体感，也别靠上面的推算）

1. `app doctor --strict` 里 `runtime.queue` 一行直接给在途条数与死信：
   `在途 N 条（pending x / running y），死信 z 条`。
2. `/metrics`（生产要带 `METRICS_TOKEN`）：
   - `worker_jobs_in_flight` —— 长期等于并发数，说明要么真忙、要么有 handler 卡死；
   - `worker_consumers{state="alive"|"desired"}` —— 两者不等说明有协程悄悄退出了。
3. 出片速度：`app libtv-account` 看排队位次与额度；任务列表里 `queued → running → completed`
   的时间差就是端到端耗时，交接那几秒忽略。
4. 压测：5 个人同时提交同一个模板，重点看**任务在 queued 停留多久、429 有几次**，
   而不是看槽位占用 —— 槽位占用在正常情况下本来就是断断续续的。

## 5. 想扩，方向要对

- **调大 `WORKER_CONCURRENCY` 只提高「交接能力」，不影响出片速度**：出片在上游，
  本机只是秒级交接。它有用在两种场景：一群人同时上传/下载素材、批量导出。
  代价是同一 LibTV 账号的上传/提交抢锁更频繁（抢不到就 `RateLimited` 重排）。
- **想多挂任务、更快出片 = 加 LibTV 账号**：上游队列与额度是按账号算的，
  起第三个 CDP 浏览器（9413）加进 `LIBTV_BROWSER_URLS` 即可，账号锁按 `host-port`
  自动分开，不用改代码。百炼那条路看它的配额。
- **扩 API = 多副本**（README §8），但每个副本各起 worker，且 `CACHE_DRIVER` 只有
  memory，多副本时限流会变成 N 倍。
- **人多时页面慢**：换 nginx 发静态（README §3 的 B 方案）拿 gzip，或者上 CDN ——
  但内网这点量不值得。

## 6. 这次改了什么

- `TASK_MAX_IN_FLIGHT_PER_USER`（默认 5，`0` = 关）：create 与 retry 都过
  `service._assert_in_flight_room()`，超限 429。它压的是**共享账号的排队位次与
  poll 频率**（不是槽位 —— 等出片本来就不占槽位）。用例在
  `api/tests/test_task_in_flight_cap.py`（含「重试同样受限」与「一条跑完就释放」）。
- 测试环境把它置 0（`tests/conftest.py`）：套件里有大量「连造十几条任务」的场景，
  限着会让它们莫名 429。这道闸门由上面那个文件自己调小后测。
