# 资产库改造设计（v2）

日期：2026-11-09
对象：`/assets` 素材库（后端 `api/src/modules/asset/`，前端 `studio/src/features/archive-library/`）
性质：结构与交互设计。**本文不写代码**，只描述数据形状、判定规则、请求划分与界面分层。
相关文档：`ASSETS_REQUIREMENTS.md`（现状与业务规则基线）、`ARCHITECTURE.md`（模块装配约定）。

## 0. 现状基线（改造的起点）

当前是**一张扁平表**：`assets` 里有 `category`（枚举字符串：source / character / product / scene / audio）、`type`（image / video / audio）、`shared`（布尔）、`owner_id`、`deleted_at`、`state_version`。没有标签、没有分类实体、没有团队实体、没有生成配方、没有向量。

**范围约定（已确认）**：素材库**不做"项目"维度**。项目就是任务，任务中心已经承担"某任务用了哪些素材、产出了什么"的视图。素材库只按「库 / 用途分类 / 标签 / 媒体类型」组织，与任务的关联靠引用记录，不靠分类。

这意味着本次不是"加几个字段"，而是换骨架。三个旧东西必须处理掉：

| 旧结构 | 问题 | 去向 |
| --- | --- | --- |
| `category` 五值枚举 | 分类是硬编码常量，用户建不了自己的用途分类；且它同时承担"业务类型"和"目录"两种语义 | 拆成「一级分类（可配置、单值）」+「媒体类型（系统判定）」 |
| `shared` 布尔 | 只有"私有 / 公开"两档，公共库里谁都能改，无审批无审计 | 拆成「可见域 visibility」+「提升审批记录」 |
| 字节与记录同表 | 一条记录 = 一份文件，"复制到另一个库"只能复制字节或共享同一行 | 拆成 `blob`（字节事实）+ `asset`（一次归属） |
| 没有团队实体 | "团队共享库"无处落地，只能退化成全员公开 | 新建 `team` 与成员关系（首批：内容 / 运营 / 技术） |

## 2. 一、数据模型

### 2.1 三类资产：两个正交字段，不是一个 kind

用户看到的"三类资产"其实是**两个独立问题叠加**的结果，必须拆成两列：

| 字段 | 取值 | 谁能改 |
| --- | --- | --- |
| `origin` | `upload`（上传/登记） / `generate`（AI 产出） | **不可改**。这是事实，不是状态 |
| `stage` | `candidate`（候选，未确认） / `adopted`（已采纳） / `discarded`（已弃用） | 只能由"采纳 / 弃用 / 回收"三个动作改 |

三类资产 = 两列的取值组合：

| 用户看到的类型 | origin | stage | 说明 |
| --- | --- | --- | --- |
| 输入型（原料） | upload | adopted | 上传动作本身就是"我要了"，无需二次确认 |
| 中间态（草稿/变体/废片） | generate | candidate / discarded | **AI 产物出生即候选**，还没被任何人认领 |
| 生成型（AI 素材） | generate | adopted | 用户确认之后才转正 |

**为什么不能用一个 `kind` 列**：`kind` 会同时编码"字节是怎么来的"和"人要不要它"，而这两件事的变更方向相反——来源永不变，采纳会变。混在一列就会出现两难：用户点"采纳"就要改 `kind`，一改，"这条是 AI 产出的"这个事实就丢了；若 `kind` 不动，候选和生成型又区分不开，只能再加一列状态——那就还是两列，只是多了一个已废弃的 `kind`。

拆开之后每列都有单一职责：`origin` 用于生成内容标识、审核口径、用量归因（AI 产物与实拍原片的合规义务不同）；`stage` 用于可见性、配额、过期与检索召回。

三类同表的理由不变：差别不在字段集合，而在**生命周期与可信度**——原料与成品要长期可读、要能进公共库；候选是过程物，留着是成本。一张表 + 两列，列表、检索、权限、计数共用一套代码；拆三张表会让"全部素材"变成三次查询合并、分页错乱、标签要建三套关联。

代价是候选行里有很多空列。这个代价用三条纪律换回来：

1. **`origin` 由写入路径决定，不接受客户端传值。** 否则 AI 产物可以被伪装成上传原片，绕开生成内容标识。
2. **`stage` 只有三个动作能改**（采纳 / 弃用 / 回收），没有"编辑"入口。
3. **列表、检索、计数、导出一律走同一个可见性谓词**（默认只放行 `adopted` 且未删除），不在各处手写 where。**为什么**：这个仓库已经踩过一次同类坑——查询里漏掉一个过滤条件，症状是"数据写进去了，列表里看不见"，而没有任何报错。谓词收在一处，才能被一条测试盯住。

### 2.2 字节与记录分离：`blob` + `asset`

| 实体 | 承载 | 关键约束 |
| --- | --- | --- |
| `blob` | 实际字节：`sha256`、`size`、`mime`、`storage_key`、`tier`（original/draft/final）、`ref_count`、`expires_at` | `sha256` 全局唯一；`ref_count=0` 且过保留期才允许物理删 |
| `asset` | 一次归属：名称、分类、可见域、媒体类型、标签、recipe 指针、软删 | 归属/可见性/命名全部在这一层 |

**为什么这样设计**：改造要支持三件旧模型做不到的事——「同一文件复制到另一个库」「模板引用不下载再上传」「草稿过期不影响成品复现」。这三件事的共同前提是"同一份字节可以有多条记录"。字节绑在记录上时，复制只能复制字节（配额翻倍）或共用一个 ID（改一处全变）；引用只能靠 URL（换桶即失效）；过期只能砍记录（血缘断掉）。

这条也顺手修掉现有的一处别扭：现在的去重索引是 `(owner_id, sha256, category)`，本质是在用"记录级唯一"模拟"字节级唯一"，所以必须带上 category 才不会误伤，结果同一个人在不同分类传同一个文件仍然会存两份字节。改成 blob 后，唯一性回到它该在的层级。

`tier` 是**派生值**，不是独立状态：由引用这个 blob 的所有 asset 里最高的 `stage` 决定（有 `adopted` → `final`，只有 `candidate`/`discarded` → `draft`，`origin=upload` → `original`）。**为什么这样定**：采纳一张 AI 产物不该触发字节搬迁（几十 MB 的视频挪一次桶就是一次失败点）；改一个派生值，字节原地不动，过期时间随之清空。同一份字节被多条 asset 引用时，也不会出现"一处是草稿桶、一处是成品桶"的矛盾。

### 2.3 生成配方：独立实体，不可变，可被共享

配方字段（生成型素材必须完整，缺一项即为"配方不完整"，不允许提交到团队库）：

| 组 | 字段 | 备注 |
| --- | --- | --- |
| 模型 | `model_key`、`model_version`、`provider` | 版本必须记实际调用的版本，不是"最新" |
| 提示词 | `prompt`（全文，不截断）、`negative_prompt`、`prompt_language` | 全文入库存 Text，列表出参只给摘要 |
| 参考 | 关联表：`referenced_asset_id`、`role`（参考图/首帧/尾帧/风格/蒙版）、`order` | 见下方"为什么不存 JSON 数组" |
| 参数 | `params`（结构化 JSON：尺寸/步数/CFG/时长/帧率/宽高比） | 键名走白名单，未识别键保留但不参与筛选 |
| 种子 | `seed`（**实际生效值**）、`seed_requested`（用户提交值） | 随机种子时两者不同，复现要靠前者 |
| 时间与人 | `generated_at`、`operator_id`、`request_id` | `request_id` 用于对上供应商工单 |
| 血缘 | `parent_recipe_id` | 衍生链，可为空 |
| 来源 | `template_id`、`template_version`、`subject_version` | 由「模板 × 主体」产出的必须记，否则回答不了"这批成片是哪套流程、哪个版本的产品图产的" |
| 标识 | `content_label`（AIGC 标识：是/否 + 标识版本 + 生成方） | 已确认**仅元数据留痕**，画面上不加可见水印；导出时把标识写进文件的元数据字段 |
| 成本 | `cost_units` / `cost_note` | 可选，用于用量对账 |

**为什么配方是独立实体而不是 asset 的一堆列**：一条素材可能被复制到三个库（3 条 asset），但它们说的是**同一次生成事件**。配方是事实，归属是视角；事实存一份，视角存三份。若把配方拍平进 asset，复制就变成"复制一份配方"，之后有人补录了原件的配方字段，三份副本会开始互相矛盾——血缘一旦分叉就不再是证据。

**为什么参考图走关联表而不是 JSON 数组**：这张设计里有两个反查必须走索引——"这张图被哪些生成用过"（删除保护、血缘展示、衍生推荐）和"这个提示词模板产出了哪些结果"。JSON 数组只能正查，反查要全表扫。同时关联表能挂 `role` 与顺序，这是"用作首帧"和"用作风格参考"的区别所在。

**为什么配方只允许插入、不允许原地改**：配方是合规与复现依据。允许编辑就等于允许事后修改"当时用了什么模型、写了什么提示词"，那它连审计价值都没有了。需要修正时补录新版本（`supersedes`），旧的保留并标注"已修正"。

### 2.4 归属规则

规则只有四条，且都落在数据库约束上，不靠约定：

1. **每条素材恰好属于一个一级分类**。`category_id` 非空，创建时未选则落到系统分类「未分类收件箱」（`is_system=true`，不可删不可改名）。
2. **每条素材可打多个标签**，标签全部来自受控词表（见 §3.3）。
3. **写边界是分类，读边界是库**。即：你能看到哪些素材由可见域（个人/团队/公共）决定；你能改哪些素材由"分类是否在当前库 + 可见域"共同决定。
4. **素材不按任务（项目）归类**。素材与任务的关系写在**引用记录**里（`recipe.task_id`、`asset_ref`），是"用过"的事实，不是"属于"的归属。一条素材可以被 20 个任务用过而不改变它的分类。

**为什么用系统分类而不是 `category_id = NULL`**："只属于一个"是一条强不变量。用 NULL 表达"未分类"会让它退化成"零个或一个"，于是每个计数、每次移动、每条唯一性判断都要多一个分支；而"未分类"恰恰是最高频的入口（用户上传后不选分类），分支会出现在最热的路径上。落成一条真实记录后，角标计数、批量移动、拖拽落点全部和其他分类一致。

**为什么素材不按任务归类**：任务是有生命周期的过程物，素材是可长期复用的资产。按任务归类会让同一张产品图在"每个任务都有一份"，一年后库里 90% 是重复项；而且任务关闭后素材就"挂在一个已结束的容器里"，跨任务复用无路可走。任务中心需要的是"这个任务用了哪几张图"——那是引用，查一次关联即可，不需要反过来污染素材的组织结构。

**为什么写边界绑分类、读边界绑库**：如果读也被分类绑死，用户在"全部素材"里看不到别的分类里的可用素材，跨库复用就退化成"先知道 ID 再搜"；如果写只绑库，用户能在不属于自己的分类里改名、移动、删除，分类就失去组织意义。这一条不对称是刻意的，实现时最容易写成对称的。

### 2.5 跨边界取用：显式复制

先划清一件事：**"取用"与"发布"是两个方向，规则不同。**

| 方向 | 例子 | 是否需要审核 |
| --- | --- | --- |
| **取用**（往下拿） | 公共库 → 我的个人库；团队库 → 我的个人库 | 不需要。我本来就能看，拿一份自己用 |
| **发布**（往上递） | 个人库 → 某团队库；团队库 → 公共库 | 需要。见 §6.2 |

本节只讲**取用**：数据动作是复制，且必须显式确认。场景有两种——**跨库**（往下拿一层）与**跨分类**（同一库内换目录）。数据上它们是同一件事：改变归属，不改变字节。

| 项 | 复制后 |
| --- | --- |
| 新 asset | 新建一行，`copied_from = 源 asset id`，`category = 目标分类`，`owner = 操作人`，`visibility = 目标库` |
| 字节 | **不复制**。`blob.ref_count + 1`，两条记录指向同一 `sha256` |
| 配方 | **不复制**。`recipe_id` 指向同一条（配方不可变，天然可共享） |
| 标签 | 默认跟随，确认弹层里可取消；取消后新素材不带标签 |
| 血缘 | 带。`copied_from` 同时是"这条素材的来历"，详情页可跳回源头 |
| 可见域 | **只降不升**：重置为操作人所在库的默认值，不继承源素材的公开状态 |
| 任务引用 | 不跟随。旧任务仍指向源素材，新副本不被任何历史任务引用 |

**为什么复制不复制字节**：复制字节会让配额和存储成本随库数线性膨胀，而"复制"在业务上想要的是"这条素材现在归我、归这个库"，不是"再存一份"。共享 blob 还让删除变安全：任一侧删除只减引用，字节在全部引用消失后才回收。

**为什么可见域只降不升**：源素材在公共库是公开的，复制到私库后如果继承"公开"，等于绕开了一次发布审核。复制是"取用"，不是"再发布"。反过来，同一个复制动作一旦方向朝上（提交进团队库），它就不再是取用而是发布，必须走审核——这就是 §6.2 存在的原因，也是这两个方向不能用同一套规则的理由。

**为什么任务引用不跟随**：任务中心要回答的是"当时用的是哪一张"。如果复制后把旧引用改指新副本，历史任务的血缘会指向一条当时还不存在的记录，成片的配方解释当场失效。

**为什么必须有 `copied_from` 而不是靠文件名/哈希猜**：哈希相同只能说明"同一份字节"，不能说明"是复制来的还是各自上传的"。前者要展示血缘、要做批量清理，后者不能合并。用哈希推断会把两个不相关用户的相同素材误连成一条谱系。

### 2.6 成组资产：主体（Subject）

一个产品有正面、背面、细节、场景、透明底五张图；一个角色有面部、半身、全身、侧面八个角度。它们不是五条可以互相替代的素材，而是**同一个东西的几个视角**——单条 asset 表达不了"这五张属于同一个产品"，五条散 asset 又表达不了"它们是同一个产品"。

不新造概念：现有的 `PackDraft / PublishedPack` 已经是这个形状（1–10 张图 + 主图 + 固定参数 + 发布版本）。改造要做的是把「包」从模板模块的私有子结构**提升为素材库的一等实体**，并补上它现在没有的三样：成员角色、跨主体共享、检索聚合。

#### 2.6.1 为什么组不能是一条 asset

| 候选方案 | 会在哪崩 |
| --- | --- |
| 组也是一条 asset（`kind=group`，父指向子） | 组没有字节、没有媒体类型、没有尺寸时长，列表/网格/权限/检索/导出每个入口都要加 `if kind==group` 分支；且"组的主图"指向自己的成员，形成环 |
| 用 collection / album 弱聚合 | 只是一份列表，承载不了"固定属性、版本、发布范围、作为整体被模板调用"——而产品/人物恰恰要作为整体被调用 |
| 主体是独立实体，成员是 asset | 生命周期分离：主体可以整套换图而不改 ID；同一素材可以同时是多个主体的成员 |

选第三种。

#### 2.6.2 形状

```
subject（主体 / 资产组）
├─ subject_type     product | character | scene | prop
├─ category_id      一级分类（与素材同一套分类）
├─ visibility       个人 / 团队 / 公共
├─ requires         主体对外承诺的能力中，必须全体成员都给的（见 2.6.7）
├─ attributes       按 subject_type 定 schema 的固定属性（3–6 个，不是万能 JSON）
├─ cover_asset_id   必须是成员之一
├─ status           draft | published | archived
└─ current_version ──► subject_version

subject_member      唯一约束 (subject_id, asset_id)
├─ role            正面/背面/侧面/细节/透明底/场景/转台…
├─ grants          该成员授予的能力子集（generate / download / derive）
├─ sort_order
└─ added_by / added_at

subject_version（不可变的发布快照）
├─ version_no、members_snapshot（每条含 asset_id + sha256）、
│  cover_asset_id、attributes_snapshot
└─ published_by / published_at / note
```

- **成员仍是完整素材**：有自己的 owner、分类、可见域、标签、配方。所以它既能被主体引用，也能独立出现在检索与网格里。
- `(subject_id, asset_id)` 唯一只限制"同一组内不重复"，**不限制跨组**：一张场景图可以同时是产品 A 的主图与产品 B 的场景图，不需要重复上传。
- 规模 **1–20 张**；允许 1 张（单图也能成为主体，不该逼用户凑数上传垃圾图）；超过 20 张说明这是序列资产（转台 36 帧），应当作为视频/3D 处理，不进主体。
- 角色是**受控词表**，按 `subject_type` 分组（产品：主图/正面/背面/细节/包装/场景/透明底；人物：面部/半身/全身/表情/服装细节/侧面）。理由同 §3.3：自由填写的角色词表在三个月后会同时出现"正面图""正面""正视图"三种写法。
- `attributes` 不是 JSON 垃圾桶：每个 `subject_type` 定 3–6 个字段（品牌、型号、颜色、材质、适用场景）。**为什么**：属性一旦可以随便加，就无法用于精确筛选与模板自动填充，最后退化成一个没人看的备注栏。

#### 2.6.3 三条铁律

**① 组装关系不是包含关系。** 删主体不删成员；删（软删）成员让主体进入"缺图"状态——阻止新的发布与调用，但历史版本仍可追溯。

> 为什么：成员是用户的独立资产，可能被别的组、别的库用着。"删组"在用户心里是"我不再用这个产品了"，不是"把这些图也一起删掉"。反过来，级联删除会立刻造成跨主体的连锁破坏，而且不可逆。

**② 权限以主体为授权单位，下载以素材为单位。** 调用主体做生成时只校验主体的可见域；但用户不会因为"这个产品是公开的"就获得五张参考图的高分辨率原件下载权（除非成员素材本身对他可见）。

> 为什么：参考原片常常是未修图的、含真人肖像、无商用授权的。随主体公开等于一次性公开全部素材，撤回成本极高。而"生成时服务端要读"和"人能不能下载"本来就是两件事——混起来的症状是"素材库变成原片泄露渠道"。

**③ 主体是权限天花板，不是地板。** 成员不因为被组装进主体而获得任何额外授权；主体的对外承诺，必须以成员实际能给的为限。发布前校验两条：**能力可达**（主体声明的能力，每一项都要被成员覆盖）与**角色可达**（每个必需角色至少有一个已采纳成员）。

> 为什么替换掉"强制把成员可见域提升到主体可见域"那一版：那一版看起来最省事——发布时一次性把成员拉到与主体同档，运行时只判主体，规则只剩一条。但它付出的代价是**发布动作会批量改写成员的权限**：一个含真人肖像、无商用授权的参考原片，因为被放进了一个要发布到公共库的产品组，就被连带公开了。而权限变更本应是逐条、可审、可拒的动作，不该是"组装"的副作用。更直接的后果是**角色分层被压平**：可见域只有三档，一旦要求全体同档，"主图可下载、参考图仅可读"这类分层就没有地方表达，最后只能靠特例代码兜。
>
> 反过来的口径（成员权限不高于主体、主体不承诺成员给不出的能力）不要求任何人改权限，只在发布时做一次**集合校验**：能过就发布，过不了就明确告诉专员"缺哪一项、缺在哪个成员"。代价是主体可能被某个保守成员拖低一档能力——这个代价可见、可解释、可由专员自行移除该成员来解决，比"悄悄公开一批原片"小得多。具体形式化见 §2.6.4。

#### 2.6.4 能力模型：可见域与能力是两件事

原方案把两件事压在一个枚举上——"能不能发现这个主体"和"能拿它的成员做什么"都靠 `visibility` 三档表达。压在一起就没有地方写"这个产品可以被所有人调用，但参考原片谁都不能下载"，于是只能靠"全体同档"来回避问题，这正是铁律③被推翻的原因。

拆开后是两个互相独立的问题：

| 概念 | 回答什么 | 取值 | 判定单位 |
| --- | --- | --- | --- |
| 可见域 `visibility` | 这个主体能不能出现在我的库里 | 个人 / 团队 / 公共（单值） | 主体 |
| 能力 `capability` | 我对它的成员字节能做什么 | 五档（见下），其中三项可授予 | 分两级：全体 / 逐成员 |

**五档能力，两种判定粒度：**

| 能力 | 语义 | 判定粒度 | 缺了会怎样 |
| --- | --- | --- | --- |
| `discover` | 主体出现在列表、可被搜到 | 主体（由可见域推导） | 看不见 |
| `preview` | 能看低清预览、能看成员缩略图 | 主体（跟随可见域） | 卡片显示占位 |
| `generate` | 服务端生成时可读成员字节 | **全体成员必须给** | 主体不可用于生成 |
| `download` / `derive` | 可下载成员原件 / 可基于成员衍生 | **逐成员判定** | 该成员降级为"仅预览" |

`subject_member.grants` 记录成员授予的能力子集——只有 `generate` / `download` / `derive` 三项可授予，`discover` / `preview` 由可见域推导、不进 `grants`。`subject_member.in_output` 标记它是否参与成品输出（默认真）。`subject.requires` 记录"必须全体成员满足"的能力，默认只有 `generate`。

**发布校验三条，缺一即不可发布：**

1. **角色可达**：`∀ role ∈ required_roles，∃ 成员 m：m.role = role ∧ m.stage = adopted`。
2. **能力可达**：`requires ⊆ ⋂ grants`（对 `in_output=true` 的成员取交集）。主体承诺的每一项，所有参与者都要给。
3. **不放大成员可见性**：`preview` / `download` 对某人生效的前提是，他本来就能看到这条成员素材；主体可见域只决定"主体能不能被找到"，不扩大任何成员自身的可视范围。`generate` 是唯一的例外——它由服务端代行、不向人展示原始字节，因此可以读一个访问者自己看不到的成员。**这条例外必须写进代码注释**，否则后来的人会把它当成越权漏洞"修掉"，而那些主体正是靠它才能成立的（如公开产品里含一张未授权原片）。

**为什么 `requires` 默认只有 `generate`，而 `download` 走逐成员：** 生成必须读全部成员的字节，少一张就产不出正确结果，这条天然是"全体"，不给就是主体不可用。而"能不能下载原件"是人的动作，天然可以一张一张判——混成一条整体能力，就会出现"一张无授权原片把整个产品拖成不可用"，专员只能删图或违规提权，两个都是坏结果。

**为什么取交集而不是并集：** 若主体能力 = 成员能力的并集，只要有一个成员允许下载，整个主体就可下载——"公开一个产品"立刻等于"公开它全部参考原片"，正是铁律②要防的事。交集（木桶最短边）是唯一不会放大的算法。

**木桶效应的三个出口**（代价必须可见，否则专员会绕过去）：

| 出口 | 做法 | 适用 |
| --- | --- | --- |
| 排除出输出 | 把该成员 `in_output` 置假（仅作视觉参考，不参与成品），它就不再压 `download` | 风格参考图、构图示意 |
| 接受降级 | 主体照常发布，卡片明示"仅可生成，原件不可下载" | 内部参考专用主体 |
| 移出主体 | 该图不进主体，改为模板参考位的 live 引用（§5.1） | 只在流程里用、不该被当素材取用 |

**角色带默认授权，成员可降不可升**：角色词表每一项带一组默认 `grants`（主图默认含 `download`，参考/无授权原片默认只有 `generate`），成员加入时按角色初始化。单个成员可以往下调（收紧天然安全），往上调需管理员操作并留审计——**为什么**：如果组装时能随手把参考图提成"可下载"，那么角色分层在第二次使用时就会退化回"全都可下载"，这次改造等于没做。

#### 2.6.5 检索与展示按主体聚合

| 场景 | 行为 |
| --- | --- |
| 语义检索 | 成员向量**取 max** 聚合到主体，不取平均；命中时标注"命中：侧面-02"，可点开看那一张 |
| 精确检索 | 文件名命中成员时，结果仍聚合到主体并标注"命中：正面.jpg"，避免用户以为搜错了 |
| 网格 | 默认"按主体合并"：组内成员折叠为一张**堆叠卡**（三层错位 4px，右上"N 张"），hover 扇出最多 5 张预览；控制条可切换为"按素材平铺" |
| 详情 | 主体浮层内以横向条带展示全部成员，可滑动、可设封面、可移除（移除即断关系，不删素材） |

> **为什么取 max 不取平均**：正面与背面的平均向量是一个"不存在的视角"，检索质量会莫名其妙地差，而且没人能定位原因。取 max 的语义是"任一张像就算命中"，与人找东西的方式一致。
>
> **为什么默认合并**：库里 60% 的图会变成组内成员，不合并等于用五张同款图淹没浏览。"我要找那张特定角度的图"这个需求由平铺模式和详情条带承接，不需要在默认视图里牺牲浏览效率。

#### 2.6.6 分类、版本与提升

- 主体有自己的 `category_id`；成员默认继承主体分类，但**保留自己的归属**（被共享的成员可能属于另一个分类）。
- 移动主体到另一分类时，确认层默认勾选"同时移动成员"，被其他主体共用的成员置灰并注明"被 N 个主体共用，仅移动主体"。

> 为什么：强制联动会悄悄改掉 N 条素材的归属，不联动会让主体和成员散落在不同分类里。让用户在这个差异上做一次显式选择，比替他决定好。

- 版本与 §5.1 的两类引用直接对接：**模板引用主体 = live（跟随最新发布版本）**；**历史任务的输入 = snapshot（指向具体 `subject_version`）**。这正是"引用分两类"最有力的证据——同一个主体，两个方向的需求同时存在。
- 提升链与素材一致（个人 → 团队 → 公共），审核前置：封面合规、全部成员合规、无缺图、属性完整、**角色可达 + 能力可达**（§2.6.4）。注意这里校验的是"主体承诺 ⊆ 成员授予"，**不要求也不允许在提升时批量改写成员可见域**。

#### 2.6.7 这块最容易踩错的四处

1. **把组做成 `asset.kind=group`**：图上看着统一，实际上每个渲染、权限、检索、导出入口都要分支，且"组的主图"与成员互相指形成环。**规避**：独立实体，成员用关联表。
2. **让组内素材"只属于组"**：一旦成员不能独立存在，跨主体共享就必须复制，库里的同类图会翻倍且各自漂移。**规避**：成员是完整素材，归属、标签、可见域独立；组只是"引用"它们。
3. **用平均向量聚组**：检索质量下降但没有任何报错，属于最难查的一类回归。**规避**：max 聚合 + 单测固定"正面图查询必须召回该主体"。
4. **把"权限约束"实现成可见域枚举比较**：三档枚举之间做 `>` 或 `⊇`，看着能跑，实际上把"能不能发现"和"能拿字节做什么"锁死在同一根轴上——于是要么被迫批量抬升成员（违反最小权限、压平角色分层），要么放弃校验（出现幽灵状态）。**规避**：能力集合与可见域分开建模，校验写成两条可达性断言（角色 ∩ 能力），单测覆盖"含一张无授权原片的主体必须发布失败或降级"。

### 2.7 与现状的字段对照

| 现状 | 目标 | 迁移方式（分批，不一次到位） |
| --- | --- | --- |
| `category` 字符串枚举 | `category` 表 + `asset.category_id` | 先建表，把 5 个枚举值写成 5 条系统分类，回填 ID；旧列保留一版做双写校验后删除 |
| `type` | `media_type`（系统判定，值域扩为 image/video/audio/document） | 字段改名 + 由探测结果回填，不信任历史值 |
| `shared` 布尔 | `visibility` + `promotion_request` | `shared=true` 映射为 `visibility=brand` 并补一条"历史公开"提升记录，便于追溯 |
| 无团队实体 | `team` + `team_member`（首批内容 / 运营 / 技术） | 新建表并初始化成员；存量素材 `team_id` 留空（其归属仍是个人的），不猜测归属 |
| 分类是全局枚举 | 分类表 + `team_id`（按库隔离） | 每个库初始化一棵分类树；旧 5 个枚举值映射为公共库的系统分类 |
| `sha256` 在 asset 上 | 提到 `blob` | 阶段一先加 `blob_id` 并回填（同 sha256 合并），资产层读 blob，写路径逐步切换 |
| `storage_key` | 提到 `blob` | 同上 |
| `ref_count` | 保留在 asset（展示用），另加 `blob.ref_count`（回收依据） | 现有 `ref_count` 会漂移，不作为删除依据，这一点沿用现有认知 |
| `pack` / `pack_draft`（template 模块私有） | `subject` + `subject_member` + `subject_version`，归 asset 模块 | pack → subject；包内图片 → member（按现有顺序填 `sort_order`，角色先统一填"未标注"）；主图 → `cover_asset_id`；固定参数 → `attributes`；已发布包 → `subject_version` v1 |
| 模板通过 packId 直接读包内图片 | 模板经注入口读主体（不许跨模块 import） | 与现有「取数留业务侧、成响应归框架」的边界一致，改造只是把注入口从 template 挪到 asset |
| pack 内图片无角色授权 | `subject_member.grants` / `in_output` | 现有 pack 没有这个维度，迁移时按角色填默认值（主图含 `download`，参考/未标注仅 `generate`）。没有历史值要保真，这是新增而非搬迁 |
| 无"维护人"概念（只有 `owner`） | `asset.maintainer` / `origin_owner` | 存量两条都回填为 `owner`；此后 `owner` 不再变动，维护权用 `maintainer` 转交（理由见 §6.2.1） |
| 生成产物落在运行工作区，未入库（`AssetSource.GENERATED` 是预留值） | 候选（`candidate`）→ 采纳（`adopted`）链路 | 新增能力，不是迁移。首批只接一条生成链路（替换模板的结果），先把批次、采纳、过期三件事跑顺再推广到其他生成模块 |

## 3. 二、分类与元数据

### 3.1 四个维度，各自只干一件事

| 维度 | 回答的问题 | 基数 | 放哪 | 能否改 |
| --- | --- | --- | --- | --- |
| 库（可见域） | 谁能看见、谁能写 | 三档：个人 / 团队（3 个）/ 公共 | 顶栏切换器 | 个人→团队：复制+审核；团队→公共：提升+审核 |
| 分类 | 这条素材"归在哪个目录" | 恰好一个 | 横向分类条 | 可移动（拖拽） |
| 标签 | 这条素材"是什么样" | 0–N | 筛选条 + 详情 | 可增删，只能选词表 |
| 媒体类型 | 这条素材"能怎么用" | 恰好一个 | 分类树第二级 | **不可改**，系统判定 |

**为什么权限必须放在顶栏而不是分类树里**：分类是"内容归到哪"，权限是"我能看到多大范围"。混在一起会立刻产生三个 bug：同一素材在树里出现两次（因为它既在"公共"又在"产品图"）、计数加起来不等于总数、把素材拖进"公共"分类时用户以为在做整理而实际上做了一次发布。这个混淆在素材类产品里极常见，且一旦上线很难纠正，因为用户已经形成了肌肉记忆。

**为什么媒体类型不能和一级分类平级**：一级分类是用户建的、可变的、会增删的；媒体类型是系统判定的、固定的、只有四个值。放同一层会让"折叠/展开"和"增删分类"变成同一个交互，用户会试图删除"视频"这个节点。

### 3.2 分类树

分类树**属于库**：个人库、每个团队库、公共库各有一棵，互不共享（理由见下）。

```
素材库（顶栏：个人库 ▾ | 内容团队 ▾ | 运营团队 ▾ | 技术团队 ▾ | 品牌公共库 ▾）
└─ 全部素材                     ← 当前库内跨分类聚合（他分类只读）
   ├─ 未分类收件箱        ⑫     ← 系统分类，角标 = 未归类素材数
   ├─ 产品图                 ← 一级分类（用户建，可改名/排序/归档）
   │   ├─ 图片            142   ← 二级：媒体类型，可折叠，计数
   │   ├─ 视频              7
   │   └─ 音频              0
   ├─ 人物形象
   │   ├─ 图片             86
   │   └─ 视频             23
   ├─ 场景与背景
   ├─ 参考视频                   ← 模板要用的运镜样本
   └─ ＋ 新建分类
```

规则：

- **深度固定两级**。一级是分类，二级是系统媒体类型分面。二级不是真实节点，而是"在一级内按媒体类型过滤"的视图。
- 一级分类只表达**用途**（产品图 / 人物形象 / 场景与背景 / 参考视频 / 合成成片…），不表达项目、不表达团队、不表达权限。这三件事分别归任务中心、库切换器、可见域。
- 计数口径：一级角标 = 该分类下未删除、当前库可见的素材数；二级 = 一级内按媒体类型分组数。计数只在筛选为空时展示总数，有筛选时改成"匹配 N / 共 M"。
- 排序：一级分类按手动顺序（可拖），二级按固定枚举顺序（图/视/音/文档），不按数量排——按数量排会让用户在素材增长时找不到位置。
- 空分类保留（显示 0），提供"归档/删除分类"。删除分类时必须选择素材去向（移至另一分类 / 移至收件箱），不允许级联删除素材。
- 各库的分类独立维护，**维护权随库走**：个人库由本人维护；团队库由该团队管理员维护；公共库由平台管理员集中维护，团队**不直建**。同名分类在不同库是两条记录。
- 公共库分类**不开放团队自建，也不做"申请分类"工单**。公共库是所有人的界面，而分类变更一年只有几次；为低频动作建一条审批流，成本高于收益。团队有需要走现有沟通渠道，管理员改一次即全员生效。**为什么不做申请流**：一旦开放，三个团队会各提一套命名，公共库的分类条会在半年内变成三套词的并集，且没有任何人对收敛负责——这正是 A8 要避免的结局。

**为什么深度锁死两级**：三级以上会让"一条素材只属于一个分类"的移动成本剧增（拖错层级就找不到了），面包屑、计数、拖拽落点、批量移动全部要重做。真实需求里"用途"一层 + "媒体类型"一层已经覆盖绝大多数查找路径；再细的查找用标签，标签是平的、可叠加的，正好补上"多维交叉"的需求——这也是标签存在的理由，不该让分类去兼任。

**为什么分类不跨库**：个人库的分类是"我自己的习惯"（我的参考、我的废片），团队库的分类是"团队约定"（产品图、人物形象）。共用一套会让个人库被团队分类污染，也会让"公共库加了个分类"变成所有人的界面变化。更实际的一层：跨库本来就必须复制（§2.5），复制时目标分类由用户在确认层里重选——分类不共享，正好对上这个动作。

**为什么"未分类收件箱"必须有角标**：这个产品最容易出的信任问题是"我上传了，但列表里没有"。收件箱带数字是唯一能让用户确信"东西在，只是没归类"的信号。反过来，角标为 0 时收件箱仍然显示，让用户知道这个位置一直存在。

**主体（成组资产）在这棵树里的位置**：一级分类下**不按资源形态分层**，主体与散素材同处一个分类——否则同一个产品会因为它的一张成员图属于别的分类而出现两次。主体视图单独给：顶栏库切换器旁一个"主体"快捷入口，按 `subject_type`（产品/人物/场景/道具）分组浏览全部主体，它不是分类节点，而是一个跨分类的**视图**，与"全部素材"同级。

### 3.3 标签体系（受控词表）

**六个维度、46 个词，全部可枚举。这是本期上线的初始词表（B1 已定），不是草案。**

| 维度 | 词表 | 数量 |
| --- | --- | --- |
| 风格 | 写实摄影 · 电影感 · 广告质感 · 3D 渲染 · 插画手绘 · 扁平矢量 · 胶片颗粒 · 极简留白 · 国潮国风 · 赛博霓虹 | 10 |
| 场景 | 棚拍纯色 · 室内家居 · 办公空间 · 城市街景 · 自然户外 · 餐厨空间 · 工业车间 · 抽象背景 · 合成虚拟 | 9 |
| 主体构成 | 无人 · 单人 · 多人 · 手部特写 · 宠物 · 群体 | 6 |
| 镜头 | 特写 · 中景 · 全景 · 俯拍 · 平视 · 推拉 · 环绕 · 手持 | 8 |
| 用途/版位 | 主图 · 详情页 · 封面 · 开屏 · 信息流 · 贴片 · 直播 | 7 |
| 内容属性 | 含真人 · 含未成年人 · 含品牌标识 · 需换脸 · 需打码 · 无水印 | 6 |

**为什么按这六个维度分，而不是按业务对象分**：一级分类已经回答了"这是什么素材"（产品图 / 人物形象 / 场景背景 / 参考视频 / 合成成片），标签再按对象分就是重复归类。标签要补的是分类给不了的三类信息：

| 类别 | 维度 | 解决的查找问题 |
| --- | --- | --- |
| 画面长什么样 | 风格、场景、镜头、主体构成 | "要一张极简留白、俯拍、无人的产品图" |
| 能放在哪 | 用途/版位 | "这批素材里哪些能直接上开屏" |
| 有什么要留意的 | 内容属性 | 合规复审时"把所有含真人的找出来" |

**三个必须遵守的边界：**

1. **内容属性不承担判定。** "含真人""需换脸"是事实描述，不参与任何自动拦截；合规结论在独立字段 + 审计记录里（理由见本节末）。**那为什么还要这个维度**：它把"找出所有含真人的素材"变成一次筛选，而这在合规复审时是刚需——但它只提供线索，不提供结论。
2. **同维度内唯一，且全局不重名。** "写实摄影"只属于风格。允许同名跨维度会让筛选器出现两个一模一样的分组标题，用户无从选择；全局唯一是更简单也更安全的约束。
3. **词必须可判定。** "高级感"不行——两个人看同一张图会给出相反答案；"极简留白"行，因为画面里有没有留白是可见的。**判据**：能不能让两个人在 3 秒内对同一张图给出相同答案。

**管理员可添加（B1 的后半）：**

- 入口只在管理页的"标签管理"，需要 `tag:manage` 权限，普通用户看不到。
- 新增即生效，**不需要第二人审批**，但记 `created_by` 与变更日志。**为什么不做审批链**：管理员本来就不多，加一道审批只会让他懒得提，最后词表靠私下约定维护；单人可加 + 留痕，比双人审批更可能被真的遵守。
- 新词 `status=active`，但**默认不进筛选条**：筛选条只展示使用次数 top 20 + 搜索框，新词被用满 5 次后才进常显区。**为什么**：词表会增长，而筛选条是一块固定宽度的界面，让它随词表增长等于让界面不可用。
- 每季度看一次 `usage_count = 0 且 90 天未使用` 的词，提示归档为 `retired`（不物理删）。

**准入三问**（写进新增表单，答不上来就不该建）：

| 问题 | 挡住什么 |
| --- | --- |
| 现在有三个素材能立刻用上它吗？ | 为想象中的需求建词，半年后全是零使用 |
| 它和现有哪个词同义？同义一律合并，不新建 | "写实""写实风""真实感"三胞胎 |
| 两个人看同一张图，会给出相同答案吗？ | "高级感""有质感"这类不可判定的词 |

规则：

- **只能从词表选**。落地方式不是"前端不给输入框"，而是接口只接受 `tag_id`，收到未知字符串直接 422；前端那个搜索框是"词表内模糊匹配"，不是"新建"。
- 标签**不物理删除**。废弃走 `status=retired`：不再出现在待选列表，历史素材上的关联保留，历史筛选结果不会静默改变。
- 标签合并（两个同义标签合一）要留重定向记录，否则沉淀在保存视图里的旧 ID 会变成空结果。
- 每个标签记录 `added_by` 与 `source`（manual / inferred）。系统推断的标签在卡片上要有区分标记，且可被人工覆盖。
- 新增路径**只有一条**（管理员的"标签管理"，见上），没有第二条。**为什么必须留这条**：完全封闭的词表在三个月内一定会被人绕过——把信息写进文件名、写进备注、或者直接改库。留一条正规路径，比假装词表不会不够用更安全。

**为什么合规状态不做成标签**：合规是状态机（待审 / 通过 / 驳回 / 复审），有当前值、有操作人、有时间、决定"能不能提升到公共库"。标签是无序描述，表达不了"当前处于哪一步"。做进标签的结果是：一个人打了"已授权"，另一个人打了"待换脸"，系统无法判定谁说了算，也没法在提升审核时做拦截。合规用独立字段 + 审计记录，词表里的"合规标记"只描述内容属性（如"待换脸"），不承担判定。

### 3.4 媒体类型由系统判定

判定顺序：MIME 白名单 → 容器探测（宽高/时长/轨道/帧率）→ 定类型；探测失败则拒绝入库并给可读原因，不做猜测。

- 类型、尺寸、时长、有无音轨全部由探测写入，不接受客户端传值（客户端传值只作为"期望值"，不一致时报错而不是采信）。
- 允许上传的最外层限制（大小、格式）与"能不能直接用于生成"是两件事。前者入库时判定，后者在生成准备时判定并在卡片上以"可用于替换 / 不适用：缺音轨"呈现。

**为什么不允许手动改**：下游全部按类型分派——视频要抽首帧、图片要降采样、音频要转码。手改一次类型，下游拿到的是错的分支，症状表现为"上传成功但预览空白""用作首帧时报错"，排查成本极高。用户真正想改的通常是"这个名字/这张图被当成图片了"，那是命名或文件本身的问题，不该开放类型字段去掩盖。

## 4. 三、检索设计

### 4.1 三种模式并存，但不是三个入口

| 模式 | 触发 | 输入 | 延迟预期 | 结果位置 |
| --- | --- | --- | --- | --- |
| 精确检索 | 任何筛选操作 | 文件名/标签/时间/上传人/分类/类型 | <100ms | 主结果区 |
| 语义检索 | 搜索框输入自然语言，或"以图搜图" | 文本或图片向量 | 300ms–2s | 语义结果区（追加在下方） |
| 上下文推荐 | 生成工作台里打开抽屉，或详情页"相似素材" | 当前场景/主题/已选素材 + 镜头字段 | 可预取 | 抽屉的独立 tab / 详情内区块 |

**为什么三者不合成一个"搜索"**：它们的确定性完全不同。精确检索的结果可解释（"因为标签是写实"），语义检索的结果只能说"相似"，推荐则连"你为什么看到它"都说不清。混在一个列表里，用户无法判断"这条为什么在前面"，也无法在语义结果不理想时退回到可信的那一半。分开呈现后，语义部分即使很差也不影响用户完成"我要找那张 3 月的产品图"这件事。

**检索单位是主体，展开是素材**：产品和人物天然成组，不聚合的话一次"找红色保温杯"会召回同一只杯子的六个角度，占满第一屏。聚合规则（max 而非平均、命中标注、折叠与平铺切换）见 §2.6.4。

### 4.2 分请求、分块渲染

```
用户输入 keyword / 改筛选
        │
        ├─► 请求 A：精确（filter + keyword 的字面匹配）
        │      └─ 返回即渲染主网格；控制条显示"共 N 项"
        │
        └─► 请求 B：语义（同一 filter 快照 + query 文本/图片向量）
               └─ 400ms 后才显示骨架（低于 400ms 不显示，避免闪烁）
                     ├─ 成功：主网格下方追加"AI 匹配"分区，带相似度与折叠
                     ├─ 空：只显示一行"没有语义相近的素材"，不占大面积
                     └─ 失败：该分区显示"语义检索暂不可用，已显示精确结果"+ 重试
```

关键约束：

- 两个请求共享同一个 `filter` 快照与同一个 `queryId`。**语义结果返回时若 `queryId` 已变，直接丢弃**，不追加。
- 语义请求的筛选条件与精确请求**完全一致**（同一份 filter 序列化），不允许"语义不做权限过滤"这种捷径。
- 语义分区默认展开，超过 12 条时折叠为"查看全部 AI 匹配"。
- 精确结果为 0 而语义有结果时：主区显示"精确检索无匹配"，语义区正常展开，并提示"已放宽为语义匹配"。这一条很重要——否则用户看到"0 项"就走了，而下面其实有货。

**为什么分请求而不是一次返回**：合成一次请求意味着最慢的那部分决定整体体验，语义索引不可用时连精确结果都拿不到。分开之后，语义只是"加分项"，它的故障域被限制在一个分区里。这也是唯一能让"先出精确结果再补语义"在工程上成立的做法——渲染顺序由请求完成顺序决定，而不是由前端做延迟拼接。

### 4.3 向量索引

- 向量存独立表：`asset_id`、`model_key`、`dim`、`vector`、`source_hash`（用于判断是否需要重算）。
- **异步补算**：入库不阻塞在 embedding 上。素材先可搜（精确），向量算完才进语义池。出参带 `semanticReady` 标记，未就绪的素材不出现在语义结果里。
- 图片向量取自**托管缩略图**，不取原图：原图可能几十 MB，批量算 embedding 会把 CPU 打满。
- 文本向量来自 `文件名 + 分类名 + 标签名 + 提示词摘要` 的拼接，不只有文件名——只喂文件名的向量空间里，"IMG_2043" 之间全部相似。
- 索引：PG 用向量索引（HNSW），SQLite 退化为暴力扫描并对总量设上限。

**为什么必须先过滤再 KNN**：向量检索的默认写法是"取全局 topK 再过滤"，在权限分层的库里面这是双重错误——结果可能远少于 K 条（因为前 K 条大多不可见），且通过"结果数量"能推断出"库里存在但我看不到的东西有多少"。正确形状是 `WHERE 可见条件 AND 分类条件 ORDER BY distance LIMIT k`，并对"过滤后不足 k 条"显式返回 `hasMore=false`。

**为什么要 `source_hash`**：素材改名、改标签、换封面都会让旧向量过期。没有这个字段就只能全量重算或永不重算，后者会让语义检索随时间慢慢变味，而且没人能发现。

### 4.4 保存筛选视图

一个视图保存：`名称`、`可见性（私有/团队）`、`筛选快照`、`排序`、`视图模式（网格/列表）`、`所属范围（库 + 分类）`。

- **筛选快照只存条件，不存页码、不存结果 ID**。存了页码的视图第二天打开是空的；存了结果 ID 的视图会变成"快照"而不是"视图"，新素材永远进不来。
- 条件序列化走**白名单**：只允许 `keyword / categoryId / tags / mediaType / timeRange / uploader / state / sort`，未知键丢弃。避免把内部调试参数写进用户视图。
- 视图入口在筛选条左侧，以胶囊呈现；最多展示 3 个，其余收进"更多视图"。
- 应用视图时，如果它引用的分类已被删除或标签已 retire，降级为"已移除失效条件"并提示，而不是报错。

**为什么视图要存在服务端**：跨设备、可共享给团队。存在本地存储的视图在换机器后消失，而"我们组的出片筛选条件"恰恰是最该被共享的东西。

## 5. 四、复用机制

### 5.1 引用式复用：两类引用必须分开

| 类型 | 绑定对象 | 行为 | 用在 |
| --- | --- | --- | --- |
| `live`（跟随） | 资产/模板 ID | 源更新，引用方看到新内容 | 品牌模板、公共素材挂载、引用式复用 |
| `snapshot`（冻结） | 资产 ID + 具体版本 | 永久定格，源再改也不变 | 生成血缘、任务输入快照、成片配方 |

**为什么必须两类**：这是两个相反的需求。"模板由管理员统一更新，引用方自动继承"要求跟随；"历史成片的配方不能被后来的模板修改污染"要求冻结。只做一种，另一个必然出错——而且错得很隐蔽：跟随式做血缘，改动模板会让历史成片的"当时用了什么"悄悄变化；冻结式做模板，管理员更新模板后没有任何人收到变化。

落地上的区分是**字段级**的：引用记录上带 `pinned_version`（可空）。空 = 跟随，非空 = 冻结。UI 上以"跟随最新 / 已锁定 v3"两种文案区分，并明示"锁定"是默认给血缘用的。

- 原始模板只读：非管理员对源资产的写操作一律拒绝，且**拒绝原因要说清楚**（见 §6.4）。
- 引用被删除时的处理：源素材删除前检查引用，被引用则进入"待定"——列出引用方，允许"仍要删除（引用方显示为失效）"或"取消"。不允许级联删除引用方的记录。

### 5.2 一键衍生的三个入口

| 入口 | 产生什么 | 数据结果 |
| --- | --- | --- |
| 用作图生图参考 | 跳转到生成页，把该素材填入参考位 | 只产生"引用"，此时不产生新素材 |
| 用作视频首帧 | 跳转生成页，填入首帧位 | 同上 |
| 提取提示词微调 | 把配方 `prompt` 填进编辑器（可编辑） | 不产生素材，也不改原素材 |

生成完成后，产物先是**候选**（`origin=generate`，`stage=candidate`），用户采纳才成为素材（`stage=adopted`）；`recipe.parent_recipe_id` 指向源的 recipe，采不采纳都不影响血缘。**衍生永远新建记录，不原地改**。

**为什么必须新建**："这条素材是怎么来的"是资产库最核心的价值。原地改（比如"用这张图做图生图，结果覆盖这一条"）会让血缘断开、让引用方看到的内容变化、让"这条被谁用过"的答案失真。新建记录还能让用户在"衍生"和"原图"之间来回对比——这恰恰是废片筛选的必经动作。

**为什么"提取提示词"不产生素材**：它产出的是一段文本，属于"参数复用"而不是"内容复用"。如果为它造一条素材记录，素材库会被提示词片段污染，而提示词本来就该由"提示词库/模板"承载。

### 5.3 跨边界使用的显式确认

拖拽是低摩擦动作，跨边界时必须打断。两种边界：**跨分类**（同库换目录）与**跨库**（取用别人的库或公共库的内容）。

```
拖动卡片从 A 分类 → 悬停在 B 分类上（或另一个库上）
        │
        ├─ 同库同分类：直接落位（排序/移动，无确认）
        └─ 跨分类 / 跨库：
             卡片显示"＋ 复制"角标，光标变 copy
             释放 → 弹确认浮层（不是 toast，不是直接执行）
                   ┌────────────────────────────────────────┐
                   │ 复制到「产品图」（个人库 · 跨分类）        │
                   │ 1 条素材 · 共享原文件，不重复占用配额      │
                   │ 标签：8 个将一并复制          [取消勾选]  │
                   │ 可见范围：个人库（不上调，不继承源）        │
                   │ 生成配方：保留（同一次生成，血缘不断）      │
                   │                    [取消]  [复制]        │
                   └────────────────────────────────────────┘
```

规则：

- 确认层必须说明**三件事**：共享字节（不占双份配额）、标签是否跟随、可见域只降不升。这三项是最容易事后引发争议的地方。
- **往上拖不是复制，是提交。** 把个人库素材拖到某团队库的落点，结果不是"团队库多一条"，而是"该团队待审区多一条"（§6.2.1）；确认层文案改为「提交到「内容团队」待审」，按钮改为「提交审核」。**为什么**：拖拽的低摩擦正是危险所在——往上一拖就进团队库的话，团队库三周内会变成所有人的个人素材堆，且没有人负责清理。往下拿（团队库 → 我的库）仍是普通复制，因为它不影响任何人。
- **跨库默认只读**：公共库素材对所有人可预览、可衍生、可被引用，但不能改名/移动/删除；其他团队的团队库**不可见**（团队是隔离边界，不是可见范围）。卡片对只读项降饱和 + 右上锁角标，悬停操作条只保留"插入 / 衍生 / 参考"。
- 批量拖拽时，确认层显示"N 条，其中 M 条已存在于目标分类（将跳过）"。不允许静默产生重复记录。
- 复用方式二选一：默认"复制"，高级选项"引用挂载（只读，跟随源）"。**为什么给引用挂载**：有些素材（品牌 Logo、合规底图）必须全局一致，复制会让它们各自漂移；但引用挂载要显式选择，不能默认，否则用户会以为自己有了一份可编辑的副本。

### 5.4 可调用资产：模板 × 主体的组合契约

**素材专员**（下称专员）的产出不是"整理好的文件夹"，而是**能直接被生成流程消费的资产**。这类资产有两种形态，且必须成对出现：

| 形态 | 是什么 | 谁产出 | 在生成里的角色 |
| --- | --- | --- | --- |
| **主体**（§2.6） | 一组产品/人物图 + 角色 + 固定属性 | 专员 | 被替换的那一方 |
| **模板** | 参考视频 + 提示词 + 固定参数 + **槽位声明** | 专员 | 被复用的那一方 |

换产品的场景 = **模板（不变）× 主体（换掉）**。所以"AI 生成时可直接选择"的真实含义是：**专员已经替用户回答了"该放哪几张图、用什么运镜、提示词怎么写"，用户只剩下"选哪个产品"**。

这条决定了设计的重点：契约必须做在专员侧，用户侧只看到"能不能用"。用户不该在生成时看到"槽位""角色"这些词，他只看到产品名、封面和一句"缺细节图，效果可能偏差"。

#### 5.4.1 模板的形状

```
template（可复用生成流程）
├─ name / description / category
├─ template_type      replacement | motion_transfer | style_transfer | …
├─ reference_asset_id 参考视频（对 asset 的 live 引用，不复制字节）
├─ prompt             提示词全文，支持占位符
├─ fixed_params       固定参数（时长 / 帧率 / 比例 / 模型版本）
├─ slots              槽位声明（见 5.4.2）
├─ visibility         个人 / 团队 / 公共
├─ status             draft | trial | published | retired
└─ current_version ──► template_version（不可变快照）
```

- 参考视频是**对素材的 live 引用**，不是副本：同一条运镜视频可以被五个模板复用（不同提示词、不同产品）。§5.1 的两类引用在这里第一次真正派上用场——模板跟随源视频更新，历史任务冻结在当时的版本。
- 参考视频本身常常是**生成产物**（`origin=generate`，已被采纳）：把一条满意的成片定为运镜参考，它就从"我的素材"进入模板池。这条让素材库与模板库闭合成一个环，而不是两套互不相干的东西。未被采纳的候选不能当参考视频——见 §6.5。
- 提示词支持**占位符**（`{product_name}`、`{brand}`、`{scene}`），取值来自主体的 `attributes` 或调用时填写。**为什么**：专员做 20 个产品时不该复制 20 份提示词；而占位符把"哪些字段会被自动填"变成可见的，用户不会在生成完才发现产品名没进去。

#### 5.4.2 槽位契约：角色词表是模板与主体的接口

模板声明它需要什么，主体声明它提供什么，两边按 `role` 对齐：

| 槽位字段 | 语义 | 缺失后果 |
| --- | --- | --- |
| `required_roles` | 必须提供（如 正面、45 度） | **不可用**，不出现在可选列表 |
| `optional_roles` | 有则更好（如 细节、背面） | 降级可用，带质量提示 |
| `min_images / max_images` | 张数边界（如 1–3 张） | 越界即不可用 |
| `preferred_cover_role` | 指定用哪个角色当主图 | 回落到主体封面，不报错 |
| `required_caps` | 模板需要的能力（默认 `generate`；需要取原片另存时为 `download`） | 主体能力不足即**不可用**，提示"缺：原件下载" |

匹配结果三态，在选择阶段就算完：

- **可用**：required 角色全满足，且 `required_caps ⊆ 主体能力` → 正常出现在"选产品"列表
- **降级可用**：缺 optional 角色 → 出现，但带"缺 细节图，效果可能偏差"
- **不可用**：缺 required 角色、或能力不足 → 不出现（而不是选了之后才报错）

> **为什么能力也是槽位条件**：角色回答"有没有这张图"，能力回答"这张图能不能这么用"。只校验角色，会出现"选的时候能用、真跑起来拿不到原片"的组合——而这类失败发生在生成中途，代价比列表里少一个选项高得多。

> **为什么在选择列表阶段就算，而不是提交时算**：等到提交才报"缺图"，用户已经调了三分钟参数。可选列表本身就是一个可判定的集合——服务端返回时带 `availability` 与 `missingRoles`，前端直接渲染禁用态与原因，不需要额外的"校验"按钮。

#### 5.4.3 试跑：专员的发布前置

专员发布主体或模板前必须能在沙箱里跑一次：

- 用最低成本参数、单主体、单镜头；产物进 `draft` 桶，按草稿过期（§6.3）。
- 试跑走**独立额度**，不进业务用量；产物不进"我的素材"，但保留在模板详情里作为"效果样例"。
- 专员显式点"通过"之后才允许发布。

> **为什么必须有**：换产品最容易出的问题是"产品图和参考视频的运动对不上"——提示词写得再漂亮，也得跑出来看产品在手里滑不滑才知道。没有试跑，专员只能等用户投诉，而模板是公共资产，一个坏模板影响所有人。顺带的好处是：试跑产物沉淀下来就是最好的使用说明。

#### 5.4.4 契约失效检测

主体换版、模板换版、参考视频被删，都会让某个"模板 × 主体"组合从可用变不可用。必须在**列表阶段**就暴露：

| 变化 | 影响 | 呈现 |
| --- | --- | --- |
| 主体成员被删 / 降级可见 | 缺 required 角色 | 组合标"不可用：主体缺 X"；历史任务不受影响 |
| 模板发布新版本 | 引用方跟随（live） | 组合列表刷新；已提交任务用旧版本快照 |
| 参考视频被删 | 模板整体不可用 | 模板卡标"参考视频已失效"，可换绑 |
| 主体属性变更（品牌名等） | 占位符取值变化 | 组合仍可用，详情标注"属性已更新" |

> **为什么专门做这件事**：这是引用式复用的必然副产品。引用越省事，失效越隐蔽——没有检测，症状是"上个月还好用，今天点生成直接报错"，而且没有任何线索指向"某张图被删了"或"模板换了版本"。

#### 5.4.5 组合预设

把"模板 × 主体 × 参数"存成命名组合（如"双11-红色保温杯-15s 竖版"），一键复用。

- 存**引用**不存快照；来源更新时提示"主体已更新到 v3 / 模板已更新到 v5，是否沿用"。
- 预设属于**调用方**，不属于专员。**为什么**：预设是"我怎么用"，不是"东西是什么"。把它升格成公共资产，会把 1000 个用户的偏好变成 1000 条需要审核的资产。

#### 5.4.6 这块最容易踩错的三处

1. **把模板做成"一组散配置"**（存在设置项或某个 JSON 字段里，而不是资产）：无法检索、无法版本化、无法授权。专员做到 50 个之后，没人能回答"哪些模板能配这个产品"。**规避**：模板必须有 ID、版本、可见域，进同一个检索与授权体系。
2. **槽位只校验数量不校验角色**：模板要"正面 + 45 度"，用户拿两张正面也能过，跑出来产品形变，最后归因成"模型不行"。**规避**：角色是契约，数量只是边界；`required_roles` 必须逐项核。
3. **试跑和生产共用一条路径与配额**：要么专员不敢试（怕烧额度），要么试跑污染生产（进"我的素材"、计入用量）。**规避**：物理分开——不同存储桶、不同配额、不同默认可见域。

## 6. 五、权限与生命周期

### 6.1 三层可见域（团队层要真建实体）

| 库 | 读 | 写 | 准入 |
| --- | --- | --- | --- |
| 个人库 | 本人 | 本人 | 默认归属地 |
| 团队共享库 | 本团队成员 | 提交者（`maintainer`）+ 团队管理员 | **复制提交 + 批次审核**（§6.2.1） |
| 品牌公共库 | 全员 | **仅管理员** | **提升 + 审核**，变更留审计（§6.2.2） |

**首批团队**：内容团队、运营团队、技术团队（已确认）。因此需要新建组织结构，而不是先把 `team` 当作枚举占位：

| 实体 | 承载 |
| --- | --- |
| `team` | 团队名、状态、创建人 |
| `team_member` | 用户 ↔ 团队，带角色（成员 / 管理员），**允许一人属多团队** |
| `category.team_id` | 分类树归属哪个库（个人库为空、团队库填 team、公共库用保留值） |
| `asset.team_id` | 素材所属团队，`visibility=team` 时必填 |

**初始团队管理员名单（B7 已定，seed 数据）**

| 团队 | 主管理员 | 备管理员 |
| --- | --- | --- |
| 内容团队 | `tm.content.lead` | `tm.content.backup` |
| 运营团队 | `tm.ops.lead` | `tm.ops.backup` |
| 技术团队 | `tm.tech.lead` | `tm.tech.backup` |

六个人，每团队一主一备。

- **为什么每团队两人**：只有一名管理员时，他休假或离职就没人能审批交付，待审区立刻开始堆积；而"临时给谁开一下权限"是一次不可审计的例外，开过第一次就会有第二次。两人是成本最低的冗余。
- **账号是占位，不是真人**：命名规则 `tm.<team>.<role>`，由 `ModuleSpec.seed` 创建，首次登录强制改密。真实人员接手时只改 `team_member.user_id` 一行，不动代码、不重跑 seed。
- **演示账号同时属于三个团队且 `team_admin=true`**，用于开发期跑通流程；**不要拿它在真实环境做审批**——它是全系统唯一一个没有责任人的管理员。

**团队管理员的权限边界（同样是「范围 + 动作」，不是身份）**

| 能做 | 不能做 |
| --- | --- |
| 审批本团队的交付批次 | 审批其他团队的交付 |
| 维护本团队分类树 | 改公共库分类（平台管理员） |
| 接管本团队素材的 `maintainer` | 改别人个人库的素材 |
| 增删本团队成员 | 任命其他团队管理员（须平台管理员） |

> 最后一条是刻意收住的：允许团队管理员自行任命同级，等于让每个团队变成一个自循环的权限孤岛，调岗或离职时无从回收。任命权集中在平台管理员，回收时才只有一个入口去找。

判定规则：一条素材的可见域是**单一值**（`visibility` + `team_id`），不是多值叠加。同一素材在"我的素材"和"团队库"里同时出现时，是同一个可见域在两种视图下的呈现，不是两条记录。

**可见域只回答"能不能发现"，不回答"能做什么"。** 后者是能力（§2.6.4），主体上的 `grants` / `requires` 独立于 `visibility` 判定。把两者合成一个可比较的枚举，就会被迫在"批量抬升成员"和"放弃校验"之间二选一，这两条路都走过一次，代价见 §2.6.3 铁律③的说明。**实现上的硬约束：代码里不允许出现 `member.visibility >= subject.visibility` 这类比较**，能力校验一律走集合包含判定。

**为什么必须真建实体，不能拿枚举占位**：团队一旦成为**读边界**，"我属于哪些团队"就变成每次列表查询的前置条件。用枚举（"内容/运营/技术"三个字符串）做占位，成员关系只能写死在代码或角色权限里，一个人调岗就要改权限配置；而真建成员关系后，调岗是改一条 `team_member`。这也是这次唯一一个"不做就得返工"的结构性决定。

**一人可属多团队**：内容团队的人经常要取运营团队的成片。多对多不是可选项——单团队归属会逼出"给这个人开全站读权限"这种更糟的解法。

**为什么可见域是单值而不是多值**：如果一条素材可以同时属于"个人 + 团队 + 公共"，那么"改权限"就变成"增删集合成员"，而"它现在到底谁能改"不再是可判定的单一事实。单值 + 单向迁移链（个人 →复制+审核→ 某团队 →提升+审核→ 公共）让每次变更都是一次状态迁移，可审计、可回滚。

**跨团队不可见**：A 团队看不到 B 团队的团队库（不是只读，是不可见）。**为什么**：三个团队并存时，"能看见但不能改"会让每个团队的素材都被其他团队当成参考库，边界形同虚设；而真正需要跨团队共享的东西，应当走提升到公共库这条路——那条路有审核，也有审计。

**专员是一个角色，不是一层库**：素材专员（§5.4）在公共库上拥有写权，但这不等于"专员的任何写操作都放行"。判定永远是「范围 + 动作」两元的：专员能改**公共库**里的主体与模板，不能改别人的**个人库**素材，也不能因为身份就绕过发布审核。**为什么强调这条**：这类系统最常见的权限退化写法是 `if is_specialist: allow`——一旦写成身份短路，之后每一次"专员能不能做 X"都要改代码，而不是改权限配置。专员的权限应当是若干权限点的集合（维护参考素材、组装与发布主体、编辑与发布模板），且这些权限点在模块声明里登记、可授予可回收。

### 6.2 进入更高可见域的两条路：复制与提升

A7 定下的口径是**个人库 → 团队库走"显式复制 + 审核"，团队库 → 公共库走"提升（改可见域）"**。两条路方向看着一样，语义相反，不能合并成一条。

| 路径 | 动作 | 新记录 | `owner` | 源更新后 | 源删除后 | 用在哪 |
| --- | --- | --- | --- | --- | --- | --- |
| **复制进团队** | 新建一条 asset，共享 blob（`ref_count + 1`） | 是，`copied_from` = 源 | 提交者 | **不跟随** | 团队副本不受影响 | 个人 → 团队（**默认且唯一**） |
| **提升到公共** | 同一条记录改 `visibility` | 否 | 不变 | 跟随 | 不存在"源" | 团队 → 公共（**唯一**） |

**为什么这个方向不能互换：**

- **个人 → 团队必须复制。** 个人库是作者的私人工作区，作者对自己的素材有完全删除权。若团队引用的是原记录，作者某天清理自己的库，团队素材就会凭空消失——而团队没有做错任何事。复制之后团队持有独立副本，作者怎么清理都不影响。
- **团队 → 公共必须提升。** 公共库是品牌资产，要求全局唯一、管理员统一更新、引用方自动继承（§5.1 的 live）。若用复制，三份"品牌 Logo"会各自漂移，改一次要改 N 处，而没改的那几处没人知道自己是旧的。

这两条方向不对称，恰好对应两种不同的所有权语义：**团队交付的是"我做的这一份"，公共库交付的是"唯一的那一份标准"**。

#### 6.2.1 复制进团队：待审区与批次审核

```
个人库 ──选择 N 条──► 提交（选目标团队）──► 团队待审区 ──通过──► 团队库
                                              │
                                              └─驳回──► 回到"我的提交"（可改后重提）
```

- **提交即进入待审区，不是直接进团队库。** 待审区只有提交者与审核人可见。**为什么**：不设待审区，团队库会被一次性灌进 200 张图，审核员实际只能"全通过"或"全驳回"，审核形同虚设。
- **审核单位是批次，不是单条。** 一次提交的 N 条共用一条审核记录。**为什么**：素材专员交付的是"这套产品图"，逐条审会让同一批素材出现"过了 3 张、卡了 2 张"的半成品状态，反而更难用；需要单条处理时，可在批次内排除某几张再提交。
- **复制到团队时必须选择目标团队**（内容 / 运营 / 技术）。**为什么**：不选目标等于同时公开给三个团队，正好把团队这道边界拆掉。
- **提交前做库内去重**：目标团队已有同 `sha256` 的 asset 时，不新建记录，提示"团队库已有同一文件（由 X 于 Y 提交）"，可选择"直接引用已有条目"或"仍要新建归属"。
- **配额不翻倍**：复制只加引用计数，字节共享（A6 口径）。**这一条要写在确认框里**，否则用户会以为复制一份就占两份空间，从而放弃复用。
- **副本可编辑，且与源分叉是预期行为**：改名、换标签、重新裁切都不影响源。确认框里明示"这是独立副本，源更新不会同步过来"。需要跟随时应当用 §5.3 的"引用挂载（live）"，而不是复制。

**副本的三个身份字段，缺一个就会在半年后变成无主资产：**

| 字段 | 含义 | 可变 |
| --- | --- | --- |
| `owner` | 谁创建的这条副本（审计用） | 不可变 |
| `maintainer` | 谁现在负责维护（改名、换标签、替换版本） | 可转交，团队管理员可接管 |
| `origin_owner` | 源素材的原始作者（历史，用于追溯"这图最早是谁做的"） | 不可变 |

> 只有 `owner` 的话，提交者调岗或离职后，团队库会沉淀一批"没人敢改"的素材——改等于动了别人的东西，不改则一直是旧的。`maintainer` 是唯一能回答"这张图现在归谁管"的字段，而它与"谁创建"确实是两件事。

#### 6.2.2 提升到公共库

```
某团队库 ──申请──► 待审 ──通过──► 品牌公共库
                     │
                     └─驳回──► 回原团队库
```

- 提升记录：`asset_id`、`from_visibility`、`to_visibility`、`to_team_id`（仅团队层）、`requested_by`、`reviewer`、`decided_at`、`note`、`status`。
- 提升**不改 `owner` 与 `maintainer`**，只改可见域。**为什么**：归属是"谁对它负责"，可见域是"谁能看"。合并两者会让"提升"变成"转移所有权"，原作者失去对自己素材的管理权，而这正是 A7 要避免的事。
- 提升后原库不再显示该素材（单值可见域），但它仍留在"我上传的"跨库视图里，避免用户以为东西丢了。

#### 6.2.3 发布前置校验

- **素材提升**：配方完整（生成型）、合规状态为通过、无未处理的举报。缺任一项，按钮置灰并给出具体缺哪项。
- **主体发布**（专员）额外要求：至少 1 名成员；封面在成员内；**角色可达 + 能力可达**（§2.6.4）；成员合规全部通过；`attributes` 按类型填全。
- **模板发布**（专员）额外要求：参考视频有效；槽位声明里的角色都在角色词表内；必需角色能被至少一个已发布主体满足；**至少一次试跑标记通过**（§5.4.3）。

> 主体这一条特别注明：校验的是"主体承诺 ⊆ 成员授予"，**不要求、也不允许在发布时批量改写成员可见域**。发布是"检查能不能用"，不是"顺手把权限统一一下"。

### 6.3 存储分桶与过期

| 桶 | 内容 | 保留策略 |
| --- | --- | --- |
| `original` | 上传的高分辨率原片 | 长期；仅随素材删除而回收 |
| `draft` | 未确认的候选（7 天）、已弃用的废片与中间帧（14 天） | 到期隐藏 → 宽限 → 回收 |
| `final` | 采用的成品、导出物 | 长期 |

过期是三级阶梯，不是一步删除：

1. **软过期**（到点）：从默认列表隐藏，详情仍可打开，卡片灰化标"已过期"。
2. **宽限期**（+7 天）：任何入口打开都给"恢复"按钮，恢复即刷新过期时间。
3. **回收**（宽限期后）：仅当 `blob.ref_count = 0` 才物理删除；仍被引用则只解除本条 asset 关联，字节保留。

**为什么草稿过期不删配方**：配方是"这次生成做了什么"的事实。草稿过期只说明"这份字节不用留了"，但它的配方仍解释了成品是怎么来的（衍生链从这里经过）。配方行不占空间，删了会让成品的血缘在中途断掉。

**为什么要有宽限期**：直接删的死法最伤信任——"昨天还能看的草稿今天 404"，而用户完全不知道有这个策略。宽限期 + 可见的倒计时（详情里写"3 天后回收"）把这件事变成可预期的。

### 6.4 只读态的界面表达

只读不是"置灰了事"，必须给三层信息：**状态、原因、出路**。

| 层级 | 表现 |
| --- | --- |
| 视觉 | 缩略图降饱和（约 60%）、右上角锁角标、卡片边框变细灰 |
| 悬停 | 可用操作保留（插入 / 衍生 / 参考），写操作置灰 |
| 点击置灰项 | 不给 toast "无权限"，给浮层："该素材属于品牌公共库，仅管理员可编辑。你可以 **复制到「当前分类」** 后修改。" |

**为什么必须给"出路"**：只读态最差的做法是让用户卡死在一个没有下一步的界面里。给出"复制后修改"这条路径，把一次拒绝变成一次可完成的动作——这也是 §5.3 复制机制真正的使用场景，比"跨库拖拽"更高频。

**"能力受限"必须和"只读"分开表达**。这两个状态在权限上不同层级，混在一起会让用户以为整个素材不能用：

| 状态 | 含义 | 视觉 | 操作条 |
| --- | --- | --- | --- |
| 只读 | 这个人对整条素材没有写权（别人库/公共库） | 降饱和 + 右上锁角标 | 插入 / 衍生 / 参考 保留，写入项全灰 |
| 能力受限 | 能用，但某一项动作不允许（可生成、原件不可下载） | **不降饱和**，只在受限按钮上加小锁 | 其余按钮正常，受限项 hover 说明"该成员未授权原件下载" |

> 若两者用同一套灰化，用户看到的是"这个产品我完全不能用"，而事实是"能用，只是不能拿原片"。前者会让人放弃使用，后者只需要换个方式取用——这是一个纯呈现问题，但决定了功能会不会被用起来。

### 6.5 候选与采纳：AI 产物怎么"转正"

AI 产出**只是中间产物**。字节落地 ≠ 成为资产：必须由用户确认一次，它才进入素材库成为"生成型素材"。这条决定了一条状态机，也决定了生成结果不能直接写进列表。

```
生成完成
  │
  ├─► candidate（候选）── 采纳 ──► adopted（生成型素材）── 移入回收站 ──► deleted
  │        │
  │        ├─ 弃用 ──► discarded（废片，字节按草稿过期回收）
  │        └─ 超时 ──► expired（未确认即回收）
  │
  └─ 生成失败：不产生素材记录，失败原因进任务日志
```

**一次生成 = 一个批次 = 一条 recipe + N 个候选**。这正是 §2.3 那个"配方可被多条 asset 共享"的设计在兑现：同一批 8 个变体共用一条配方，用户采纳其中 2 个，它们各自是一条 `adopted` 素材，配方仍然只有一条——血缘不因为只采纳了一部分而丢失。

规则：

- 候选落 `draft` 桶，**不进"我的素材"网格**，只进"待确认"区（§7.9）。候选的数量不计入"我的素材 N 项"。
- 采纳可逐条、可批量；同一批允许只采纳一部分，其余继续留在候选区等过期。
- 采纳时补齐：分类（默认当前库的未分类收件箱）、可选标签、合规状态置"未评估"。**采纳不写配方**——配方在生成那一刻就写死了（§2.3）。
- 采纳产生审计记录（谁、何时、来自哪个批次）。**为什么**：AI 生成内容需要可追溯的"责任人认领"记录，争议时这是唯一证据；也让"这批图是谁选的"在团队协作里可回答。
- 候选**不计入**用户配额，采纳才计入。**为什么**：候选是系统刚吐出来的东西，用户还没决定要不要。按候选计费会让人不敢多生成，而"一次多出几张再挑"恰恰是这个产品的核心用法。

**四级递进，任何两个都不能合并**：

| 层级 | 含义 | 谁做 | 结果 |
| --- | --- | --- | --- |
| 采纳 `adopted` | "这张我要了" | 生成者本人 | 进入我的素材，可被引用、可打标签 |
| 合规 `approved` | "这张可以对外用" | 审核人 | 可交付、可用于公共场景 |
| 交付 `delivered` | "这张进团队库" | 提交者 → 审核人 | 团队内可见（**复制副本**，§6.2.1） |
| 提升 `promoted` | "这张进公共库" | 管理员审核 | 全员可见（**改可见域**，§6.2.2） |

> **为什么要反复强调**：四件事的时间点、责任人、可逆性都不同——采纳是即时的、个人的、可撤销（移入回收站）；合规是有依据的、留档的；交付与提升是组织行为。合并后的典型后果是"用户为了让图出现在列表里，顺手点了发布"，于是公共库里混进一堆没人审过的内容。另一个后果是审核人被迫承担"要不要这张图"的业务判断，而那是生成者的事。
>
> **交付与提升也不能合并**，尽管它们看起来都是"往上放"：交付**新建一条记录**（团队拿到独立副本，作者删原件不影响团队），提升**改原记录的可见域**（公共库要求全局唯一、跟随更新）。合并成一个"发布"动作，就只能二选一——要么公共库出现多份会漂移的品牌素材，要么团队库的素材会随作者清理个人库而消失。

硬约束（每一条都是有具体事故的样子）：

- **只有 `adopted` 能被主体引用、被模板消费、被检索召回、被打标签、进语义索引。** 候选进主体，等于"产品图组里混着没确认的图"；候选打标签，等于描述一个还没被决定的内容；候选进向量索引，等于搜出来一堆用户已经丢弃的废片。
- **候选过期 7 天**（比草稿桶短），过期前 48 小时在待确认区标"2 天后清理"。
- **过期即回收，不复活。** 采纳一个已被清理的候选 → 返回"该候选已清理"，给"重新生成"。**为什么**：复活会与引用计数、存储回收、批次统计三处冲突，而用户本来就没打算要它。
- **谁生成谁采纳，且不建 `adopted_by` 字段。** 别人可以看、可以用（同团队内），但"认领"必须由生成者做，否则责任人字段会变成一句空话。既然采纳人恒等于生成者，只记 `adopted_at` 与审计记录，不建 `adopted_by`——**建了就会有人开始往里写别的值**，而那个值一旦存在，"谁认领了这张图"就要重新解释一遍。生成者离职或调岗时，候选**不做代采纳、不做所有权接管**，7 天后自然过期。**为什么**：候选是价值最低的中间物，重跑一次的代价远低于走一遍"谁能替别人认领作品"的判定；而那个判定一旦开口，就再也关不上了。

### 6.6 配额计量（A6：按去重后的字节）

先划清一件事：**配额是账面口径，不是物理占用。** 物理上只有一份字节（`blob` 唯一），账面要回答的是"这个计费主体占了多少空间"。两者在很多情况下不相等，混用会让用户遇到"删了一堆素材空间没变"或"什么都没传空间却少了"这两种都解释不通的现象。

**三条规则：**

**① 计费主体按可见域定，不按 `owner` 定。**

| 素材可见域 | 记在谁头上 |
| --- | --- |
| 个人库 | `owner` 的个人额度 |
| 团队库 | 该团队的额度（**不记提交者**） |
| 公共库 | 平台成本，不计入任何个人或团队 |

> 为什么按可见域：交付给团队的素材占用的是团队的空间。若记在提交者头上，一个人交付 100G 就把自己额度用光，而他是在为团队做事；反过来团队库被填满时，管理者应当看到"是团队在用"，而不是"某个人的额度满了"。

**② 同一计费主体内按 `sha256` 去重。** 个人额度 = 该人名下 `visibility=personal` 且未删除的素材，按 distinct `sha256` 求字节和；团队额度同理（`visibility=team` 且 `team_id=t`）。同一文件复制到 5 个分类只算一次——这是 A6 的全部意义，否则复制被计费、跨库复用直接被劝退（§2.5）。

**③ 跨计费主体各计一次。** A 把 100G 交付给团队（复制），账面变成"个人 100G + 团队 100G"，物理仍 100G。这是口径的固有边界：两个主体各自要能独立回答"我占了多少"，若按"第一个拥有者计费"会变成扯皮，按物理占用分摊则需要一个谁都不认的算法。

> 处置方式不是自动删原件（交付不等于放弃），而是在交付确认框里明示："原件仍在你名下、占用个人额度；如需释放可移入回收站。"用户自己决定。

**为什么不用"素材条数"计量**：这是最直观也最坑的口径。按条数计，一次复制 = 计费翻倍，用户会立刻学会"不复制、直接改别人的"，正好废掉整个复用机制；而存储成本其实一点没涨。**计费口径会直接塑造用户行为**，选错等于给最想鼓励的动作加税。

**候选、草稿、回收站怎么算：**

| 状态 | 计不计额度 | 显示方式 |
| --- | --- | --- |
| 候选（`candidate`） | **不计**（§6.5） | 只在待确认区显示条数，不显示体积 |
| 已采纳 / 上传素材 | 计 | 总量主数字 |
| 草稿桶（`tier=draft`） | 计 | 单独一行"草稿 2.1G · 14 天后回收" |
| 回收站（软删） | **不计**（账面已释放） | 单独一行"回收站 1.4G · 清空可释放" |
| 物理已删（`ref_count=0`） | 物理释放 | 不显示 |

> 草稿要单独显示的原因：它占真实空间，藏起来会让"我删了很多东西空间却没变"变成不可解释的谜；混进总量又会让用户误以为自己超标。
>
> 回收站不计账面、但**物理不释放**（`blob.ref_count` 仍 > 0）。因此会出现"账面还有余量、物理已满"：此时新上传被拒，提示"回收站占用 1.4G，清空可释放"。**这是刻意的**——回收站里的东西随时可能被恢复，不能在恢复时因为"额度已满"而失败；而物理空间必须有个真实的上限。

## 7. 六、前端页面结构

### 7.1 双形态：一个组件，两种密度

| | 管理页 | 工作台抽屉 |
| --- | --- | --- |
| 密度 | comfortable（卡片 200px+，双行信息） | compact（卡片 120px，单行信息） |
| 顶栏库切换 | 有 | 有（压缩为下拉） |
| 分类条 | 横向胶囊，两层 | 只显示一级，二级收进筛选 |
| 筛选条 | 常驻 | 折叠为"筛选 (3)"按钮 |
| 控制条 | 吸顶 | 保留上传 + 排序，去掉视图切换 |
| 详情 | 右侧浮层 / 底部抽屉 | 同组件，宽度受限 |
| 批量 | 有 | 有（用于"一次插入多张"） |

**共享**：数据查询层（同一套 filter 与缓存键）、卡片组件、详情组件、筛选逻辑、空/错/载状态。
**不共享**：外层布局、控制条结构、分类条的折叠方式。

**为什么用密度而不是两套组件**：这个仓库已经付过一次代价——同一份能力做成两套接口、两套页面，问题永远只在其中一套里被修，另一套长期带病。所以"共享数据层 + 共享卡片 + 密度开关"是硬约束。但也**不能强行 100% 共享**：抽屉里塞进"视图切换、保存筛选视图、批量移动分类"这些东西会把抽屉变成一个迷你的管理页，违背它"随手取用"的定位。密度 + 能力开关（`capabilities`）两个维度控制，边界写在组件契约里。

### 7.2 管理页：纵向五段式

```
┌ ① 顶栏：库切换 ────────────────────────────────────────────────┐
│ [内容团队 ▾] 素材库   · 成员 8               搜索…    [上传素材]   │
├ ② 横向分类条 ──────────────────────────────────────────────────┤
│ [全部素材 213] [未分类 12] │ [产品图 149] [人物形象 86] [＋]      │
│   └ 展开后：图片 86 · 视频 23 · 音频 0（可折叠，带计数）           │
├ ③ 筛选条 ──────────────────────────────────────────────────────┤
│ [视图▾] 风格:写实 ✕  场景:棚拍 ✕  近30天 ✕   清空               │
│ 标签: 风格 ▾ 场景 ▾ 镜头 ▾ 主体 ▾ 用途 ▾ 属性 ▾  ＋更多        │
├ ④ 吸顶控制条 ──────────────────────────────────────────────────┤
│ 共 213 项 · 匹配 86    [排序:最近上传▾] [网格|列表]  [选择]        │
├ ⑤ 内容区 ──────────────────────────────────────────────────────┤
│  ▢ ▢ ▢ ▢ ▢ ▢      网格：全宽，最小列宽 180px，自动列数             │
│  ▢ ▢ ▢ ▢ ▢ ▢      列表：缩略图 + 名称 + 标签 + 时间 + 操作        │
│  ── AI 匹配（语义结果，追加在下方）──                             │
└────────────────────────────────────────────────────────────────┘
```

顺序的理由：**先定范围（库）→ 再定位置（分类）→ 再定条件（筛选）→ 再定呈现（控制条）→ 最后是内容**。每一步都在缩小集合，用户的视线是自上而下收敛的，不会出现"在筛选之后才发现库选错了"的回头路。

### 7.3 网格卡片

```
┌──────────────────────┐
│ [AI]            ●    │  ← 左上：生成型角标；右上：合规状态点
│                      │     绿=通过 黄=待审 红=驳回 灰=未评估
│      缩略图           │     只读时整体降饱和 + 右上加锁
│                      │
├──────────────────────┤
│ ▶ 产品主图-01.jpg     │  ← 类型图标 + 文件名（单行截断，hover 全名）
└──────────────────────┘
   悬停浮出：[插入] [衍生] [参考]
```

- 角标只在生成型出现（输入型不标"非 AI"，避免满屏角标）。
- 合规点在未评估时不显示灰点，而是一律显示——**为什么**："没有点"和"点是灰的"传达的信息不同，前者像加载失败。
- 悬停操作条必须**键盘可达**（Tab 聚焦卡片即出现），触屏用长按。纯 hover 的操作在触屏上等于不存在。
- 多选态：复选框常驻左上（与 AI 角标换位），操作条收起（避免与批量操作冲突）。
- 视频卡片：hover 静音预览首 3 秒，移出即停；音频显示波形占位而非空白。

**主体卡片（成组资产的变体）**：

```
┌──────────────────────┐
│ [AI]            ● ⑤  │  ← 右上合规点；再往左"N 张"计数
│   ╭────────────╮      │
│   │ 封面（主体）│▨▨    │  ← 右侧与下方各露 4px 的堆叠层（最多 3 层）
│   ╰────────────╯      │
├──────────────────────┤
│ ▣ 不锈钢保温杯-红      │  ← 类型图标换成"组"图标，名称是主体名
└──────────────────────┘
   悬停：扇出最多 5 张成员预览 + [插入] [查看 N 张] [衍生]
```

- 堆叠层只在"按主体合并"模式下出现；平铺模式里成员卡片与普通素材完全一致，但左上角带一个"组"角标，点角标跳主体。
- 主体卡片的主操作是"查看 N 张"，不是"插入"——插入时到底插哪一张必须由用户在浮层里选。**为什么**：默认替用户选封面，会在成品里反复出现同一角度，而用户以为系统"懂"了。

### 7.4 详情：右侧滑出浮层

选右侧浮层而不是固定侧栏，理由有两条：

- 侧栏会永久压缩网格宽度，在 1440 宽屏上等于少一列。
- 侧栏的"选中即打开"与多选冲突——多选时需要点卡片只勾选、不开详情。

浮层内容分四块，纵向滚动：

1. **大图/播放器** + 底部一行原始信息（尺寸、时长、大小、上传时间、上传人）。
2. **生成血缘**（仅生成型）：模型与版本、提示词全文（可复制、可折叠）、参考图缩略图（可点开，指向被引用素材）、参数表、种子（带"随机"标记）、生成时间、操作人。衍生链以横向缩略图序列呈现，当前节点高亮。
3. **标签与合规**：标签按维度分组，可增删（只能选词表）；合规状态与审批记录（谁、何时、依据）。
4. **引用关系**：被哪些模板/任务/素材引用（live / snapshot 分组），可跳转；`copied_from` 显示"复制自 …"。

底部固定操作栏：`插入`、`衍生`、`复制到当前分类`、`下载原件`（只读素材时前三项保留、后两项按权限）。

**为什么详情不做成新页面/新 tab**：素材浏览是"扫一眼再继续"的节奏，跳页面会丢失滚动位置与筛选状态（回来的成本比看详情还高）。浮层让上下文保持在原地，这是这类界面的关键。

### 7.5 批量操作替换控制条

多选后，第 ④ 段控制条**原地变形**，不新增一层：

```
普通：  共 213 项 · 匹配 86    [排序▾] [网格|列表]  [选择]
多选：  ✓ 已选 7 项  [全选本页] [清空]  [移动分类] [打标签] [复制] [⋯]  [退出]
```

**为什么原地变形**：新增一条批量栏会让页面在进入多选时整体下移，用户刚要点的卡片跑掉了；而且吸顶区域会变成两条，滚动时占掉更多屏高。

批量操作结果必须逐条可见（成功/失败/跳过），不允许只给一个"操作完成"。批量移动与批量复制都走 §5.3 的确认层（含"已存在的跳过"提示）。

### 7.6 滚动时三层合并

```
滚动前                       滚动后（> 24px）
┌ 分类条 ──────────┐         ┌ 精简条 ──────────────────────┐
├ 筛选条 ──────────┤   ──►   │ 个人库 · 产品图 · 4 个条件 ▾ │
├ 控制条 ──────────┤         │                  [排序] [上传] │
└──────────────────┘         └──────────────────────────────┘
                              ↑ 单行 48px，点击"4 个条件"展开筛选
```

**为什么合并**：三段各自吸顶在 1440×900 的屏上会吃掉近 1/3 高度，网格一屏看不全一行半。合并成单行后，用户仍然知道"我在哪个库、哪个分类、筛了什么"，但把垂直空间还给内容。展开时以覆盖层出现，不推挤内容。

### 7.7 边界状态

| 状态 | 表现 | 禁止 |
| --- | --- | --- |
| 首次加载 | 网格骨架（6–8 个占位块），计数显示 `—` | 不显示"暂无素材"，不显示 `0` |
| 分类空 | "「产品图」还没有素材" + 上传入口（有权限时） | 不复用"搜索无结果"文案 |
| 搜索/筛选无匹配 | "没有匹配的素材" + 一键清空条件 | 不提示"上传第一条"（用户明明有素材） |
| 语义检索中 | 主网格已渲染，语义区显示"AI 匹配中…"+ 3 个骨架 | 不阻塞主网格，不显示全局 loading |
| 语义检索失败 | 语义区一行提示 + 重试，主结果不受影响 | 不弹全屏错误 |
| 语义结果为空 | 一行"没有语义相近的素材"，不展开空区 | 不显示空插画占位 |
| 只读库 | 卡片降饱和 + 锁；写操作置灰并给"复制后修改"出路 | 不弹"无权限" toast |
| 列表刷新失败但有缓存 | 顶部细条"更新失败，当前为上次内容" + 重试 | 不清空已有网格 |
| 草稿将过期 | 卡片右上"3 天后回收"角标，详情有恢复按钮 | 不做成不可逆的静默删除 |
| 素材已被删除但仍被打开 | 浮层内提示"该素材已被删除" + 关闭 | 不显示空白浮层 |
| 主体缺图 | 卡片角标"缺 2 张"，置灰"发布/用于生成"，浮层列出缺失成员 | 不静默降级为"少几张也能用"；已有历史版本不受影响 |
| 主体未发布（草稿） | 仅创建者与团队管理员可见，卡片带"草稿"标，检索不召回（个人视图除外） | 不让草稿从搜索漏进公共视野 |
| 成员私有（可见域低于主体） | 主体照常可用；无权限者的该成员位置显示"1 张私有参考图"占位，服务端生成仍可读（`generate`），不可预览、不可下载 | 不暴露缩略图，**也不因此阻止发布**（这正是 §2.6.4 相对旧方案的核心收益） |
| 主体能力降级 | 详情浮层展示能力矩阵：可生成 ✓ / 原件下载 ✗（标注是哪张、为什么） | 不在下载时才报错，不在卡片上隐去整个主体 |
| 复制副本的源已被删除 | 详情"来源"一栏显示"源素材已删除"，副本本身照常可用 | 不给 404 断链，不自动清理副本 |
| 账面额度不足 | **上传前**拦截，提示"个人额度已用 98%，其中回收站 1.4G 可清空释放"，给两个动作：去清回收站 / 升级额度 | 不在上传到 100% 才报错，不把"额度"和"物理"混成一个数字 |
| 物理已满但账面有余 | 提示"回收站占用 1.4G，清空可释放"+ 直达回收站 | 不报"磁盘错误"这类没有出路的文案 |
| 上传进行中 | 批次内逐条状态（等待/处理中/成功/失败/未处理），锁定当前分类 | 不给虚构的百分比进度 |
| 有待确认候选 | 顶部横幅"待确认 N"，不并入网格 | 不把候选算进"我的素材 N 项"（规模感会失真） |

### 7.8 素材专业台（专员的两个编辑界面）

两个独立路由，**不放进五段式管理页**。

> **为什么**：编辑一个对象（组装主体 / 编辑模板）需要三栏、常驻校验、试跑，信息密度与"浏览一堆对象"的吸顶/批量/网格完全冲突。硬塞进去会把两个都做坏——管理页被编辑态的重面板拖慢，编辑态被吸顶条压到没有操作空间。

**组装台（主体）**

```
┌ 左：散素材池 ─────┬ 中：成员画布 ─────────┬ 右：属性与校验 ──┐
│ [搜索] [筛选]      │  正面   ┌───┐  [+]    │ 名称 / 类型       │
│ ▢ ▢ ▢             │         └───┘         │ 品牌 型号 颜色    │
│ ▢ ▢ ▢   ← 可拖    │  45度   ┌───┐  [+]    │ ── 校验清单 ──    │
│                   │         └───┘         │ ✓ 有封面          │
│ 已选 3 张          │  细节   ┌───┐  [+]    │ ✓ 成员权限足够    │
│                   │         └───┘         │ ! 缺「45 度」     │
│                   │  ＋ 添加角色            │ [试跑]  [发布]    │
└───────────────────┴───────────────────────┴──────────────────┘
```

- 拖入按"当前空槽"自动吸附角色；槽已满则问"替换 / 追加为新角色"。
- 校验清单常驻并实时更新，不弹窗；发布按钮未全绿时置灰，旁边直接写缺哪一项。
- 从库里拖入的素材若已在别的主体里使用，槽位上标"共用中"——专员要知道自己不是在复制。

**模板编辑器**

```
┌ 参考视频 ─────────────────────────────┐
│ [预览]  00:00 ──●────────────── 00:15  │
│ 运动段落：0–3s 推近 / 3–9s 环绕 / …      │
├ 提示词 ───────────────────────────────┤
│ {product_name} 的 {color} 产品，镜头…    │
│ 可用占位符：[product_name][brand][…]     │
├ 槽位声明 ─────────────────────────────┤
│ 必需：正面 · 45度      可选：细节        │
│ 张数：1–3    主图角色：正面               │
├ 试跑样例 ─────────────────────────────┤
│ [用「红色保温杯」试跑]   结果缩略图 ×3    │
└───────────────────────────────────────┘
```

- 时间轴标注是给提示词对齐用的：专员写"3–9s 环绕"时对着画面标段，减少"提示词节奏和视频对不上"这类跑完才发现的问题。
- 占位符以 chip 列出、点击插入，不许手打——**为什么**：打错一个字母就会永远填不进去，而症状是"提示词里显示了 `{product_nam}`"这种要到成品里才看得见的东西。
- 试跑样例区保留最近几次结果，用于对比"改了提示词之后是变好还是变坏"。

### 7.9 候选确认区（AI 产物的待确认）

同一组件，两处复用：素材库顶部一条横幅；生成工作台里则是生成完成后就地出现的结果面板。

```
┌ 待确认 12 ─────────────────────────── [全部采纳] [管理] ┐
│ 批次 · 今天 14:32 · 保温杯换产品 · 8 张（已采纳 2）        │
│ ▢ ▢ ▣ ▢ ▢ ▢ ▣ ▢      ← ▢ 待选  ▣ 已采纳                  │
│ 批次 · 今天 11:05 · 人像风格迁移 · 4 张                   │
│ ▢ ▢ ▢ ▢                                                  │
└──────────────────────────────────────────────────────────┘
```

- **以批次为单位分组**，不按时间铺平。同一批的 8 张必须放在一起比较，否则用户在几十张候选里分不清哪几张是同一提示词的变体，只能全采纳——库立刻被废片塞满。
- 生成工作台里生成完就地出面板，不等用户离开页面：`A` 采纳 / `D` 弃用 / 空格切换选中 / 方向键移动。**为什么必须给键盘**：一次 8 张，鼠标点 8 次采纳的现实结果是"全选采纳"，候选机制等于没做。
- 采纳后卡片**淡出右移**而不是瞬间消失，已采纳计数 +1；让用户看见"我刚才点的那下生效了"。
- 横幅在候选为 0 时**消失**（不像"未分类收件箱"那样常驻）。**为什么**：候选是待办，不是分类；常驻的空待办只会变成视觉噪音。
- 超过 20 条时折叠为"待确认 32（查看）"，不吃掉首屏。

边界状态：

| 状态 | 表现 |
| --- | --- |
| 生成失败 | 面板显示失败原因 + 重试，**不产生候选记录** |
| 全部弃用 | 计数归零、横幅消失，字节进回收队列 |
| 采纳时已过期 | 卡片标"已清理"，不可采纳，给"重新生成" |
| 采纳成功但列表刷新失败 | 分开提示"已采纳 / 列表更新失败"，不让用户以为没生效 |
| 部分采纳 | 已采纳的移出候选组，剩余继续等待，批次头显示"8 张（已采纳 2）" |
| 长任务未完成 | 显示进度与预计，候选位先占位（禁用），避免用户以为没生成 |

## 8. 落地顺序

| 批次 | 内容 | 为什么先做 |
| --- | --- | --- |
| M1 | **team 实体（三团队 + 成员关系）** + `blob` 拆分 + **配额口径（按可见域聚合、`sha256` 去重）** + 分类表（按库隔离）+ 未分类收件箱 + 媒体类型系统判定 | team 必须在建分类表之前就有：分类树属于库，`category` 需要 `team_id`。这几项都是地基，且回填可验证（哈希、计数、类型、成员能全对账）。配额要跟 `blob` 同期上线——它是用户第一眼看到、也最容易被质疑的数字，晚做就得对已上传的存量重新算一遍 |
| M2 | 受控标签词表 + 筛选条 + 保存视图 | 不依赖向量，用户立刻可感知；标签数据也可反喂语义检索的文本向量 |
| M2.5 | 主体：成员关系 + 角色词表 + **角色默认授权（`grants` / `in_output`）+ 角色可达与能力可达校验** + 封面 + 主体卡片（替换现有 pack 的读路径） | 只依赖 M1；不先做这层，标签与检索会按"单图"建模，之后补聚合要重做结果集与卡片。能力模型必须与主体同期落地——晚一步补，`grants` 就得对存量成员做一次人工回填，而那时没人记得哪张能下载 |
| M3 | 配方与血缘 + **候选与采纳（转正）** + 详情浮层 + 衍生的三个入口 | 依赖 M1 的记录结构，独立于检索。候选机制必须在"生成结果入库"这一步之前就位，否则第一批生成物会直接混进素材库 |
| M3.5 | 模板实体 + 槽位契约 + 组装台与模板编辑器 + 试跑与发布 | 专员的价值全在这一层；没有它，主体只是"整理好的图组"，生成时仍要人肉挑图。依赖 M2.5 |
| M4 | 向量索引 + 语义分区 + 上下文推荐（含主体聚合 max） | 成本最高、最易回滚，放最后；前面几步已经把"找不到"解决掉大半 |
| M5 | **复制进团队（待审区 + 批次审核 + `maintainer`）** + 提升到公共 + 团队管理员授予 + 只读态与能力受限态 + 分桶过期 + 主体版本发布 | 涉及组织流程，需要运营侧配合；跨团队不可见与可见域从 M1 就生效，M5 补的是"往上递"这两条流程。复制排在 M5 而不是更早，是因为它必须先有审核人与团队管理员——没有审核人，待审区会变成一个无人清的堆积区 |

明确不做（本期）：物理永久删除入口、多人实时协同编辑标签、跨团队素材市场、自动生成标签（先只做人工 + 管理员新增）。

## 9. 最容易踩的六个坑

### 坑 1：把"库/权限"做成分类树的节点
**症状**：上线三个月后有人发现"公共素材"这个节点下的计数与"产品图"分类加起来对不上，因为两者有交叉；更糟的是把素材拖进"公共"分类时，用户以为在整理，实际做了一次发布。
**规避**：库与分类是两个正交维度，物理上分开——库是 `visibility` 字段 + 顶栏切换器，分类是 `category_id` 单值列。在数据层就不允许出现 `category = 'public'` 这类值；做一个断言测试：分类表里不允许存在与可见域同名的系统分类。

### 坑 2：配方里把参考图存成 URL 数组
**症状**：当期能用，三个月后需要"这张图被哪些成片用过"时发现只能全表扫 JSON；某张参考图被删了，历史配方里的链接变成 404，血缘断在这里；换存储桶后所有旧配方一起失效。
**规避**：参考关系落关联表（带 `role` 与顺序），URL 只在出参时按当前存储驱动现拼。配方存"指向",不存"地址"。

### 坑 3：引用与快照共用一种关系
**症状**：要么"管理员更新了模板，历史成片的配方跟着变了"（跟随式做血缘），要么"模板换版后没有任何引用方收到更新"（冻结式做模板）。两种都不会立刻报错，只在某次审计或某次复现失败时爆出来。
**规避**：`pinned_version` 可空，空=跟随、非空=冻结；代码命名就分开（`ref` / `snapshot`），UI 文案分开（"跟随最新" / "已锁定 v3"）。默认策略写进文档：模板默认跟随，血缘默认冻结。

### 坑 4：向量检索先取 topK 再过滤权限
**症状**：语义结果条数总是少于预期，且不可见素材越多、结果越少；细心的人能从"结果数量随账号变化"推断出库里的隐藏资产规模。
**规避**：SQL 里就是 `WHERE 可见 AND 分类 ORDER BY distance LIMIT k`，不是先取后过滤。对"过滤后不足 k 条"显式返回 `hasMore=false`，让前端知道"就这么多"，而不是"还在加载"。

### 坑 5：抽屉和管理页做成两套实现
**症状**：抽屉里能按标签筛，管理页不能（或者反过来）；修复某个空状态只改了其中一处；一年后没人敢动抽屉，因为它"有自己的逻辑"。
**规避**：数据查询层、卡片、详情、筛选逻辑全部单实现，靠 `density` + `capabilities` 两个参数区分形态。验收时对两种形态跑同一组筛选断言（同一个 filter 输入，两种密度下结果条数必须一致），把它做成契约测试而不是人工对比。

### 坑 6：用"转移所有权"把素材交给团队
**症状**：转移后原作者再也改不了自己做的图，于是他复制一份继续改，库里出现两条会各自演化的同名素材；或者更常见——原作者调岗离职，团队库里那批素材的 `owner` 变成一个不在团队的人，谁也不敢改，因为"那是他的东西"。
**规避**：**个人 → 团队一律新建副本 + 批次审核，不改任何已有记录的 `owner`**；副本用 `maintainer` 表达"现在归谁维护"（可转交、管理员可接管），`origin_owner` 保留"最早是谁做的"（不可变）。只有团队 → 公共才改可见域，且此时 `owner` 仍不变。**判据**：如果一个动作会让"谁创建"和"谁负责"同时变化，它就是两个动作被错误地合并成了一个。

## 10. 一句话总结

这次改造的实质不是"给素材加标签和搜索"，而是把**一条记录同时承担"字节、归属、事实、权限"四种角色**拆开：字节归 `blob`、归属归 `asset`、事实归 `recipe`、权限归 `visibility`。四种角色一旦分开，复制、引用、过期、血缘这四件互相冲突的需求才有各自的落点；不分开，任何一件都得靠特例实现，而特例会随功能数量指数增长。

拆开之后还有第五件事需要独立表达：**"同一个东西的几个视角"**——产品与人物天然成组，这既不是素材的属性，也不是字节的属性，只能由 `subject` 承担。把它压进 asset，前四种角色会重新黏在一起（因为组又要开始承担归属与权限），拆分的收益当场归零。

第六件是这次最后补上的：**"能不能被发现"与"能拿字节做什么"也是两件事**。可见域只回答前者，能力回答后者。两者一旦合成一个可比较的档位，就只剩下两条路——要么为了让别人能用而批量抬权（成员权限集体上浮、角色分层消失），要么放弃校验（出现"能调用但读不到"的幽灵状态）。拆开之后，"公开的产品里含一张未授权原片"不再是违规或漏洞，它只是能力矩阵里的一列：可生成、不可下载。
