## 0. 一页结论

本次审查覆盖整个仓库（后端 `api/`、前端 `studio/`、契约与迁移），方法是**先测基线 → 三路并行深审（权限安全 / 数据并发 / 前端链路）→ 逐条回源码复核 → 对可判定的项写临时探针实跑**。

结论：**四条高危里有三条落在同一个根因上 —— 「写操作缺谓词 / 校验太晚」**：

1. 终态保护是「读后写」，不是原子条件更新（三个模块 + 巡检）；
2. 乐观锁与版本号校验同样是读后写（模板草稿、资产 state_version）；
3. 发布闸放过正文里的坏引用，等到使用者点生成才 400。

也就是说，这套代码**注释与测试里写着的保护，与实际发出的 SQL 之间有系统性落差**：守卫生效的前提是「读到之后没有别人插进来」，而这个前提从来没有被机制保证过。这与仓库自己的反模式清单 #2（读-改-写不加锁）和 BE-09 完全对得上，只是此前没人把三处 `_guard` 放在一起看。

第四条高危独立：**图片模板的提示词上限与生图端点漂移**，属于「上限没有随能力声明」，钉住常量的测试只覆盖了视频端点。

## 2. 发现

### 2.1 高

#### 问题 1 · 图片模板的提示词上限与执行端点漂移，使用者填完素材才 422

- **位置**：`api/src/modules/image/schema.py:99`（`GenerateImageIn.prompt`，`max_length=2000`）；`api/src/core/template_spec/models.py:52`（`EXECUTION_PROMPT_LIMIT = 7000`）；`api/src/modules/template_pack/spec_service.py:287`（发布闸）与 `:1152`（编译后长度）；`studio/src/features/template-library/taskPayload.ts:188`（`prompt: compiled.prompt`）；`studio/src/features/template-library/SpecLibrary.tsx:747`（走生图端点）
- **触发**：作者用**图片模型**写 2001–7000 字的提示词 → 发布通过（按 7000 判）→ 编译通过 → 使用者填完素材点「生成图片」→ 落到生图端点的 `max_length=2000` → **422**
- **根因**：上限常量是**端点**的属性，但只按「视频任务端点」钉了一份。`api/tests/test_template_spec_api.py:714` 的守卫测试名就叫 `test_execution_prompt_limit_matches_task_schema`，断言对象是 `modules.task.schema.CreateTaskIn`，**没有覆盖 `modules.image.schema.GenerateImageIn`**
- **影响**：作者能发布一个所有人都用不了的模板；错落在使用者的操作里，作者看不到自己的问题。这正是那条守卫测试注释里写明要避免的形态：「模板能发布、填表能编译、点生成才 422」
- **建议**：上限随能力声明（`Capability.IMAGE` / `Capability.VIDEO` 各带一个 prompt 上限），发布闸按模板模型所属能力取对应上限；守卫测试改成遍历所有执行端点的 schema，而不是只对 task schema

#### 问题 2 · 终态保护是「读后写」，不是原子条件更新

- **位置**：`api/src/modules/task/pipeline.py:82`（`_guard`）、`api/src/modules/image/pipeline.py:117`（`_guard`）、`api/src/modules/model_driver/store.py:31`（`_guard`）、`api/src/modules/export/service.py:289`（导出超时巡检）
- **触发**：A 读到 `running` → 另一会话提交 `cancelled` / `completed` → A 继续按自己读到的状态写回
- **行为**：三处 `_guard` 的形状一致 —— `session.get` → `flush()` → `refresh()` → **在 Python 里**判 `status in TERMINAL` → 之后 ORM 发出的 UPDATE 只有 `WHERE id`，没有 status 谓词。刷新确实读到了别人刚提交的终态，但**判断与写入之间隔着 `await`**，中间状态一变就被覆盖
- **影响**：用户先见「已取消」又见「生成中」，进度条回退，产物还进了草稿箱；导出超时巡检同理会把已 `succeeded` 的导出改回 `failed`
- **修正说明**：子审报告把机制描述成「巡检无条件覆盖终态（SELECT 不筛状态）」，**这一点不准确** —— SELECT 本身按 `status IN (queued, running)` 筛选（`api/src/modules/task/worker.py:57`）。真正的缺陷在**写的那一步没有谓词**
- **对照**：同仓库 `api/src/modules/library/lifecycle.py:381` 已用「条件 DELETE + rowcount 判定」的正确写法，可直接照抄；`modules/library/{sharing,text_assets}.py` 亦然
- **建议**：把终态判断下沉到 SQL —— `UPDATE ... WHERE id = ? AND status NOT IN (终态)`，用 `rowcount` 判定是否真的写到了；命中 0 行即说明状态已被别人推进，按「已被推进」返回

#### 问题 3 · 发布闸放过正文里的坏引用，等别人点生成才 400

- **位置**：`api/src/core/template_spec/rules.py:222`（`_validate_prompt_text` —— 不做残留引用检查）、`api/src/core/template_spec/rules.py:586` / `:610`（`has_bad_slot_ref` **只用在两段槽位文案上**）、`api/src/core/template_spec/compile.py:216`（真正的拦截在这里）
- **触发**：正文写 `主图 {{Mixed 1}}，再加一张 {{slot:Hero}}`（大写 key、少括号等任何形状不坏的引用）
- **探针实测**：`validate_spec` / `validate_required_slot_refs` / `validate_optional_slot_refs` **全部通过** → 预检绿、发布绿 → 使用者提交时 `compile_spec` 抛「提示词里有无法解析的槽位引用」
- **影响**：作者能发布一个**所有人都用不了**的模板，错误现场在别人的操作里。同一份代码里 `compile.py:40-42` 已经把这类形态点名（「预检与发布都过、用户在模板库点生成才 400」），但闸门位置放错了层
- **可达性**：前端编辑器会拦（`studio/src/features/template-specs/specDraft.ts:1006` 的 `promptRefError`），所以主路径被挡住；缺口在**API 直调、存量数据、其他写入路径（案例快照 / 迁移脚本）**。后端不能只靠前端（SEC-01）
- **建议**：在 `_validate_prompt_text` 里对正文与随机档各加一次 `has_bad_slot_ref`（它本来就摘掉合法引用再查残留）

#### 问题 4 · 模板规格列表接口 N+1

- **位置**：`api/src/modules/template_pack/spec_service.py:970`（`items = [await _spec_out_of(session, row) for row in rows]`）、`:267`（`_spec_out_of` → `_latest` + `_slots` 各一条 SQL）
- **探针实测**：造 5 条已发布模板 → 列表接口发出 **18 条 SQL**（6 条鉴权 + 1 条 count + 1 条主查询 + **10 条逐行查询**）；未发布的草稿因为 `current_version == 0` 提前返回，不触发
- **影响**：`pageSize` 上限 100 → 单次列表请求 200+ 次查询；模板库页面每翻一页都打一次（BE-12 / PERF-01）
- **建议**：按页内的 spec id 批量取「当前版本」与「槽位行」，各一条 `IN (...)` 查询，替掉逐行的 2N 条

### 2.2 中

#### 问题 5 · `POST /model-driver/libtv/progress` 横向越权 + 回环 SSRF

- **位置**：`api/src/modules/model_driver/libtv/routes.py:97`（路由，只要求 `task:read`）、`api/src/modules/model_driver/libtv/account.py:363`（`progress` 直接转发上游）、`:193`（`account` 一路当 CDP endpoint 传给 node）
- **触发**：任意持 `task:read` 的账号（内置 viewer / editor 角色都有该码）
- **行为 A（越权）**：`payload.task_ids` 是上游 LibTV task_id 列表，**未与 `video_tasks` 做归属比对**。上游账号是全团队共用，响应含 `status / percent / queue_position / failed_reason`，即他人任务的排队与失败原因。同一模块的任务读取走的是 `task:read:all` 独立权限码（`api/src/modules/task/service.py:323` 的 `_can_access`），此处口径不一致
- **行为 B（SSRF）**：`payload.account` 完全由客户端给，服务端随即 `GET http://127.0.0.1:<任意端口>/json/version`（限制在 loopback + http，但足以探测本机端口）；每次请求 spawn 一个 node 子进程；`task_ids` 长度无上限
- **建议**：`task_ids` 先与当前用户在 `video_tasks` 里的 `external_id` 取交集（不在集合内的不查）；`account` 改为只允许配置里已登记的账号别名，任意 CDP 地址不接受

#### 问题 6 · 并发打标撞唯一索引 → 500

- **位置**：`api/src/modules/library/tags.py:437`（`replace_asset_tags`：DELETE 非保留项 → SELECT 当前 → INSERT 缺失项）、唯一索引在 `api/src/modules/library/models.py:201`
- **触发**：两人同时 PATCH 同一资产且 `tag_ids` 有交集 —— 双方都 SELECT 不到、都要 INSERT，后提交者 `IntegrityError` → 500
- **附带**：一方刚 INSERT 的标签会被另一方的 DELETE（`not_in(kept)`）删掉 → 标签丢失
- **建议**：INSERT 改 `ON CONFLICT DO NOTHING`；或整体改成「条件 DELETE + 差集 INSERT」的幂等写法（与问题 2 同一根因：写操作缺谓词）

#### 问题 7 · 乐观锁读后写，并发下失效（丢失更新）

- **位置**：`api/src/modules/template_pack/spec_service.py:644`（草稿 `revision` 校验）、`api/src/modules/library/service.py:684` / `:715`（`state_version`）
- **触发**：两个请求带同一个 `revision` / `expectedVersion` 并发提交
- **行为**：校验在**读到的行**上做（`payload.revision != head.revision` → 409），随后的写是无条件 UPDATE。两个请求都能通过校验，后写者覆盖先写者，版本号只 +1 → 前端拿到的版本号无法区分「谁覆盖了谁」
- **建议**：改成条件 UPDATE（`WHERE id = ? AND revision = ?`）并用 rowcount 判定；0 行即 409

#### 问题 8 · 并发发布模板 → 500

- **位置**：`api/src/modules/template_pack/spec_service.py:743`（`version = head.current_version + 1`，无锁）、唯一约束 `api/src/modules/template_pack/models.py:139`
- **触发**：同一草稿被并发发布两次
- **行为**：两次算出同一个 version → 撞 `uq_template_spec_versions_spec_version` → `IntegrityError` 未捕获 → 500（幂等分支 `:720` 只在串行下成立）
- **建议**：与问题 7 同法，条件 UPDATE 抢占版本号；或捕获 IntegrityError 后重查最新版本返回它（幂等语义更贴「重复发布返回同一版本」这句承诺）

#### 问题 9 · 创建任务 / 生图没有幂等键 → 双击两次付费提交

- **位置**：`api/src/modules/task/service.py:357`、`api/src/modules/image/service.py:209`；在途上限闸 `api/src/modules/task/service.py:332`（`_assert_in_flight_room`，只限条数不判重）
- **触发**：客户端双击「生成」，或 POST 读超时后重试
- **行为**：每次都新建一行、各自 `provider.submit` 一次 → 两条任务、两次供应商提交、两次计费
- **建议**：受理时接受幂等键（提交方生成），唯一约束落在「幂等键 + 主体」上；同键不同业务参数拒绝（检查清单 BE-33 / GEN-05）

#### 问题 10 · Mixed 形态的畸形 token 全链路不拦，原样进供应商提示词

- **位置**：`api/src/core/template_spec/rules.py:43`（`_MIXED_REF`）、`:67`（`_LEFTOVER` 只找 `{{slot:`）、`api/scripts/migrate_spec_ref_modifiers.py:60`（迁移脚本同形状）
- **触发**：正文里出现 `{{Mixed 2 *}}`（修饰符前有空格）、`{{Mixed2}}`、`{{Mixed}}`
- **探针实测**：这三种形态 `validate_spec` 全部通过；`compile_spec` 的成品提示词里**原样保留**这三个字符串（`{{Mixed 1}}` 是合法编号形态，不受影响）
