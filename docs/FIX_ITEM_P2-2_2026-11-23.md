## 1. 背景

素材库的乐观锁一直用 `expected_version` 传递「客户端看到的资产版本」，
但这个字段的**取值 0 同时表达了两种意思**：

- **「我不关心版本，别校验」**——`_check_version(row, expected)` 里
  `if expected and ...`：0 被当作「跳过校验」；
- **「版本号就是 0」**——而资产的 `state_version` 从 1 起，0 根本不是合法版本。

后果是：**任何漏传版本的调用都会静默降级为「不校验」**。
主计划里的 P0-1、P0-4 是在**症状层**绕开它：

- P0-1：审批时 `expected = payload.expected_version or row.expected_version`，
  0 回落到申请单快照，不再等于「不校验」；
- P0-4：批量入口对会消费版本的动作做前置校验，缺版本直接 400。

这两处让「共享审批」和「批量写」不再是空转，但**根因还在**：
`expected_version: int = 0` 这个类型和默认值还留在 schema 里，
下一个写接口的人照样会踩进去——而且是在**静默**的情况下。

## 2. 范围与目标

### 范围内

只覆盖 `expected_version` / `expected_versions` 的**取值语义**：

- 把「不校验」与「版本号 0」拆成两个可区分的取值；
- 明确哪些接口**必须**带版本、哪些允许不校验；
- 给出可灰度、可回滚的迁移路径。

### 范围外

- 不改任何业务语义（哪些动作该校验、哪些不该，本次不动）；
- 不动乐观锁的**实现**（`_check_version` 的比对逻辑）；
- 不在本轮改代码——本轮只产出决策记录与代码里的 TODO 标记。

### 目标

让「漏传版本」这件事**不可能被静默忽略**：要么显式不校验（`None`），
要么显式带版本，任何一种都不会落到「因为是 0 所以放行」。

## 3. 现状分析

| 字段 | 位置 | 现在的含义 | 问题 |
| --- | --- | --- | --- |
| `ShareRequestIn.expected_version: int = 0` | `api/src/modules/library/schema.py` | 0 = 不校验 | 漏传即不校验 |
| `ShareDecisionIn.expected_version: int = 0` | 同上 | 0 = 不校验 | 漏传即不校验（P0-1 已用快照兜底，但类型没变） |
| `DraftDecisionIn.expected_version: int = 0` | 同上 | 0 = 不校验 | 漏传即不校验 |
| `BulkIn.expected_versions: dict[str, int]` | 同上 | 缺 key = 该条不校验 | 缺 key 与「版本 0」不可区分 |
| `_check_version(row, expected: int)` | `api/src/modules/library/service.py` | `if expected and ...` | 0 = 跳过校验 |

`state_version` 从 1 起（见 `LibraryAsset.state_version` 的默认值与自增逻辑），
所以 **0 永远不是合法版本号**——这正是「用 0 当哨兵值」不可行的根本原因。

## 4. 方案选型

### 方案 A：`Optional[int] = None`，`None` 表示不校验（**建议**）

```python
expected_version: int | None = None   # None = 明确不校验；0 = 非法输入
```

- `None` 与 `0` 可区分：漏传（默认 `None`）和「明确不校验」在类型上仍然同义，
  但**0 不再是哨兵值**——带 0 的请求会被当成「非法版本」拒绝（422/400）。
- 调用方要表达「不校验」必须**显式写 `None`**，写错就报错而不是静默放行。
- 代价：`Optional` 在调用链上多一层判空；前端要能区分「不带这个字段」和
  「带 null」。

### 方案 B：保持 `int = 0`，只在注释里写清楚

- 零改动，但**不解决根因**：下一个人还是会写 `if payload.expected_version and ...`。
- 与 P2-1 新增的静态守卫（写操作必须带版本）部分重叠，但守卫只能挡住
  「写死 0」，挡不住「漏传」。

### 方案 C：取消「不校验」语义，版本一律必填

- 最干净，但影响面最大：所有单条写接口都要改，前端每个入口都要带版本。
- 与主计划 P0-4 的批量必填校验是同一条路线，可以合并推进，但**不是本轮**。

### 结论

**采纳方案 A**，理由：

1. 它把「0 = 不校验」这个**双重语义**彻底拆掉，而这正是严重#1 的根因；
2. 改动面可控：只动 schema 的类型与默认值 + 若干判空，不需要重写乐观锁；
3. 可以分批迁移：先改 schema 与 `_check_version` 的判空，再逐个接口补 `None`；
4. 与方案 C 兼容——将来若决定「版本一律必填」，只需把 `None` 也拒掉。

**本轮不实施**，只留决策与 TODO（见 §7）。

## 5. 依赖关系与并行性

### 前置依赖

- **P0-1（已完成）**：共享审批的版本校验已改为「0 回落到申请单快照」。
  方案 A 与它**不冲突**：迁移时「不校验」的分支要显式写成 `None`，
  快照回落那条路径要保留（它是兜底，不是「不校验」）。
- **P0-4（已完成）**：批量入口缺版本即 400。方案 A 落地后，批量接口的
  `expected_versions` 从「缺 key = 不校验」改为「缺 key = 400」，
  现有守卫（`api/tests/test_architecture.py` 的写操作必须带版本）继续适用。

### 并行性（为什么互不阻塞）

- 本事项**不改**运行时行为，只改类型与默认值，
  因此**不阻塞**主计划的 P0/P1/P2 任何条目；
- 主计划的任何条目也**不依赖**本事项：P0-1、P0-4 已经用「回落到快照」
  与「缺版本即 400」把严重#1 的实际危害堵住了——
  即便本事项无限期不实施，线上行为也是安全的（只是类型上仍留着坑）；
- 因此本事项可以**独立排期、独立评审、独立回滚**：
  回滚只需把 `int | None` 改回 `int = 0`，无数据迁移、无接口契约变更。
