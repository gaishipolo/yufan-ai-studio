#### P0-1 · 共享审批绕过乐观锁（审查#1，唯一严重项）

**位置**：
- `api/src/modules/library/sharing.py:244`（版本判断被 `0` 短路）
- `api/src/modules/library/schema.py:533-548`（`ShareRequestOut` 缺 `state_version`，前端拿不到版本）
- `studio/src/features/library/ShareRequestsModal.tsx:46`（前端硬编码 `expectedVersion: 0`）

**问题**：`decide()` 的判断是 `if payload.expected_version and asset.state_version != payload.expected_version:`。
`0` 是 falsy，整条分支被跳过。申请单是快照（`sharing.py:250-251` 的注释自己承认），
若资产在申请后被改名/换标签/改可见性，审批人点「通过」时后端只重跑 `_recheck_target`
（校验共享目标是否仍有效），**不校验资产版本**——旧快照照样生效。
`request()` 路径（`:117`）有版本校验，`decide()` 路径实际没有，两条路径口径不一致。

**改法**（后端一处 + 前端一处 + 契约一处）：

1. **后端复用申请单已存的快照版本**。`LibraryShareRequest.expected_version` 存的就是申请发起时
   申请人看到的版本（`models.py:249`），且申请路径前端**确实传了**真实版本
   （`LibraryShareModal.tsx:103` 传 `expectedVersion: asset.stateVersion`）。
   所以后端不需要新数据，只需改回落规则：

   ```python
   # sharing.py:244 附近
   expected = payload.expected_version or row.expected_version
   if expected and asset.state_version != expected:
       raise Conflict(...)
   ```

   注释里写清「为什么 0 不再等于放弃校验」——呼应 `library/service.py:1431-1437` 的约定。
2. **`ShareRequestOut` 补 `state_version`**（申请单快照版本），前端据此展示「申请已过期」并回传。
   `LibraryAssetOut` 已带 `state_version`（`schema.py:213`），字段本就在契约里，只是没带到申请单出参。
3. **前端回传申请单快照版本**（`ShareRequestsModal.tsx:46`），不再硬编码 0。
4. **跑 `app export-openapi`** 重新生成四份契约（`docs/openapi.json`、`docs/API.md`、
   `studio/src/shared/api/schema.ts`、`studio/src/shared/api/permissions.ts`）。
   `api/tests/test_openapi_contract.py` 会做字节比对，不重新生成 CI 必红。

**注意**：`test_library_sharing.py:408` 的 `test_rejecting_an_outdated_request_is_still_allowed`
断言「驳回一条已经过时的申请单是正当操作，不能被 409 拦住」——**驳回路径不能加版本校验**，
否则这条既有正确设计会被破坏。只在 approve 路径生效。

**验收**：
- 新增用例：申请后修改资产 → 审批 → 409 且 `details.stateVersion` 与当前版本一致；
- 既有 `test_share_request_checks_the_expected_version`（`:513`）保持绿；
- 驳回过期申请单仍返回 200（`test_rejecting_an_outdated_request_is_still_allowed` 保持绿）。

**工作量**：3 小时（含用例与契约重生成）。

#### P0-2 · CSV 公式注入转义漏 `-`（审查#4，安全）

**位置**：`api/src/modules/export/sources.py:71-73`

```python
# CSV 公式注入：让 Excel 把这一格当文本，而不是执行它
return "'" + value if value[:1] in ("=", "+", "@", "\t", "\r") else value
```

**问题**：转义集合含 `= + @ \t \r`，唯独缺 `-`。`-` 是 Excel / LibreOffice 公式注入的经典触发字符
（`-2+3+cmd|' /C calc'!A0`）。导出 CSV 被用户用 Excel 打开时，攻击者可控的单元格内容
（素材名、标签名、审计 detail）可能被当公式执行——这条路径跨用户边界。

**改法**：补 `-`，但要兼顾负数：

```python
# 以 "-" 开头且后面不是数字/空白时才当公式（负数是合法业务值，"-2" 不能被改坏）
if value[:1] == "-" and not _NUMERIC_RE.match(value[1:].lstrip()):
    return "'" + value
```

`_NUMERIC_RE = re.compile(r"^[+-]?(\d+\.?\d*|\.\d+)([eE][+-]?\d+)?$")`。
**理由要写进注释**：单纯把 `-` 加进集合会把所有负数变成文本，那是数据损坏不是安全修复。

**验收**：新增用例——`-2` 原样输出、`-cmd|...` 前缀加 `'`；既有 `= / + / @` 行为不变。

**工作量**：1 小时（含用例）。

#### P0-3 · 导出失败把原始异常回显前端（审查#3，信息泄露）

**位置**：`api/src/modules/export/worker.py:100-108`

```python
record.status = ExportStatus.FAILED.value
record.error = str(exc)[:512] or type(exc).__name__
```

**问题**：`ExportOut.error` 是对外字段（`export/schema.py:49`），随列表/详情接口返回前端。
异常字符串可能含内部文件路径、SQL 片段、数据库连接串、上游依赖地址。
同一模块的其它两处错误都用了面向用户的中文文案（`service.py:165`「任务入队失败，请重新导出」、
`service.py:275`「导出超时未完成，请重新导出」），只有 worker 这一处是原始异常——口径不一致。

**改法**：

   **不要**把 `str(exc)` 写进去。
2. 完整异常保留在 `logger.exception`（`:108` 已有），并补上 `export_id` / `source`（已有）。
3. 若要保留可定位性，加一个稳定 `error_code` 字段（短码，非异常文本），供前端分流。

**注意**：worker.py:101-102 的注释说明了「吞掉异常是刻意的」（模块 docstring 第 2 条），
这条设计**保留**，只改写进对外字段的内容。

**验收**：新增用例——源查询抛异常 → 响应 `error` 不含异常类名/路径/SQL 片段，
且日志里有完整 traceback。

#### P1-2 · 导出产物在内存中整体拼装（审查#7）

**位置**：`api/src/modules/export/sources.py:77-84`；`api/src/modules/export/worker.py:84`

```python
# sources.py:79-84
buffer = io.StringIO()
writer = csv.writer(buffer, lineterminator="\r\n")
writer.writerow(list(columns))
for row in rows:
    writer.writerow([_cell(value) for value in row])
return ("\ufeff" + buffer.getvalue()).encode("utf-8")
```

**问题**：上限 10 万行（`export_max_rows`），中文场景 CSV 可达数十 MB。构造过程中同时存在
str 缓冲、拼接后的 str、编码后的 bytes 三份副本。`config.py:389-390` 明确指出
「worker 是共享进程，会连带同一进程里其他模块的 job 一起 OOM」——这正是放大器。
另外 `render_csv` 是同步 CPU 密集调用，在 worker 的异步处理函数里直接执行（`worker.py:84`），
会阻塞事件循环。

**改法**：
1. `render_csv` 改写为写入二进制流（`io.TextIOWrapper` + `io.BytesIO`，或直接用
   `csv.writer` 写 `BytesIO`），避免「str → 拼 BOM → encode」的三份副本。
2. `worker.py:84` 用 `asyncio.to_thread(render_csv, ...)` 移出事件循环。
3. 加字节数熔断：超过阈值直接失败并给用户文案，而不是把内存吃穿。

**验收**：新增用例——10 万行导出的峰值内存不随行数线性放大（可用 `tracemalloc` 断言量级）。

**工作量**：3 小时。

**位置**：`api/src/modules/library/schema.py:526-530`（`ShareDecisionIn.expected_version: int = 0`）；
`api/src/modules/library/service.py:1431-1437`（`_check_version` 里 0 = 不校验）

**问题**：同一模块内同一个字段名承载两套含义——`service._check_version` 里 0 = 不校验
（注释明写「单页操作没必要为了一个数字失败一次」），而共享审批场景需要 0 = 用申请单快照。
这是 P0-1 的深层成因。

**改法**：P0-1 落地后，审批路径的 0 有了确定含义（回落快照），**但通用路径的 0 仍是「不校验」**。
建议把「不校验」表达为 `Optional[int] = None`，让 `0` 成为一个**真实的版本号**而非哨兵值——
版本号从 1 开始，0 本身就不该出现在合法数据里。
若采纳，需要评估所有 `expected_version` 的调用点（改动面较大，建议单独排期，不阻塞前 11 条）。

**验收**：`expected_version=0` 的请求被显式拒绝或明确回落，不存在「静默不校验」的路径。

**工作量**：1 小时（立项）；**已实施**——见 §10 表格的 P2-2 行与 `docs/FIX_ITEM_P2-2_2026-11-23.md`。
